## 二、协议、注册与执行

### 2.1 MCP：智能体工具侧的协议基线

**【一手】MCP 传输与生命周期要点**（来源：MCP 规范资料汇总，`https://github.com/Heretyc/subagent-mcp/blob/main/skills/mcp-builder/references/protocol-spec.md`，原文要点；规范正文版本 2025-06-18）：

> "The client sends a version it supports. If the server supports it, the server 'MUST respond with the same version'; otherwise it 'MUST respond with another protocol version it supports'"

> "SSE transport is deprecated as of 2025-11-25. Use Streamable HTTP for new remote servers."

> "**stdio rule**: Never write anything to stdout except JSON-RPC messages. console.log in Node / print() in Python = fatal corruption."

**【一手】方法与原语**（来源：MCP 实践指南，`https://martinuke0.github.io/posts/2026-09-07-building-agents-with-mcp-the-model-context-protocol-in-practice`，原文要点）：

> "MCP is JSON-RPC 2.0. Three message types matter: initialize, the tools/list and tools/call pair, and the notifications/..."

> "The June 2025 spec added structured content, async task support, and the Streamable HTTP transport that replaces the older HTTP+SSE pair."

**能力协商与注册**：MCP 的「注册」是**能力协商**而非静态注册表 —— 服务端在 `initialize` 响应里声明 `capabilities`（如 `tools: {listChanged: true}`），客户端**只调用已声明的能力**；工具清单由 `tools/list` 动态获取。**【一手】** 原文要点（来源：MCP 教学材料，`https://techeazyconsulting.com/courses/building-ai-agents/session-02`）：

> "Server Capabilities Declare only what you implement. Undeclared = must not use."

⇒ 对本仓的映射：MCP 式能力协商 ≈ 本仓 `Endpoint` 需要补的**能力标记字段**（是否支持 tools / 流式 / 视觉）。**注册表是「静态声明」，能力协商是「运行时握手」**，两者不可互相替代。

### 2.2 MCP 取消规范（老宅场景的一手依据）

**【一手】全文要点**（来源：MCP 规范 `specification/2025-06-18/basic/utilities/cancellation`，`https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/cancellation.md`，原文逐条）：

> "The Model Context Protocol (MCP) supports optional cancellation of in-progress requests through notification messages. Either side can send a cancellation notification to indicate that a previously-issued request should be terminated."

> 取消通知的内容："The ID of the request to cancel" + "An optional reason string that can be logged or displayed"

```json
{
  "jsonrpc": "2.0",
  "method": "notifications/cancelled",
  "params": {
    "requestId": "123",
    "reason": "User requested cancellation"
  }
}
```

**行为要求（逐条引用原文）**：

1. "Cancellation notifications **MUST** only reference requests that: Were previously issued in the same direction; Are believed to still be in-progress"
2. "The `initialize` request **MUST NOT** be cancelled by clients"
3. "Receivers of cancellation notifications **SHOULD**: Stop processing the cancelled request; Free associated resources; **Not send a response for the cancelled request**"
4. "Receivers **MAY** ignore cancellation notifications if: The referenced request is unknown; Processing has already completed; The request cannot be cancelled"
5. "The sender of the cancellation notification **SHOULD** ignore any response to the request that arrives afterward"

**时序与竞态**：

> "Due to network latency, cancellation notifications may arrive after request processing has completed, and potentially after a response has already been sent. Both parties **MUST** handle these race conditions gracefully"

**错误处理**：

> "Invalid cancellation notifications **SHOULD** be ignored: Unknown request IDs; Already completed requests; Malformed notifications. This maintains the 'fire and forget' nature of notifications while allowing for race conditions in asynchronous communication."

**实现提示**：

> "Both parties **SHOULD** log cancellation reasons for debugging"
> "Application UIs **SHOULD** indicate when cancellation is requested"

⇒ **这七条是本仓取消语义的直接设计输入**：

| MCP 条款 | 本仓对应设计 |
|---|---|
| fire-and-forget、无 ack | `/cancel` 端点**不返回确认**，客户端不等待 |
| 接收方 SHOULD 停止处理 + 释放资源 + **不发响应** | 网关取消上游后**不再向下游发任何帧**，直接收口 |
| MAY 忽略（未知 / 已完成 / 无法取消） | 取消注册表查不到 / 已收口 ⇒ 静默忽略，不报错 |
| 发送方 SHOULD 忽略迟到的响应 | 取消后到达的迟到分片**丢弃**，不追加到客户端 |
| MUST 优雅处理竞态 | 取消与「上游刚好完成」同时发生 ⇒ 幂等收口，只记一次 |
| SHOULD 记录取消原因 | Trace 属性 `gateway.cancel.reason` |
| UI SHOULD 标示已请求取消 | 客户端状态机（前端职责，网关只提供证据） |

### 2.3 MCP 授权（与注册表同源的安全约束）

**【一手】原文要点**（来源：MCP 规范 `specification/2025-06-18/basic/authorization`，`https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization`，原文逐条）：

> "Access tokens **MUST NOT** be included in the URI query string"

> "authorization **MUST** be included in every HTTP request from client to server, even if they are part of the same logical session"

> "MCP servers **MUST** validate that access tokens were issued specifically for them as the intended audience, according to RFC 8707 Section 2."

> "MCP clients **MUST NOT** send tokens to the MCP server other than ones issued by the MCP server's authorization server."

> "If the MCP server makes requests to upstream APIs, it may act as an OAuth client to them. The access token used at the upstream API is a separate token, issued by the upstream authorization server. The MCP server **MUST NOT** pass through the token it received from the MCP client."

> "MCP proxy servers using static client IDs **MUST** obtain user consent for each dynamically registered client before forwarding to third-party authorization servers"

> "MCP servers **MUST** return appropriate HTTP status codes for authorization errors: 401 Unauthorized (Authorization required or token invalid); 403 Forbidden (Invalid scopes or insufficient permissions); 400 Bad Request (Malformed authorization request)"

**Confused Deputy 与 token passthrough**（同页原文）：

> "Attackers can exploit MCP servers acting as intermediaries to third-party APIs, leading to **confused deputy** vulnerabilities. By using stolen authorization codes, they can obtain access tokens without user consent."

> "The MCP server **MUST NOT** accept or transit any other tokens."（Token Passthrough 禁止）

⇒ 与本仓 `AGENTS.md` 规则 21（凭据隔离）完全同构：**网关自己发凭据，不透传调用方的**。本仓下一轮的凭据模型必须是「调用方凭据 → 网关凭据」两段式，而不是把调用方的 key 直接透传给 provider。

### 2.4 A2A：智能体之间的任务状态机

**【一手】任务状态与关联标识**（来源：A2A 协议规范中文社区版，`https://doc.a2amcp.cn/specification/`，原文要点；官方规范 `https://a2a-protocol.org/latest/`）：

> 任务状态枚举（活跃 / 中断 / 终态三类）：
> `TASK_STATE_SUBMITTED`（活跃）· `TASK_STATE_WORKING`（活跃）·
> `TASK_STATE_INPUT_REQUIRED`（中断）· `TASK_STATE_AUTH_REQUIRED`（中断）·
> `TASK_STATE_COMPLETED`（终态）· `TASK_STATE_FAILED`（终态）·
> **`TASK_STATE_CANCELED`（终态）** · `TASK_STATE_REJECTED`（终态）

> "`contextId` 是把多个 Task 和独立 Message 归为一组的关键标识"；"`taskId`" 标识单个任务

**【一手】安全考量**（来源：A2A 官方规范安全章节，`https://a2a-protocol.org/v0.2.0/specification/`，原文要点）：

> "Push Notification Security: Webhook URL validation (by the A2A Server sending notifications) is crucial to prevent SSRF."

> "Resource Management: Implement rate limiting, concurrency controls, and resource limits to protect agents from abuse or overload."

⇒ **取消要挂在 `taskId` 上，不是笼统地「取消整个会话」**；`contextId` 级取消需要显式遍历。这对本仓下一轮的 `client_request_id` 设计有直接含义：**取消粒度 = 单次上游执行**，会话归组另设字段。

### 2.5 OpenAI 兼容 API：客户端唯一需要知道的东西

三家网关一致的选择是**对外暴露 OpenAI 兼容 API**（agentgateway README、Envoy 1.0 release notes、LiteLLM 文档三处一致）。这意味着本仓下一轮的第一入口是 `POST /v1/chat/completions`，且**协议转换（Anthropic / Gemini / Bedrock ↔ OpenAI 形状）属于 provider 适配层的职责**，不进入网关核心。

## 三、路由与上下文

### 3.1 策略谱系与「可复现」约束

**【一手】LiteLLM 的策略清单与状态需求**（来源：LiteLLM Router 文档整理，`https://serhiismetanskyi.com/docs/libs/litellm/03-router-reliability`，原文要点）：

> "simple-shuffle (default) — Random, weighted by rpm/tpm/weight; **Most setups; no extra state**"
> "least-busy — Deployment with fewest in-flight requests"
> "latency-based-routing — Lowest recent latency"
> "usage-based-routing-v2 — Most remaining TPM/RPM headroom; Tight provider quotas; **needs Redis** with several instances"

**【一手】失败类型分级的 fallback**（来源：LiteLLM 官方文档，`https://litellm.vercel.app/docs/proxy/fallback_management`，原文要点）：

> "Fallback Types Explained — **General** Fallbacks: Used for any type of error that occurs during model invocation."
> "**Context Window** Fallbacks: Specifically triggered when a context window exceeded error occurs."
> "**Content Policy** Fallbacks: Specifically triggered when content policy violations occur."
> "Budget Fallbacks: reroute a request to another model when a per-key model_max_budget is exceeded"

**【一手】LiteLLM 自己的坑**（同上 skill 文档，原文要点）：

> "When using default_fallbacks, they do NOT apply to ContentPolicyViolationError or ContextWindowExceededError -- use specialized fallback types for those"

⇒ **直接映射到本仓**：现有 `Router.fallback_chain` 是**一条通用链**（`AGENTS.md` 规则 24 的「显式有序」要求成立）。但业界共识是**上下文超限与内容策略拒绝要走不同的降级路径** ⇒ 下一轮 `Router` 需要按**失败类型**产出不同的链，而不是只有一条。现有 `fallback_chain(primary)` 保留为「通用链」，另加 `fallback_chain(primary, failure_kind)`。

**【二手】可复现性的张力**（来源：`https://www.datastudios.org/post/litellm-multi-provider-routing-load-balancing-failover-and-cost-tracking`，原文要点）：

> "LiteLLM ships with two things: a Python SDK and a Proxy Server... Five routing strategies are available: simple-shuffle (the default), least-busy, latency-based, usage-based, and cost-based -- the last two need Redis to track state across requests."

⇒ 本仓 `AGENTS.md` 规则 24 要求「同输入 + 同注册表 + 同配置 ⇒ 同决策」；上表里 `usage-based` / `cost-based` 是**带状态**的，与该要求冲突 ⇒ 若将来引入，状态必须**显式化且可重放**（把状态作为决策输入的一部分），否则不可复现。本轮**不引入**带状态策略。

### 3.2 路由的学术口径

**【一手】综述定位**（来源：arXiv 2502.00409 摘要，`http://scirate.com/arxiv/2502.00409`，原文要点）：

> "This survey aims to provide a comprehensive overview of routing strategies in LLM-based systems. Specifically, it reviews when, why, and how routing should be integrated into LLM pipelines to improve efficiency, scalability, and performance. We define the objectives to optimise, such as cost minimisation and performance maximisation, and discuss the timing of routing within the LLM workflow, whether it occurs before or after generation."

> "It details the various implementation strategies, including similarity-based, supervised, reinforcement learning-based, and generative methods."

**【一手】级联的判据**（来源：FrugalGPT 思路的工程实现，`https://huggingface.co/spaces/Ypeng12/InferRoute/`，原文要点）：

> "A Reliability Judge assesses output quality at each tier, escalating to the next tier if the quality score falls below $\tau$."

⇒ 路由的两个正交维度：**生成前**（按请求特征选模型，如难度 / 长度 / 意图）与**生成后**（按质量判定升级）。本仓现有 `priority` / `round_robin` 属**生成前的静态选择**；第一阶段不做质量判定升级（需要模型输出与判官，成本高）。

### 3.3 上下文维度

- **上下文窗口是端点必备字段**（本仓已有 `context_window`）；
- **上下文超限需要专用降级类型**（见 3.1）；
- **prompt caching 是成本主手段**：**【一手】** OTel GenAI 规范的设计取舍（来源：`https://chengaoshen.com/en/posts/otel_genai`，原文要点）：

> "The Anthropic sub-spec introduces almost no proprietary new fields -- it just specifies `gen_ai.provider.name=\"anthropic\"` and how prompt-cache hit / write tokens should be expressed using common fields. The reasoning: caching isn't Anthropic-only (OpenAI does automatic cache, Gemini has context cache), so put it in the common namespace where other providers can reuse it later."

⇒ 本仓下一轮计量 token 时**要把缓存读写 token 单独记出来**（公共 `gen_ai.usage.*` 命名空间），否则成本核算会把缓存命中算成全价。

## 四、错误、治理与成本

### 4.1 错误分类：4xx / 5xx 必须分开

**【一手】LiteLLM 的归一化及其有损性**（来源：LiteLLM 错误诊断，`https://www.swfte.com/errors/litellm-errors`，原文要点）：

> "LiteLLM normalises every backend into OpenAI-compatible exception types: AuthenticationError, BadRequestError, RateLimitError, Timeout, ContextWindowExceededError, APIConnectionError, ServiceUnavailableError. That uniformity is the point of the proxy, and it is also why the surfaced error can look nothing like the real one."

> "a failure during upstream preparation or authentication can be normalised into a generic server error before any provider detail reaches your client"

⇒ **归一是对外的，原始信息必须对内保留**。本仓下一轮的错误对象要同时携带：归一后的对外分类 + **原始上游状态码与来源端点**。

这与本仓 `AGENTS.md` 规则 32 完全一致：

> "**不许把「端点校验更严导致 400」误报成「模型没能力」**：**现象**：换到一个严格端点后整轮请求 400，报告却按「可用样本 0」呈现……**根因**：400（请求不合法）与「模型答不出」是两类完全不同的失败，被同一个统计口径吞成了一类"

### 4.2 限流与预算：按 token，不只按请求

**【一手】Envoy AI Gateway 的 token 级限流**（见 1.1 引文）。

**【一手】agentgateway 的预算与用量控制**（来源：agentgateway 产品页，`https://www.solo.io/products/agentgateway`，原文要点）：

> "Set limits and stop budget surprises — Apply request and token-based rate limits to prevent budget overruns and provider throttling."

> "Token-based rate limiting per user, team, or API key. Fine-grained budget enforcement with denial-of-wallet protection. Per-model cost attribution and real-time consumption dashboards."

**【二手】OWASP 的 Denial-of-Wallet 与治理清单**（来源：`https://nhimg.org/ai-gateway-and-llm-gateway-guide`，原文要点）：

> "Count tokens, not just requests. Cost and abuse scale with tokens; gateways that only limit requests per minute leave Denial of Wallet (OWASP LLM10:2025) wide open."

### 4.3 熔断与冷却

**【二手】状态机描述**（来源：InferRoute 技术文档，`https://huggingface.co/spaces/Ypeng12/InferRoute/`，原文要点）：

### 4.4 重试 vs 降级：分别有上限

本仓 `AGENTS.md` 规则 24 已定：

> "**降级 ≠ 重试**：重试打同一个端点（换一次可能成功），降级换端点（换一次可能成功）—— 两者的次数**必须分别有上限**，不许合成一个「兜底循环」。"

**【一手】LiteLLM 的两级 order 语义**（来源：`https://www.datastudios.org/post/litellm-multi-provider-routing-load-balancing-failover-and-cost-tracking`，原文要点）：

> "Failover runs on an order field: lower numbers get tried first, each order level gets its own retries, and the router only escalates to the next order level -- or to a separate fallbacks list -- once a level is exhausted."

⇒ 业界实现与本仓规则一致：重试在「级」内、降级在「级」间，**两者各自计数**。

| 情形 | span status | `error.type` | `gen_ai.response.status` |

## 七、专题：流式请求的「用户点停止」全链路

> 这是老宅点名追问的场景，也是本轮调研信息量最大的部分。

### 7.1 场景与事实链

**场景**：发起一段流式请求 → 收到几段内容 → 用户点停止 → ①前端停止追加内容 ②网关取消这次上游请求 / 关闭上游响应流 ③Trace 能查到这次调用 ④可以取消结束。

**「用户点了停止」在协议层的标准形状**：MCP 用 `notifications/cancelled`（带 `requestId` + `reason`），是 **fire-and-forget、无 ack、必须容忍竞态**（全文见 2.2）。

**HTTP / SSE 侧没有对应标准** ⇒ 事实标准是**客户端 abort ⇒ TCP 断开**。

**【一手】浏览器侧的形状**（来源：SSE 实践文章，`https://www.dreaming.press/posts/how-to-stream-llm-tokens-to-the-browser-server-sent-events.html`，原文要点）：

> "On the server, listen for the request/response close event and call `AbortController.abort()` on the fetch to the provider — otherwise the model keeps generating (and billing) a response nobody will read."

> "EventSource ... only does GET" ⇒ POST + 自定义头场景须走 `fetch` + `ReadableStream`。

### 7.2 网关该做什么（五个动作）

**动作 1 —— 断连检测：不能只等「下一次写失败」**

写失败要等下一个 chunk 才有 ⇒ 两条路并行：**轮询 `request.is_disconnected()`**，或**独立 watcher task 监听 ASGI `http.disconnect` 并 cancel 主任务**。

**【一手】框架实测行为**（来源：ASGI 断连实测，`https://async-concurrency.com/network-io-protocol-handling/asgi-servers-and-frameworks/detecting-client-disconnects-in-asgi-handlers`，原文要点；环境：Uvicorn 0.54 + Starlette 1.7）：

> "a plain handler sleeping for 5 s was **not** cancelled; it ran to completion and its response was discarded."
> "A streaming response's generator was **cancelled** as soon as the server tried to write to the closed connection (0.5 s in)."
> "A handler that polled `request.is_disconnected()` every 100 ms noticed after 1.01 s, and a watcher that cancels the work on `http.disconnect` cancelled it at 1.00 s."

⇒ **判据**：普通 request-response handler **不会**被取消（跑满 5s）；**流式生成器会**（0.5s）；watcher 1.00s、轮询 1.01s。⇒ **非流式路径必须自己挂 watcher**；流式路径虽被框架取消生成器，**但不能依赖它去关上游**。

**动作 2 —— 取消传播到上游**

显式关闭上游 httpx 响应（`await response.aclose()`），或 cancel 上游请求 task。

**【一手】不做这一步的后果**（来源：流式代理工程指南，`https://www.technologyonthe.net/2026/10/streaming-backpressure-and-client.html`，原文要点）：

> "The proxy often keeps reading from the model, the GPU keeps decoding, and you keep paying for tokens nobody will see."

> "Silent orphan streams — the client TCP/HTTP connection is gone, but the proxy keeps the upstream request open until finish_reason or a hard timeout."

**【一手】计费的真实口径**（来源：`https://lmversity.com/learn/genai-app-dev/backpressure-and-cancellation`，原文要点）：

> "Provider billing is based on tokens actually generated **up to the moment of abort** — not tokens the client received, and not the request's original max_tokens ceiling."

> "Billing granularity is whole output tokens, not partial ones. You can't get a partial refund for a token that was half-generated when the abort landed."

⇒ 取消能省的是**取消点之后**的 token，已生成的照付 ⇒ 取消**越早送达越省**，这正是动作 1 的延迟要压到有界的原因。

**动作 3 —— 清理必须独立于 body 迭代（本轮最关键的工程发现）**

**【一手】真实缺陷记录**（来源：OpenViking issue #6888，`https://github.com/volcengine/OpenViking/issues/6888`，原文要点）：

> "a client disconnect during a Gateway hidden-tool streaming response can leave the upstream response open and its heartbeat pump running. This concerns `ProxyRequest.tool_response`: **cleanup is inside the response body generator, but Starlette can stop consuming it while that generator is suspended or before it has started.**"

> "Actual: the flag remains false in all three cases. In the ASGI 2.4 body case the heartbeat pump is also still running after 100 ms."
> "Explicitly closing the body iterator cleans up the latter case; **when the generator never started, closing that iterator alone does not close the upstream.**"

⇒ **现象**：客户端断连 ⇒ 上游响应未关闭 + 心跳 pump 仍在跑。
**根因**：清理只挂在 body 生成器上，而框架**可能根本不消费那个生成器**（挂起 / 从未启动）。
**为什么这么修**：清理必须挂在**独立于 body 迭代**的生命周期上 ⇒ **两道闸**：① 生成器 `finally`（正常路径）② 请求级 `finally`（生成器从未启动 / 挂起时的兜底）。
**不修会怎样**：上游连接与后台任务泄漏，且**泄漏得静默** —— 表现为连接数缓慢上涨而非报错。

> 按 `AGENTS.md` 规则 3，这属于「预料之外的 edge case 资产」：必须钉住。

**动作 4 —— 取消原因分类**

`client_disconnect`（用户点了停止）/ `upstream_error` / `timeout` / `shutdown` ⇒ 分类要进 Trace。理由：**用户主动**与**系统故障**混在一个错误率里，就没法回答「网关到底因为什么被叫停」。

**动作 5 —— 前端停止追加（客户端职责，网关只提供证据）**

**【一手】** 客户端要点（来源：`https://hammyasf.github.io/cancel-streaming-llm-response.html`，原文要点）：

> "The stop button only closes your end. ... you abort that fetch, the connection closes, and the UI goes quiet. But your server was in the middle of its own request to the model provider, and closing the browser connection does nothing to that."

> "The cure is a generation id on every stream. Every write carries the id of the stream that produced it, and the server drops any write whose id is no longer the active one."

⇒ 网关侧能做的只有「不再发新分片 + 正常收口 + 在 Trace 留证据」；**客户端已断开时网关发不出任何额外帧** ⇒ 前端停止追加必须由前端状态机自己保证，不能等网关通知。

### 7.3 「怎么确认网关真的做了」—— 三层证据链

这是老宅问题的正面回答。**只信网关自己的 span 是不够的**。

#### L1 网关自证（可自动断言）

| 断言 | 手段 |
|---|---|
| 上游连接已关闭 | fake upstream 记录 `closed` 标志；断言为 true |
| 取消后再无读取 | 取消后上游读取计数不再增长 |
| 取消已写入 Trace | span 已结束 + `gen_ai.response.status=cancelled` + `gateway.cancel.*` |
| 无分片泄漏到客户端 | 取消后客户端收到的帧数 == 取消点前的帧数 |

#### L2 传输层佐证

**【一手】nginx 约定 499**（来源：ASGI 实测文，`https://async-concurrency.com/network-io-protocol-handling/asgi-servers-and-frameworks/detecting-client-disconnects-in-asgi-handlers`，原文要点）：

> "What status code should I return when the client disconnected? It is never delivered, so it only matters for your logs; **499, the nginx convention for client closed request**, is common."

> "Why does my app never see disconnects in production? A reverse proxy or load balancer may keep its connection to your server open after the browser leaves. **Check the proxy's client-abort setting and count http.disconnect messages to confirm.**"

⇒ 代理的 client-abort 计数与网关观测到的 cancel 计数要对账；**若代理吞掉断连，网关根本感知不到** ⇒ 必须先确认断连真的到达。

#### L3 外部可核对（关键，别只信自证）

**【一手】arXiv 2611.08684 的实测结论**（来源：论文摘要页，`https://arxiv.org/abs/2611.08684`；作者 Xindan Zhang, Fei Wang，提交 2026-11-05；原文逐句）：

> "Clients and proxies in front of an LLM engine retry calls that time out. After a transient overload, these retries can keep the engine from recovering even when calls arrive below its capacity."

> "**We find that with retries on, cancellation alone did not restore service in any run, and only 12-38% of the calls that arrived after the overload were delivered.**"

> "The traces suggest why: retries that vLLM ran typically started prefill **less than half a second** before they timed out. **Executions that vLLM later aborted took 79-85% of the prompt tokens it computed**, and **vLLM's prompt-token counter missed a third to half of all computed prompt tokens.**"

> "A retry budget restored service by shedding retries but left many of the overload's calls undelivered. **Request coalescing delivered every call from the overload onward**, some late, unless cancellation had already aborted the running execution."

> "**Overload controls should thus be judged by the executions that retries add and the calls that clients receive.**"

⇒ **对「取消成功」这个指标的证伪**（论文正文的补充，来源：`https://arxiv.org/html/2611.08684v1`，原文要点）：

> "A request can be marked cancelled at the API layer while the engine has already spent most of its compute on it."

⇒ **判定口径必须是两条同时看**：
1. **重试额外制造了多少次上游执行**（ executions that retries add）
2. **客户端最终真正收到了多少调用**（ the calls that clients receive）

**配套控制**（论文原文要点）：
- **请求合并（coalescing）**：唯一「送达了过载后每次调用」的机制；前提是**每次尝试都带同一个标识**（论文指出 "Coalescing requires every attempt of a call to carry one identifier; the OpenAI SDK they tested sent none of its own"）⇒ 直接支撑本仓 `client_request_id` 必须贯穿全部尝试。
- **重试预算**：能砍掉重试恢复服务，但会留下未送达的调用。

⇒ **provider 自报的 token 数不能当唯一依据**（论文实测：vLLM 自己的 prompt-token 计数器漏掉三分之一到一半）。

### 7.4 取消后必须抑制重试（late cancel race）

**【一手】三类失败模式**（来源：流式代理指南，`https://www.technologyonthe.net/2026/10/streaming-backpressure-and-client.html`，原文要点）：

> "**Late cancel races** — you cancel upstream, but a retry or a second proxy hop has already started another completion for the same user turn."

> "Tag every turn with `client_request_id`; **reject or replace aborted ids on retry.**"

⇒ 本仓下一轮：取消注册表里的 `client_request_id` 进入**终态**后，同 id 的后续尝试（重试 / 降级 / 第二跳）**必须被拒绝或替换**。

### 7.5 Trace 口径表（「查得到这次调用，并能取消结束」）

**span 生命周期**：请求发起时创建 → **取消发生的那一刻结束**（不等上游自然结束）⇒ 取消后立即能在 Trace 里查到这条调用已收口，**不是悬挂 span**（依据：5.2 引的 span 生命周期原文）。

| 属性 | 值 | 出处 |
|---|---|---|
| `gen_ai.operation.name` | `chat` | GenAI spans 规范 |
| `gen_ai.provider.name` | 实际落到的 provider（如 `openai` / `deepseek`） | 同上；规范注：可与「客户端配置的 provider」不同 |
| `gen_ai.request.model` / `gen_ai.response.model` | 请求模型 / 实际响应模型 | 同上 |
| `gen_ai.request.stream` | `true`（仅流式设） | 同上 |
| `gen_ai.request.stream_cursor` | 最后一个 SSE 事件游标 | 同上；用于断点续传 |
| `gen_ai.usage.input_tokens` / `output_tokens` | **取消点前**的实际值 | 同上 |
| `gen_ai.response.status` | **`cancelled`** | 同上；合法枚举值 |
| `gen_ai.response.finish_reasons` | `["error"]` | 同上；规范规定 cancelled → error |
| **span status** | **`Unset`（不设 ERROR）** | recording-errors 规范 |
| **`error.type`** | **不设** | 同上 |
| `gateway.cancel.reason` | `client_disconnect` / `upstream_error` / `timeout` / `shutdown` | 本仓自定义（见下） |
| `gateway.cancel.detected_latency_ms` | 从断连到关上游的延迟 | 本仓自定义 |
| `gateway.cancel.upstream_closed` | 是否真的关了上游连接 | 本仓自定义 |
| `gateway.cancel.tokens_after_cancel` | 取消后仍产生的 token 数（应为 0） | 本仓自定义 |

⚠️ **自定义属性为何不进 `gen_ai.` 命名空间**：GenAI semconv 是**封闭的语义命名空间**，往里塞私造字段等于污染标准。**【一手】** 规范编写指南的通用原则（来源：`https://andygol-otel.netlify.app/docs/specs/semconv/how-to-write-conventions/`，原文要点）："If the attribute doesn't follow an existing naming pattern, and there's no existing attribute that fits, create a new namespace." ⇒ 本仓用 `gateway.*` 前缀。

**降级链上每个端点各自独立 span**，属性对应各自 provider ⇒ 「这次到底打了谁」在 Trace 里一目了然。

## 八、结论与对本仓的映射

| 功能域 | 业界共识（一句话） | 本仓下一轮该长什么样 |
|---|---|---|
| **协议 / 注册 / 执行** | 对外统一 OpenAI 兼容 API；内部按 provider 适配；注册表存**别名 + 真实上游 + 凭据来源引用 + 能力标记**；协议转换不进核心 | `protocol/openai.py`（Pydantic 边界）+ `upstream.py`（provider 适配）+ `Endpoint` 补字段 |
| **路由 / 上下文** | 静态策略够用；带状态策略（usage/cost）需跨实例状态；**失败类型决定降级路径**；上下文超限走专用降级 | `Router.fallback_chain(primary, failure_kind)`；上下文越界判定 |
| **错误 / 治理** | 4xx/5xx 分开；归一对外、原始对内；**token 级限流 + 预算阻断**；重试与降级分别上限；guardrails = 正则 + Webhook | `errors.py` + `policy/{ratelimit,budget,guardrail}.py` |
| **可观测** | OTel GenAI semconv（已搬家、未 stable ⇒ 字段集中管理）；**取消 = `cancelled` + span status 留 Unset**；内容默认不采集；取消要保 trace 全留需 tail sampling | `telemetry.py` 单一映射层 + `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT` 默认 `NO_CONTENT` |
| **安全** | 网关是凭据集中点；每调用方一密钥；**不透传调用方凭据**；出口层统一遮蔽；出网 URL 单点校验；管理面不暴露 | `Endpoint` 存凭据来源引用 + 出口层遮蔽 + 出网校验 |

## 九、未验证与推测清单

**⚠️ 以下条目不是搜索所得的结论，读者勿当公论引用。**

1. **【推测】把 MCP 的 `notifications/cancelled` 语义映射到 HTTP/SSE 侧的「用户点停止」是我的映射**。MCP 规范本身**没有**定义 HTTP 侧的取消事件；HTTP/SSE 侧只有「客户端 abort ⇒ TCP 断开」的事实标准（见 7.1）。⇒ 下一轮若实现 HTTP 侧取消，本仓**自定**语义并显式声明「借鉴 MCP、非 MCP 规范」。
2. **【未验证】agentgateway 与 Envoy AI Gateway 的取消传播具体实现**。本轮只取其公开的协议与能力清单（README / release notes），**未逐行核 Rust 源码与 Envoy 扩展**。若下一轮要抄其语义，需 clone 仓库读源码（`AGENTS.md` 规则 30 要求先搜后抄）。
3. **【未验证】主流 provider（OpenAI / Anthropic 官方 API）对「客户端断开」是否立刻停止计费的逐家差异**。本轮只取到业界通行的机制性描述「上游连接关闭即停解码」（见 7.2 引文），**无官方逐家确认**。⇒ 下一轮若接真实 provider，需按家实测并写进本仓 `docs/`。
4. **【单一来源】arXiv 2611.08684 的数字（12–38%、79–85%、三分之一到一半）目前只有该论文一个来源**。检索中出现的多个二手转述（`cctest.ai`、`devfeed.tech`、`vibeleaderboard.ai`、`arxiv-troller.com`）**均指向同一篇**，**不构成独立验证**。⇒ 引用时只引 arXiv 摘要页 / HTML 全文。
5. **【未验证】Uvicorn 0.54 + Starlette 1.7 的断连实测数据**来自单一第三方实测文（`async-concurrency.com`），**非本仓实测**。本仓下一轮必须用自己的 socket 级测试复现（见 `specs/001` 的 SC-6 / SC-7），否则不得当作本仓结论。
6. **【推测】三家网关「都选了 OpenAI 兼容 API」的收敛判断**，基于本轮读到的三个项目自述 + 一份第三方比较（`seminal.ai`）。**未穷举**其余网关项目（如 Kong AI Gateway、Bifrost、Cloudflare AI Gateway），故表述为「本轮观察到的三家一致」而非「业界全部一致」。
