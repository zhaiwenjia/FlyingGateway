# 多供应商并发 · 流量上限归属与并发计量调研

## 检索轮次

**第 1 轮（2026-11-14 22:0x）**：起因——老宅提问「多供应商异步转发，每家供应商都有自己的流量上限，
网关的不同请求混在一起，怎么计算并发？」。检索词：
`OpenAI Anthropic Gemini provider rate limits RPM TPM concurrent requests comparison`、
`API gateway per-upstream concurrency limiting in-flight requests Envoy max_connections circuit breaker`。

## 一、来自搜索（结论 + 出处 + 原话要点）

### A. 供应商侧的流量上限维度与归属粒度

1. **各家限流维度不统一，「并发」是独立的一维**：RPM、TPM（OpenAI 输入+输出合并计；Anthropic 拆
   ITPM/OTPM 且缓存读不计 ITPM）、RPD/TPD、RPS（xAI 按 requests/second 计）、IPM、
   以及 **concurrent（同时在途请求数）**。**DeepSeek 干脆只限并发**：「DeepSeek: no tiers, just
   concurrency: 2,500 on deepseek-flash and 500 on deepseek-v4-pro」。
   出处：[Freaky Jolly — LLM API Rate Limits and Usage Tiers Compared (Nov 2026)](https://freakyjolly.com/llm-api-rate-limits-tiers)。
   另见 [DevTk.AI — AI API Rate Limits 2026](https://devtk.ai/en/blog/ai-api-rate-limits-comparison-2026)
   （「DeepSeek offers a unique value proposition: extremely low pricing, automatic context caching,
   and **no public paid tier ladder**」）。

2. **并发位由长流式调用长期占用**：「DeepSeek 429 with few users: **long streaming calls hold
   concurrency slots**. Close streams you no longer need.」——并发的占用时长 = 整个流的生命周期，
   不是首字节。
   出处：[Freaky Jolly](https://freakyjolly.com/llm-api-rate-limits-tiers)。

3. **配额归属粒度（scope）各家不同**：Anthropic 「Limits are **per workspace per model**.
   claude-sonnet-4-6 and claude-haiku-4-5 have **separate counters** — a fanout to both doubles your
   effective RPM」，且「multiple model versions within the same pool draws from **one shared bucket**」；
   OpenAI 按 organization + project；Gemini「limits apply **per Google Cloud project**, so every key
   in a project **shares the same quota**」；Azure 按 deployment/subscription。
   出处：[GitHub — Provider Tier Matrix（langchain-rate-limits）](https://github.com/jeremylongshore/tons-of-skills-marketplace/blob/main/skills/.curated/langchain-rate-limits/references/provider-tier-matrix.md)、
   [Freaky Jolly](https://freakyjolly.com/llm-api-rate-limits-tiers)。
   ⚠️ 即：**同一供应商的多个模型/多个 key 可能共享一个配额池**（Gemini 项目级、Anthropic 同 pool），
   也可能各自独立（Anthropic 不同 model class）——归属粒度必须可配置。

4. **「哪一维先绑死」取决于负载形态**：「For any given workload, exactly one limit binds」——
   短回复 RPM 先绑、长输入 ITPM 先绑、长输出 OTPM 先绑；建议「Configure requests_per_second at
   **70% of binding limit**」（留 headroom）。
   出处：[GitHub — Provider Tier Matrix](https://github.com/jeremylongshore/tons-of-skills-marketplace/blob/main/skills/.curated/langchain-rate-limits/references/provider-tier-matrix.md)。

5. **剩余额度回传**：OpenAI `x-ratelimit-remaining-*`、Anthropic `anthropic-ratelimit-*-remaining`
   头随响应回传，客户端可据此**主动节流**而不等 429。
   出处：[gpt0x — AI API Rate Limit Comparison](https://gpt0x.com/answers/ai-api-rate-limits.html)、
   [Provider Tier Matrix](https://github.com/jeremylongshore/tons-of-skills-marketplace/blob/main/skills/.curated/langchain-rate-limits/references/provider-tier-matrix.md)。

### B. 网关侧的并发控制机制（业界实现）

6. **Envoy 熔断 = 按上游 cluster 的资源型并发上限**（不是错误率熔断）：五个旋钮
   `max_connections` / `max_pending_requests` / **`max_requests`（在途请求数）** /
   `max_retries`（**并发**重试数，非每请求重试次数）/ `max_connection_pools`；超限**立即 503**
   （`x-envoy-overloaded` 头）**不排队**；粒度 per-cluster（跨该集群全部 host 汇总）。
   出处：[OneUptime — Envoy circuit breakers](https://oneuptime.com/blog/post/2026-02-09-envoy-circuit-breakers-fault/view)、
   [Hivebook — Envoy Circuit Breaking and Outlier Detection](https://hivebook.wiki/wiki/envoy-circuit-breaking-and-outlier-detection-limits-and-host-ejection)
   （「max_requests: Total **in-flight requests** to the cluster at once；When a threshold is exceeded,
   the request is rejected immediately with HTTP 503」）。

7. **HTTP/2 下并发上限要看 `max_requests` 而非 `max_connections`**：「HTTP/2 clusters need
   max_requests, not max_connections. Multiplexing means one connection carries many streams;
   max_connections does not bound concurrency.」——**连接数 ≠ 并发请求数**。
   出处：[Hivebook](https://hivebook.wiki/wiki/envoy-circuit-breaking-and-outlier-detection-limits-and-host-ejection)。

8. **并发上限可细到单 endpoint**：Kubermatic 的 Envoy 封装提供 `perEndpoint.maxConnections`；
   且 per-tenant 覆盖全局（Tenant CRD 覆盖 Config CRD）——**层级：全局 → 租户/组 → 单端点**。
   出处：[Kubermatic — Circuit Breakers](https://docs.kubermatic.com/kubelb/v1.4/tutorials/envoy-proxy/circuit-breakers/)。

9. **重试占并发位、且要按预算限流**：「`max_retries` counts **concurrent** retries」；
   retry budget「caps retries across all concurrent requests **as a percentage of active traffic**」
   （如 20%），防重试风暴放大（「multiplying load 2–3x at the worst possible moment」）。
   出处：[request-routing.com — Circuit Breaking & Retry Budgets](https://www.request-routing.com/middleware-chains-request-transformation/circuit-breaking-retry-budgets)、
   [polariscode — Envoy Circuit Breaking Without the Docs](https://polariscode.net/articles/envoy-circuit-breaking-without-the-docs)。

10. **客户端侧并发计量惯例**：用信号量（semaphore/p-limit/bottleneck）+ 分布式限流器（Redis）
    在**调用方**预算并发，「Budget RPM at the client level (semaphore + Redis limiter)」；
    并发按「绑定约束的 70%」设水位。
    出处：[Provider Tier Matrix](https://github.com/jeremylongshore/tons-of-skills-marketplace/blob/main/skills/.curated/langchain-rate-limits/references/provider-tier-matrix.md)、
    [AI API Rate Limit Calculator](https://www.githubactionscost.online/api-rate-limit-calculator)。

## 二、我的推测（与搜索结论分开）

**「不同请求混在一起怎么计算并发」的机制答案**（推论，基于 A/B 两组事实）：

1. **并发的计量单位 = 在途上游尝试（in-flight upstream attempt）**，不是用户请求：
   发起上游调用时 +1，该次调用**收口**（流式 = 最后一帧收完 / 取消 / 失败）时 −1。
   一次用户请求经重试/降级会在不同供应商**串行**地先后占用并发位（同一时刻至多占一个组的位）；
   流式长调用占位到流结束（来源 2）。这与 Envoy `max_requests`（在途请求）语义一致（来源 6）。
2. **归属粒度 = 供应商配额的 scope**：基本单位是**配额共享组**——同组的端点（同供应商多模型/
   多 key/多部署共享一个配额池，如 Gemini 项目级、Anthropic 同 pool，来源 3）共享同一个计数器；
   独立配额的模型/部署各成一组。⇒ 注册表需要可选的 `limits_group` 声明，缺省 = 端点自成一组。
3. **多维并联判定**：并发位（in-flight 上限）与令牌桶（rpm/tpm）是不同机制，同一请求同时过两道，
   任一不足即拒（429 + Retry-After 进重试/降级决策）——与「exactly one limit binds」（来源 4）对应：
   每维都可能成为绑定约束，都要能表达。
4. **全局与局部两级**：全局 max-in-flight 护网关自身容量（已有）；组级 concurrency_limit 护供应商
   并发契约（缺失 ⇒ 本轮补）。层级同 Kubermatic 全局→租户→端点（来源 8）。
5. **连接数 ≠ 并发数**（来源 7）：网关的出站连接池复用下，计量按**在途请求数**而不是 TCP 连接数。

**判断：需要改进。** 现状只有「rpm/tpm 双维桶（按端点）+ 全局 max-in-flight」，缺口两处：
① **并发维缺失**——DeepSeek 这类「只限并发」的供应商在当前 schema 里根本无法表达；
② **共享组缺失**——Gemini 项目级/Anthropic 同 pool 的「多端点共享一个配额池」无法表达，
   多端点各配一份限额会超发（多 key 共享配额时各自计数 = N 倍超发）。
本轮落地方案：`Endpoint.concurrency_limit`（可选，0=不限）+ `Endpoint.limits_group`（可选，
共享组名；rate_limit 与 concurrency_limit 都按组共享计数），超限 429 + Retry-After；
同组声明不一致 ⇒ 启动报错。**不做**：retry budget（并发重试预算，来源 9）与剩余额度头回传
（来源 5）——记为后续项。

## 三、与原有印象冲突

- **原以为**：供应商限流 = RPM/TPM 两维，网关把桶按端点配好即可；**实测/查得**：并发是一等公民
  （DeepSeek 只限并发），且配额池可能跨端点/跨 key 共享（Gemini 项目级）⇒ **因此改口**：
  「怎么计算并发」不是桶的补充细节，而是限流模型缺不得的一维 + 归属粒度问题。
- **原以为**：并发按 TCP 连接计即可；**查得**：HTTP/2 多路复用下连接数不约束并发（来源 7），
  必须按在途请求计。
