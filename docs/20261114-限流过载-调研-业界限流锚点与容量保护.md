# 限流与过载保护 · 业界限流锚点与容量保护调研

## 检索轮次

**第 1 轮（2026-11-14 21:4x）**：起因——吞吐/延迟阶梯（1→16384 并发）在 c≥256 档出现大量 429

把系统压出隐藏天花板；老宅裁定「正式上线肯定要开令牌桶，这个矛盾需要解决，而不是关闭」，
并要求联网集思广益。检索词：`LLM gateway token-based rate limiting TPM RPM quota best practice`、

## 一、来自搜索（结论 + 出处 + 原话要点）

1. **限流与过载保护是两种机制，锚点不同**：rate limiting = 按**上游真实配额**约束单个调用方；
   load shedding = 保护**网关自身容量**、在过载前主动拒绝。二者独立生效，合规调用方在网关容量
   危机中也可能被拒，这是正确行为而非 bug。
   出处：[Superteams.ai — Rate Limiting & Load Shedding](https://www.superteams.ai/courses/ai-gateway-architecture-multi-llm-routing/15-rate-limiting-and-load-shedding)
   原话：「rate limiting enforces a ceiling per caller against a provider's real quota; load shedding protects the gateway's own capacity by deliberately rejecting some traffic before it can overwhelm everything」。

2. **配额数字必须来自套餐契约（tier contract），不许拍脑袋**；突发容量（桶深）来自真实客户端
   扇出形态。无人知晓的数字等于人人无意违反的数字。
   出处：[devopsinterviewprep — Design rate limiting for a public API](https://devopsinterviewprep.com/q/rate-limiter-public-api)
   原话：「Sustained rate from the tier contract, burst from realistic client fan-out, validated against observed p99.9 demand, then published. Numbers nobody can discover are numbers everyone violates accidentally」。

3. **RPM + TPM 双维度同时执行**（whichever comes first）：token 维度防 Denial-of-Wallet
   （大 prompt 放大成本），请求维度防连接洪水；只按请求数会放跑 token 滥用，只按 token
   会漏掉高频小请求。
   出处：[Fast.io — LiteLLM Rate Limits](https://fast.io/resources/litellm-rate-limit)
   原话：「RPM……protects against connection flooding, worker pool exhaustion, and upstream request frequency quotas；TPM……the primary operational bottleneck」。
   另见 [samaustinai — LLM Token Limits](https://samaustinai.com/llm-gateway-token-limits-optimization)（LiteLLM 的
   `tpm_limit`/`rpm_limit`/`max_parallel_requests`/`max_budget` 维度清单）。

4. **令牌桶是公 API 的默认算法**（桶深=突发、补充速率=稳态上限），429 契约 = `429` +
   `Retry-After` + `X-RateLimit-Limit/Remaining/Reset` 头；客户端按头退避（指数退避 + jitter）。
   出处：[bitecode — 6 Production Decisions for API Rate Limits](https://www.bitecode.tech/en/blog/api-rate-limiting)
   原话：「Token bucket is the right default for most public APIs……a 429 Too Many Requests response, a Retry-After header, and X-RateLimit-* headers so the caller knows exactly where it stands」。
   同口径：[Apache APISIX — API Gateway Rate Limiting](https://apisix.apache.org/learning-center/api-gateway-rate-limiting/)、
   [Vibgrate — Token Bucket Pattern](https://vibgrate.com/patterns/token-bucket-pattern)（桶深 B=突发上限、
   补充 R=稳态上限的经典语义）。

5. **限流阈值按实测标定，不靠猜**；分布式限流是 best-effort（AWS/Azure 均如此表述）；
   集群部署需共享计数（Redis）或「本地桶 + 周期对账」的近似模式。
   出处：[blogsite — Rate Limiting and Throttling](https://blogsite-seven-weld.vercel.app/blog/rate-limiting-throttling-api-design)
   原话：「always set your limits based on actual load testing — not guesswork」；
   [HowPremium — API Rate Limiting Explained](https://howpremium.com/api-rate-limiting-explained-how-algorithms-and-production-controls-work)
   （AWS best-effort targets / Azure 分布式限流不可能完全精确）。

6. **复合限流（composite limits）**：每请求同时扣「每调用方桶」与「全局/端点桶」，任一空即拒
   ——配额层级（调用方 ⊂ 端点 ⊂ 全局）用多个桶并联建模。
   出处：[ACE Journal — API Gateway Rate Limiting with Token Bucket Algorithms](https://www.acejournal.org/2025/08/21/api-gateway-rate-limiting-token-bucket-algorithms)
   原话：「a single request decrements from both a per-client bucket and a global endpoint bucket, rejecting if either is empty」。

7. **弹性限流（可选后续）**：LiteLLM dynamic_rate_limiter_v3——集群未饱和时允许调用方借用
   闲置容量超过基线份额，饱和时按预留份额限流。
   出处：[Fast.io — LiteLLM Rate Limits](https://fast.io/resources/litellm-rate-limit)（「When total cluster usage is below a defined saturation threshold, any key can consume idle capacity beyond its baseline allocation」）。

8. **失败语义**：配额服务不可用时，应用层配额 fail open（可用性优先，损失几分钟公平性好过
   全量拒绝），安全限制 fail closed。
   出处：[devopsinterviewprep](https://devopsinterviewprep.com/q/rate-limiter-public-api)。

## 二、我的推测（与搜索结论分开）

- **对本仓的推论**：本仓默认桶（60000/10000 tokens/s 全局值）属来源 2 所指「nobody can discover
  的数字」⇒ 它既不锚定套餐也不锚定容量，凭空造出 ≈454 rps 的隐藏天花板；矛盾的解法是
  **锚点分离**而非「关桶」：限流（rate limiting）锚定套餐契约（注册表 `rate_limit`：tpm/rpm/burst），
  容量保护（load shedding）独立为 `max-in-flight` 并发上限（锚定实测容量）。
- 压测口径推论：吞吐阶梯应在「生产形」配置下跑（桶开 + 契约配额 + 过载上限），图上的「上限」
  语义 = 过载上限；旧默认值数据（P3/P4）作反面教材入档。
- 归一化 token（SDD 7.2）作计数口径不变；RPM 双维度（来源 3）可作补充，本轮是否引入待定。

## 三、与原有印象冲突

- **原以为**：默认令牌桶是「防滥用护栏」，默认开就该有默认值；**实测/查得**：无契约锚点的默认值
  就是隐藏吞吐天花板（454 rps 实测吻合），业界做法是配额数字只来自套餐契约、未登记则不造数字
  ⇒ **因此改口**：默认值不是护栏，是负债；「上线开桶」= 按契约登记配额后开，不是靠拍脑袋默认值。
