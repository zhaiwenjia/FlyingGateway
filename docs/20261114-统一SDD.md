## 第一编 网关目标、范围与硬约束

### 1.1 一句话目标

给定 **base URL + model name**，自动识别供应商 ⇒ 自动套用该供应商的请求 schema ⇒ 收到回复后归一化成**统一格式**供本地智能体消费 ⇒ **精确记录输入 / 输入缓存命中 / 输出**三类 token。

面向的问题：一个智能体的请求要打到不同模型上（快的打热路径、强的打难任务、贵的省着用），11 家供应商的协议形状、用量字段、计价口径各不相同；网关是中间那层 —— 注册端点、识别供应商、转换协议、归一化用量、治理失败、计量费用。

### 1.2 三条硬约束

| 编号 | 硬约束 | 落地含义 |
|---|---|---|
| 1 | **同时支持 OpenAI Chat Completions 与 OpenAI Responses 两种入站模式** | 对外两套 API 形状都要有：`POST /v1/chat/completions` + `POST /v1/responses` |
| 2 | **Claude 用 Anthropic 自己的格式** | 出站各家原生形状：Claude 走 `/v1/messages`，⛔ 不用 OpenAI 形状硬转 |
| 3 | **统一输出以 OpenAI Chat Completions 为基准，但必须是超集** | 内部规范模型以 OpenAI 骨架为基线，承载 reasoning / signature / cache_control / finish_reason 超集 |

### 1.3 两项口径

| 口径 | 规则 | 落地含义 |
|---|---|---|
| **会话态口径** | **默认无状态：客户端带全量历史**；`previous_response_id` 仅在上游支持时透传，不支持则**显式报错**（⛔ 不静默丢弃）；`prompt_cache_key` 始终透传以保住缓存命中 | 客户端负责维护全量历史；网关不做会话存储 |
| **取消时机口径** | **默认立即取消**（`cancel_grace_period = 0`）；「延迟取消」做成可配置项；重挂机制不做 | `cancel_grace_period > 0` 时窗口内保持上游连接、显式取消可提前结束 |

共同原则：**不静默降级** —— 能力缺失时显式报错或显式标记。

### 1.4 贯穿原则

#### 1.4.1 语义字段 vs 优化字段（区分「丢了会变答案」与「丢了只变成本」）

| 类别 | 例子 | 丢了会怎样 | 正确行为 |
|---|---|---|---|
| **语义字段** | `previous_response_id`、`thinking.signature`、`encrypted_content`、`instructions` | **答案变了**（模型没看到历史 / 多轮推理断链），但 HTTP 200、无报错 | **显式报错**或响应体 `x_gateway.degradations[]` 标记 |
| **优化字段** | `prompt_cache_key`、`safety_identifier`、`seed`、`service_tier` | 只影响成本 / 延迟 / 限流，不影响答案正确性 | 可静默忽略（但最好记录） |

#### 1.4.2 不静默降级三则

1. 降级目标不可用（探活失败 / 凭据失效 / 参数不兼容）时**显式报错**，⛔ 不许悄悄换一个看起来能用的端点；
2. 转换不可逆（签名、加密推理链丢失）**必定**产生 `x_gateway.degradations[]` 标记，⛔ 不静默丢；
3. **降级 ≠ 重试**：重试打同一端点、降级换端点，两者次数**分别有上限**，⛔ 不合成一个兜底循环。

#### 1.4.3 可复现

同一输入 + 同一份注册表 + 同一份配置 ⇒ **同一个路由决策**。⛔ 不在路由里掺随机数、墙上时钟抖动或依赖遍历顺序的隐式状态；顺序敏感时显式排序。识别结果同样可复现（同输入 ⇒ 同 Provider / Shape）。

### 1.5 Non-goals（不做）

- 不做 MCP / A2A 协议网关（另立 spec）；
- 不做语义缓存 / prompt cache 命中优化（只**计量**缓存 token，不主动优化）；
- 不做计费报表 / 预算阻断的完整实现（先保证 usage **计量准确**，治理另议）；
- 不做多租户虚拟密钥体系（先保证凭据只从**来源引用**读取，不落明文）；
- 不做前端。

## 第二编 总体架构

### 2.1 数据流与分层（入站双模式 → 内部规范模型 → 供应商识别 → 出站适配 → 归一化输出）

数据主线：本地智能体以 **OpenAI Chat Completions / OpenAI Responses 两种入站形状**发起请求（入站双模式）⇒ 识别层依据 base URL + model name 判定供应商与上游 API 形状 ⇒ 请求被转换为**内部规范模型**（能承载两种入站形状的超集）⇒ 出站经**供应商适配器**套用该供应商的原生请求 schema ⇒ 响应经适配器解析、usage 归一化后输出**统一格式**。

分层架构（自上而下）：

```
┌──────────────────────────────────────────────────────────────────────┐
│  本地智能体（OpenAI SDK / 任意客户端）                                │
│    ├── client.chat.completions.create(...)   → POST /v1/chat/completions │
│    └── client.responses.create(...)          → POST /v1/responses       │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  ← 入站双模式（Chat + Responses）
┌───────────────────────────────▼──────────────────────────────────────┐
│  ① 入口层  server/                                                 │
│      路由：/v1/chat/completions · /v1/responses · /v1/models · /health │
│      鉴权：调用方 key → 网关自己的凭据（不透传）                      │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────────┐
│  ② 识别层  detect/                                                 │
│      base URL → host → 供应商（优先）                                  │
│      model name → 前缀（兜底）                                         │
│      path → API 形状（Chat / Responses / Messages / 原生）                │
│      ⇒ 产出 Provider 决策                                             │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────────┐
│  ③ 内部规范模型  core/（★ 关键：能承载 Chat 与 Responses 两种形状）      │
│      Request{Messages[], Instructions, Tools[], Reasoning, ...}        │
│      Response{OutputItems[], Status, Usage, ...}                       │
│      Usage{InputTokens, InputTokensUncached, CacheRead, CacheWrite,    │
│             OutputTokens, ReasoningTokens, ...}                        │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
        ┌───────────────────────┼───────────────────────────┐
        │                       │                           │
┌───────▼────────┐  ┌───────────▼─────────┐  ┌──────────────▼──────────┐
│ ④ 入站 codec   │  │  ⑤ 供应商适配器       │  │  ⑥ 出站 codec           │
│  codec/chat    │  │  adapter/<provider>/  │  │  codec/responses        │
│  codec/resp    │  │    每家一个            │  │  codec/messages(Claude) │
│  Chat ⇄ 规范   │  │    请求构造 + 响应解析  │  │  codec/原生(Gemini等)    │
│  Resp ⇄ 规范   │  │    + usage 归一        │  │                         │
└────────────────┘  └─────────────────────┘  └─────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────────┐
│  ⑦ 计量层  usage/                                                  │
│      统一 Usage 结构 + 原始 JSON 保留 + estimated 标志                 │
└──────────────────────────────────────────────────────────────────────┘
```

各层职责要点：

- **入口层 `server/`**：路由（`/v1/chat/completions` / `/v1/responses` / `/v1/models` / `/health`）与鉴权；调用方 key 换成网关自己的凭据，⛔ 不透传调用方凭据。
- **识别层 `detect/`**：base URL → host → 供应商（优先）；model name → 前缀（兜底）；path → API 形状；产出 Provider 决策。
- **内部规范模型 `core/`**：OpenAI 骨架的超集，能同时承载 Chat 与 Responses 两种形状。
- **入站 codec**：`Chat ⇄ 规范`、`Resp ⇄ 规范`；**出站 codec**：`Chat / Responses / Messages(Claude) / 原生(Gemini 等)`；**供应商适配器**：每家一个，请求构造 + 响应解析 + usage 归一。
- **计量层 `usage/`**：统一 Usage 结构 + 原始 JSON 保留 + estimated 标志。

技术分层（core / codec / adapter / detect / …）是**实现载体**；功能主线按五个核心功能域组织，每条设计都落到某个域上。

### 2.2 适配器模式（每供应商一个适配器，⛔ 不用一套 struct 硬扛）

**架构结论**：每个供应商一个适配器（`adapter/<provider>/`），接口统一、内部自便 —— 每家的请求构造、响应解析、usage 归一由该适配器独立承载；一套共享 struct 无法承载各家 usage 字段（缓存层级、输入语义、流式携带）与响应体（输出结构、终止原因、推理位置）的语义差异而不失真。

### 2.3 五域功能主线（① 协议/注册/执行 ② 路由/上下文 ③ 错误/治理 ④ 可观测 ⑤ 安全；每域一张要点清单）

**域① 协议 / 注册 / 执行** 要点清单：

- **能力**：入站双 API 形状（Chat + Responses）；11 家上游的原生协议适配；请求 schema 自动套用；响应归一化；流式（SSE / NDJSON / 事件流三种）；执行与取消。
- **注册**：端点注册表字段 `name` / `base_url` / `model`（别名）/ `upstream_model`（实际上游）/ `context_window` / `max_output_tokens` / `capabilities`（tools/stream/vision）/ `credential_ref` / `timeout_s` / `max_retries` / `priority`。
- **执行**：请求构造 → 上游调用 → 流式/非流式解析 → 取消传播（两道闸 + watcher）。
- **约束**：⛔ 未知字段拒绝（config 层）；⛔ 不透传调用方凭据；取消不是错误；有损转换必须标记。

**域② 路由 / 上下文** 要点清单：

- **路由含义**：本设计的「路由」是「**给定 base URL + model，选哪个供应商与哪个 API 形状**」；「一个模型组内选哪个端点」是另一层调度，两者互补。
- **能力**：供应商识别（host 优先 / model 前缀兜底 / OpenAI 兼容兜底）；API 形状判定（Chat / Responses / Messages / 原生）；置信度。
- **上下文**：`context_window` 越界判定；上下文超限走**专用降级路径**（与通用降级链分开）；`max_output_tokens` 上限；上下文压缩由客户端负责（网关只判定越界）。
- **约束**：⛔ 路由决策**可复现**（同输入 + 同注册表 + 同配置 ⇒ 同决策）；⛔ 上下文超限**不静默截断**（显式报错或走专用降级）。

**路由的两级判定**：

```
Level 1（识别）：base URL + model name → Provider + APIShape
   host 命中 → confidence=high
   model 前缀命中 → confidence=medium
   都不中 → OpenAI 兼容兜底，Fallback=true

Level 2（执行形状）：Provider + 入站模式 → 出站形状
   Provider 支持入站模式的原生形状 → 直接透传（最低转换成本）
   Provider 只支持另一种形状 → 转换（有损则产生 `x_gateway.degradations[]` 标记）
   Provider 只支持原生非标准形状 → 走原生 codec（Gemini / Ollama）
```

**上下文越界判定**：

| 判定 | 做法 |
|---|---|
| 输入越界 | 估算输入 token + `max_output_tokens` > `context_window` ⇒ 走 `context_window` **专用降级路径** |
| 无专用降级路径 | ⛔ **显式报错**（`400 context_exceeded`），**不静默截断** |
| 估算不确定 | 估算值 ≠ 实际 token 数（各家 tokenizer 不同）⇒ 判定用**保守上界**，宁可早报错，不可悄悄截断 |

**上下文压缩是客户端职责** ⇒ 网关只判定越界，不主动改写历史。网关要透传 `context_window` 信息给客户端（如在 `/v1/models` 响应里带 `context_window` / `max_output_tokens`），让客户端能自己做裁剪决策。

**`/v1/models` 端点**：不做动态模型发现；模型列表由注册表生成（注册表是唯一真源），响应带：

```json
{
  "object": "list",
  "data": [
    {
      "id": "gpt-4o-mini",            // 客户端别名（Endpoint.Model）
      "object": "model",
      "owned_by": "openai",             // ProviderName
      "context_window": 128000,
      "max_output_tokens": 16384,
      "capabilities": {"tools": true, "stream": true, "vision": true}
    }
  ]
}
```

⇒ 本地智能体调 `client.models.list()` 即可知道每个模型的能力与上下文上限，**不必硬编码**。

**域③ 错误 / 治理** 要点清单：

- **能力**：错误分类（七类）；错误响应保留原始上游信息；重试与降级**分别有上限**；token 级限流；预算阻断；guardrails（正则 + Webhook）。
- **约束**：⛔ 4xx 与 5xx **分开归类**；⛔ 重试与降级不合成兜底循环；⛔ 归一化对外、原始信息对内。

**错误分类七类**：

| 类别 | 典型来源 | 可重试？ | 可降级？ |
|---|---|---|---|
| `invalid_request` | 请求畸形 / 参数不支持 | ❌ | ❌ |
| `context_exceeded` | 上下文超限 | ❌ | ✅（`context_window` 专用链） |
| `content_policy` | 内容策略拒绝 | ❌ | ✅（`content_policy` 专用链） |
| `auth` | 鉴权失败（401） | ❌ | ❌（换端点也一样） |
| `rate_limit` | 限流（429） | ✅（退避） | ✅（换端点） |
| `upstream_error` | 上游 5xx / 连接失败 | ✅（退避） | ✅ |
| `timeout` | 超时 | ✅ | ✅ |
| `budget_exceeded` | 预算触顶 | ❌ | ❌（触顶即拒） |
| `cancelled` | 取消 | ❌ | ❌（⛔ **取消不触发降级或重试**） |

**归一化分类对外、原始上游信息对内保留**：错误对象必须同时携带两者，原始 provider 细节不许丢：

```go
type ErrorDetail struct {
    // 归一化分类
    Category    ErrorCategory   // 上表七类
    HTTPStatus  int             // 对外状态码
    Message     string          // 对外消息（脱敏后）
    // 原始上游信息（对内保留，⛔ 不丢）
    Provider    Provider
    UpstreamStatus int          // 上游原始 HTTP 状态码
    UpstreamBody   string       // 上游原始响应体（脱敏后）
    UpstreamRequestID string   // 上游请求 ID（若有）
}
```

**治理三件套**：

| 治理项 | 做法 | 超限行为 |
|---|---|---|
| **token 级限流** | 令牌桶以 **token** 为单位（⛔ 不只按请求数 —— Denial-of-Wallet） | `429` + `Retry-After` |
| **预算上限** | 每调用方 token 预算；**触顶即拒**（在发起上游请求之前） | `429 budget_exceeded` |
| **guardrails** | 正则匹配 + Webhook 前置校验（均在上游请求**之前**） | `403 content_policy` |

**限流与预算的 token 口径**：用归一化 token 计，⛔ 不用 provider 自报的 `total_tokens`（可能不准）：

$$
\mathrm{normalized} = \mathrm{InputTokens} + \mathrm{OutputTokens}
$$

缓存命中与缓存写入均计入 InputTokens，不打折；token 限流用归一化 token 计，费用预算按实际计得费用计。

**域④ 可观测** 要点清单：

- 每次上游执行一个 span（OTel GenAI 语义约定口径）。
- span 属性：`gen_ai.operation.name`（`chat`）/ `gen_ai.provider.name` / `gen_ai.request.model` / `gen_ai.response.model` / `gen_ai.request.stream` / `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens` / `gen_ai.response.status`。
- **取消 ⇒ `gen_ai.response.status="cancelled"`，span status 留 `Unset`、不设 `error.type`**（取消不是错误）。
- 额外自定义属性（`gateway.*` 命名空间，⛔ 不塞进 `gen_ai.`）：`gateway.provider` / `gateway.shape` / `gateway.detect_confidence` / `gateway.fallback` / `gateway.degradations[]` / `gateway.cache_read_tokens` / `gateway.cache_write_tokens` / `gateway.usage_estimated`。
  - **`gateway.degradations[]`（OTel 属性）** 与 **`x_gateway.degradations[]`（响应体字段）** 是**两个不同层面的同一信息**：OTel 属性供 Trace 查询与指标聚合；响应体字段供客户端解析。两者**内容一致**，⛔ 不许只记一边。
- **usage 缺失要有指标**：`gateway.usage_missing_rate`。

**域⑤ 安全** 要点清单：

- **能力**：凭据隔离（只存来源引用，不存明文）；出口层统一遮蔽；不透传调用方凭据；出网 URL 校验（防 SSRF / shadow access）；管理面与数据面分离。
- **约束**：⛔ 凭据只从环境变量或密钥服务读；⛔ 不透传调用方凭据；⛔ 遮蔽形态统一 `[REDACTED:<类型>]`。

**凭据隔离三步**：

```
1. 注册表只存 credential_ref（环境变量名 / 密钥别名），⛔ 不存明文
2. 运行时从环境变量 / 密钥服务读取真实凭据，注入上游请求头
3. 出口层（日志 / Trace / 异常序列化）统一遮蔽为 [REDACTED:<类型>]
```

## 第三编 核心设计

### 3.1 内部规范模型（双模式承载；类型定义逐字段给出）

规范模型是 **OpenAI 骨架的超集**：以 OpenAI Chat Completions 骨架为基线，但必须承载 reasoning / signature / cache_control / finish_reason 超集，从而同时容纳 Chat 与 Responses 两种入站形状。Go 类型定义逐字段如下（包 `core`）：

```go
// core 包的规范模型：OpenAI 骨架的超集
type Request struct {
    Model    string
    Messages []Message       // Chat 形状的消息序列
    // Instructions 是 Responses 形状的系统提示；Chat 侧由 messages[0] 承载
    Instructions string
    Tools      []Tool
    ToolChoice *ToolChoice
    MaxOutputTokens int
    Temperature *float64
    TopP       *float64
    Stop       []string
    Reasoning  *ReasoningConfig
    Stream     bool
    // CacheControl 是 Anthropic 的缓存断点（Chat 形状无对应物）
    CacheControl *CacheControl
    // PreviousResponseID / Conversation 是 Responses 的服务端会话态
    PreviousResponseID string
    Conversation        string
    // Extra 承载供应商特有的非标准参数（enable_thinking / prompt_cache_options / ...）
    Extra map[string]any
}

type Message struct {
    Role    string          // system / user / assistant / tool / developer
    Content []ContentPart   // 统一的多模态 part
    // ReasoningContent 承载各家推理文本
    ReasoningContent string
    // ThinkingSignature 承载 Anthropic thinking.signature（不可压平）
    ThinkingSignature string
    // EncryptedContent 承载 OpenAI reasoning item 的 encrypted_content
    EncryptedContent string
    ToolCalls  []ToolCall
    ToolCallID string        // role=tool 时
    Name       string
}

type ContentPart struct {
    Type     string          // text / image_url / input_text / input_image / file / ...
    Text     string
    ImageURL string
    MIMEType string
    Data     string          // base64
}

type ToolCall struct {
    ID       string
    CallID   string          // Responses 的 call_id（与 ID 不同）
    Name     string
    Arguments string         // JSON 字符串
    Type     string          // "function"
}

type Response struct {
    ID     string
    Model  string
    Status string             // completed / failed / incomplete / cancelled / in_progress / queued
    // OutputItems 是异构联合，承载 Chat 的单条 message 与 Responses 的多 item
    OutputItems []OutputItem
    // Text 是便捷字段（对应 Responses 的 output_text）
    Text string
    FinishReason string       // 超集枚举
    Usage *Usage
    Error *ErrorDetail
}

type OutputItem struct {
    Type    string           // message / reasoning / function_call / ...
    ID      string
    Role    string
    Content []ContentPart
    // Reasoning 相关
    Summary  []SummaryPart
    // FunctionCall 相关
    CallID    string
    Name      string
    Arguments string
    // Refusal
    Refusal string
}
```

双模式承载的关键设计点：

- `Request.Instructions` 是 Responses 形状的系统提示；Chat 侧由 `messages[0]` 承载，**入站保留 system 角色**（不提升为 Instructions，转换在出站时做）。
- `Message.ThinkingSignature` 承载 Anthropic `thinking.signature`，**不可压平**（压平即丢语义）；`Message.EncryptedContent` 承载 OpenAI reasoning item 的 `encrypted_content`，**必须保留**。
- `Response.OutputItems` 是异构联合（`message` / `reasoning` / `function_call` / …），承载 Chat 的单条 message 与 Responses 的多 item。
- `Request.Extra` 承载供应商特有的非标准参数（`enable_thinking` / `prompt_cache_options` / …）。
- `Response.FinishReason` 是超集枚举，必须纳入 `model_context_window_exceeded`（智谱超上下文）等非标准取值。

### 3.2 统一 Usage（输入/输入缓存命中/输出三类必准；缓存写入单列不累加；Anthropic 残值语义；流中断 Estimated=true 且不产生负数）

输入 / 输入缓存命中 / 输出三类 token 必须准确（`InputTokens` / `CacheReadTokens` / `OutputTokens`）。类型定义：

```go
type Usage struct {
    // ---- 三项必准字段 ----
    InputTokens        int64   // 总输入 token（对 Anthropic 系 = input + cache_creation + cache_read 合成）
    CacheReadTokens    int64   // 输入缓存命中（从缓存读取）
    OutputTokens       int64   // 输出 token

    // ---- 补充维度（必需，否则成本算不准）----
    CacheWriteTokens   int64   // 写入缓存（Qwen / Kimi / Claude / OpenAI 都有）
    InputTokensUncached int64  // 未缓存的新增输入
    ReasoningTokens    int64   // 推理 token
    TotalTokens        int64   // provider 原报的总值（保留，不重算）
    ToolUsePromptTokens int64  // Gemini 的 tool_use_prompt_token_count

    // ---- 可信度标记 ----
    Estimated bool     // true = usage 缺失/被截断，用估算值
    // ---- 原始数据 ----
    Raw json.RawMessage // provider 原始 usage JSON（账单核对 / 协议排障）
}
```

**字段口径的三条硬规则**：

1. `InputTokens` 是**总输入**。Anthropic 系必须合成：`input_tokens + cache_creation_input_tokens + cache_read_input_tokens`。
2. `CacheReadTokens` 与 `CacheWriteTokens` **分列**。只统计命中量会**低估写入成本**（Claude 5m 写入 ×1.25、1h ×2）。
3. `Estimated` 必须有。流中断时末帧 usage 可能拿不到，**未收到 usage 不代表不计费**。

由此展开的四条口径（每条自包含）：

- **输入必准（Anthropic 残值语义）**：Anthropic 系 `input_tokens` 是**残值**（不含缓存部分），归一化必须合成三项之和。例：`input_tokens=50, cache_read=200000` ⇒ 归一 `InputTokens=200050`（**不是 50**）。
- **缓存写入单列不累加**：`CacheWriteTokens` 与 `CacheReadTokens` 分列统计，⛔ 不合并、⛔ 不互相累加；`InputTokensUncached`（未缓存新增）同样单列。
- **流中断**：末帧 usage 拿不到 ⇒ `Estimated = true`（用估算值），且**不产生负数 token**（`CacheRead` / `Output` 等字段不为负）。
- **原始数据保留**：`Raw` 保留 provider 原始 usage JSON（账单核对 / 协议排障），`TotalTokens` 保留 provider 原报总值、**不重算**。

**逐家 usage 字段语义对齐**（归一化目标：`InputTokens` / `CacheReadTokens` / `CacheWriteTokens` / `OutputTokens`；原始 usage 无对应字段 ⇒ 归一化记 0）：

| 供应商 | 输入侧字段 | CacheReadTokens | CacheWriteTokens | 输出侧字段 | 归一化要点 |
|---|---|---|---|---|---|
| Gemini 原生 | `promptTokenCount` / `toolUsePromptTokenCount` | `cachedContentTokenCount` | 0（显式缓存按存储费计，不按写入 token 计） | `candidatesTokenCount` / `thoughtsTokenCount` | InputTokens = `promptTokenCount` + `toolUsePromptTokenCount`；OutputTokens = `candidatesTokenCount` + `thoughtsTokenCount`（thoughts 独立于 candidates，**不含在 candidates 内**）；`totalTokenCount` = prompt + candidates + toolUsePrompt + thoughts |
| OpenAI | `prompt_tokens` | `prompt_tokens_details.cached_tokens` | 无独立字段 ⇒ 0（写入按 TTL 30m / 12h 两档计价） | `completion_tokens`（`completion_tokens_details.reasoning_tokens` 单列） | InputTokens = `prompt_tokens` |
| Anthropic | `input_tokens` / `cache_creation_input_tokens` / `cache_read_input_tokens` | `cache_read_input_tokens` | `cache_creation_input_tokens` | `output_tokens` | **InputTokens = 未缓存 + 缓存写 + 缓存读（三项之和）**；`input_tokens` 是残值 |
| DeepSeek | `prompt_tokens` / `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens` | `prompt_cache_hit_tokens` | 0 | `completion_tokens` | `prompt_tokens` = 命中 + 未命中；`prompt_tokens_details.cached_tokens` 与 `prompt_cache_hit_tokens` 同值 |
| Kimi / Moonshot | `prompt_tokens` / `cached_tokens` / `prompt_tokens_details.cache_write_tokens` | `cached_tokens` | `prompt_tokens_details.cache_write_tokens` | `completion_tokens` | **输入 = 未命中 + 命中 + 缓存写入（三段相加才等于 `prompt_tokens` 口径）** |
| 智谱 GLM | `prompt_tokens` / `prompt_tokens_details.cached_tokens` | `prompt_tokens_details.cached_tokens` | 0（隐式缓存无写入计费） | `completion_tokens`（`completion_tokens_details.reasoning_tokens` 单列） | 思考计入输出计费 |
| MiniMax | `prompt_tokens` | 0 | 0 | `completion_tokens`（`completion_tokens_details.reasoning_tokens` 单列） | **无缓存命中/写入字段**；另有 `total_characters`，随 `Raw` 保留 |
| xAI / Grok（Chat） | `prompt_tokens` / `cached_prompt_text_tokens`（旧形态） | 两形态取其一：`cached_prompt_text_tokens`（旧）/ `prompt_tokens_details.cached_tokens`（现行，真实样本与 xAI 现行文档口径）⛔ 不累加 | 0 | `completion_tokens`（`reasoning_tokens` 单列） | 另有 `cost_in_usd_ticks`（实际计费额，见下） |
| xAI / Grok（Responses） | `input_tokens` | 0 | 0 | `output_tokens` | 另有 `cost_in_usd_ticks` |
| Ollama `/v1` | `prompt_tokens` | 0 | 0 | `completion_tokens` | **无缓存明细**，缓存读写记 0 |
| Qwen / DashScope（兼容层） | `prompt_tokens` | `prompt_tokens_details.cached_tokens` | `cache_creation_input_tokens` | `completion_tokens` | 缓存命中价与创建价按费率口径另计 |

逐家要点：

1. **Gemini 原生**：`thoughtsTokenCount` 独立加项、不含在 `candidatesTokenCount` 内；`totalTokenCount` = prompt + candidates + toolUsePrompt + thoughts；`promptTokensDetails` / `responseTokensDetails` / `cacheTokensDetails` / `toolUsePromptTokensDetails` 按模态细分（随 `Raw` 保留）。缓存写记 0（显式缓存按存储费计，不按写入 token 计）。Gemini 的 OpenAI 兼容层 usage 为 OpenAI 形（`prompt_tokens` / `completion_tokens` / `total_tokens` + `prompt_tokens_details.cached_tokens`）。
2. **Anthropic**：`input_tokens` 是残值（不含缓存部分）⇒ 归一化必须合成三项之和；缓存写入按 TTL 5m（1.25x）/ 1h（2x）分档计价；命中价按模型档位 0.025x / 0.05x / 0.1x。
3. **Kimi / Moonshot**：输入 = 未命中 + 命中 + 缓存写入；缓存写入按 TTL 5m / 1h 两档单列计费，响应头 `Msh-Usage-Cache-Write-Tokens-5m` / `Msh-Usage-Cache-Write-Tokens-1h` 给分档写入量；请求参数 `prompt_cache_options: {mode, ttl}`（ttl 仅 5m / 1h），显式 `prompt_cache_breakpoint` 被拒（400）；`message.reasoning_content` 承载思考。
4. **DeepSeek**：`prompt_tokens` = `prompt_cache_hit_tokens` + `prompt_cache_miss_tokens`；缓存按前缀单元命中（64 token 存储单元，best-effort）。
5. **智谱 GLM**：隐式缓存自动命中，命中部分按更低价格计（约为标准价 50%）；流式 `stream_options.chunk_include_usage` 控制逐块累计 usage；`finish_reason` 存在非标准取值 `model_context_window_exceeded`，必须纳入超集。
6. **MiniMax**：无缓存命中/写入字段 ⇒ `CacheReadTokens` / `CacheWriteTokens` 记 0；错误对象 `base_resp: {status_code, status_msg}`（200 状态与业务错误码并存，必须检查）；鉴权仅 `Authorization: Bearer`，无 GroupId；`finish_reason` 取值含 `stop` / `length` / `content_filter` 等（流式 chunk 同一枚举口径处理）。
7. **xAI / Grok**：`cost_in_usd_ticks` 是实际计费额（折扣后、含服务端工具费），1 USD = 10^10 ticks：

$$
\mathrm{cost\_usd} = \frac{\mathrm{ticks}}{10^{10}}
$$

   长上下文（≥200K 输入）全价 ×2。流式须 `stream_options.include_usage`，usage 在最终 chunk（空 choices）。

8. **Ollama**：`/v1` 兼容层无缓存明细 ⇒ 缓存读写记 0；本地部署费用为 0；鉴权任意值忽略。
9. **OpenAI**：流式 `stream_options.include_usage`；**流被中断时可能收不到最终 usage 块** ⇒ `Estimated = true`。

**限流/预算计数口径（归一化 token）**：

$$
\mathrm{normalized} = \mathrm{InputTokens} + \mathrm{OutputTokens}
$$

缓存命中与缓存写入均计入 InputTokens，不打折；token 限流用归一化 token 计；费用预算按实际计得费用计。

### 3.3 供应商识别（识别顺序 host 优先、host 规则表、model 名信号）

**识别的输入来自注册表**：`(base_url, upstream_model)` 由端点注册表提供；⛔ 调用方请求不携带 `base_url`、不指定上游模型 —— 调用方只传 `/v1/models` 列表内的模型名（见 9.1 模型映射）。

**识别顺序 host 优先**：base URL 优先级高于 model name（前缀有歧义，model 名只作兜底）。

```
1. 解析 base URL → host + path
2. host 精确匹配规则表 → 命中则 provider 确定，confidence=high
3. host 未命中：
   3a. model name 前缀匹配 → provider 确定，confidence=medium
   3b. 都未命中 → provider=Unknown，shape=OpenAIChat（兜底），Fallback=true
4. path 后缀判定 shape：
   /chat/completions        → OpenAIChat
   /responses               → OpenAIResponses
   /messages                → AnthropicMessages
   /v1/text/chatcompletion_v2 → 原生（MiniMax V2）
   :generateContent / :streamGenerateContent → Gemini 原生
   /api/chat                → Ollama 原生
```

**host 规则表**：

| 规则（host 后缀 / 精确匹配） | Provider | Shape |
|---|---|---|
| `api.openai.com` | OpenAI | Chat 或 Responses（按入站模式） |
| `api.anthropic.com` | Anthropic | **AnthropicMessages** |
| `api.deepseek.com` | DeepSeek | Chat 或 Responses |
| `api.moonshot.cn` | Moonshot | Chat 或 Responses |
| `open.bigmodel.cn` | Zhipu | Chat |
| `*.maas.aliyuncs.com` / `dashscope.aliyuncs.com` | Qwen | Chat 或 Responses（原生 text-generation 单独处理） |
| `api.minimax.io` | MiniMax | Chat / AnthropicMessages / 原生 V2 |
| `api.xiaomimimo.com` / `batch-api-cn.*` / `token-plan-cn.*` | Xiaomi | Chat |
| `api.x.ai` | XAI | Chat（legacy）或 Responses（推荐） |
| `generativelanguage.googleapis.com` / `aiplatform.googleapis.com` | Gemini | 原生 generateContent |
| `localhost:11434` / `127.0.0.1:11434` | Ollama | 原生 `/api/chat` 或 `/v1/chat/completions` |

**两条实现约束**：

- **Qwen 的地域绑定**：API Key 与地域强绑定，跨地域调用返回 401 `invalid_api_key` ⇒ 识别时**不能只看 host 后缀**，还要看 WorkspaceId 与地域的组合；识别失败时应给出**明确报错**而非默默换端点。
- **MiMo 的非标准鉴权头**：`api-key:` 而非 `Authorization: Bearer` ⇒ 鉴权注入按 provider 分派。

**model 名信号**：host 不可识别时按 model name 前缀匹配，`confidence=medium`；前缀有歧义（`deepseek-r1` / `qwen2`），故**只作兜底**，host 冲突时以 host 为准（例：`deepseek-r1` + Ollama host ⇒ 判 **Ollama**；`deepseek-r1` + DeepSeek host ⇒ 判 DeepSeek）。都未命中 ⇒ `provider=Unknown`、`shape=OpenAIChat`、`Fallback=true`。

**不做用户显式覆盖**：⛔ 调用方不能在请求里指定 provider（不提供 `X-Gateway-Provider` 一类覆盖头）——供应商由注册表端点绑定，识别只是对端点 `(base_url, upstream_model)` 的判定。

**识别结果类型定义**：

```go
type Provider int

const (
    ProviderUnknown Provider = iota
    ProviderOpenAI
    ProviderAnthropic
    ProviderDeepSeek
    ProviderMoonshot   // Kimi
    ProviderZhipu      // 智谱 GLM
    ProviderQwen       // DashScope
    ProviderMiniMax
    ProviderXiaomi     // MiMo
    ProviderXAI        // Grok
    ProviderGemini
    ProviderOllama
)

type Resolution struct {
    Provider Provider
    // Shape 是要调用的上游 API 形状
    Shape    APIShape
    BaseURL  string
    Model    string
    // CredentialRef 只存来源引用，不存明文（规则 21）
    CredentialRef string
    // DetectConfidence: host 命中=high，前缀命中=medium，都不中=fallback
    Confidence DetectConfidence
    Fallback  bool   // true = 走 OpenAI 兼容兜底
}
```

### 3.4 入站双模式转换（Chat ⇄ 规范模型、Responses ⇄ 规范模型、两模式之间转换代价的显式承认）

**两个入口的职责**：

| 入口 | 请求解析 | 响应序列化 |
|---|---|---|
| `POST /v1/chat/completions` | `codec/chat` ⇒ 规范 `Request` | 规范 `Response` ⇒ `chat.completion` / `chat.completion.chunk` |
| `POST /v1/responses` | `codec/responses` ⇒ 规范 `Request` | 规范 `Response` ⇒ `response` 对象 / `response.*` 事件 |

**Chat ⇄ 规范模型**：

- **入站 Chat**：`messages[]` ⇒ 规范 `Messages[]`；`messages[0].role=system` ⇒ 规范 `Messages[0]`（**保留 system 角色**，不提升为 Instructions，转换在出站时做）。
- **出站 Chat**（对 OpenAI 形状供应商）：规范 ⇒ `messages[]`（system 消息还原成 `messages[0]`）。

**Responses ⇄ 规范模型**：

- **入站 Responses**：`input[]` ⇒ 规范 `Messages[]`：
  - `input` 是字符串 ⇒ 规范 `Messages[0]{Role:"user"}`；
  - `input` 是 item 数组 ⇒ 逐 item 映射（`type:"message"` → Message；`type:"reasoning"` → Message{ReasoningContent, EncryptedContent}；`type:"function_call"` → Message{ToolCalls}；`type:"function_call_output"` → Message{Role:"tool", ToolCallID}）。
  - **`reasoning` item 的 `encrypted_content` 必须保留** ⇒ 规范模型有 `Message.EncryptedContent` 字段。
- **出站 Responses**（对有 Responses 的供应商）：规范 `Messages[]` ⇒ `input[]` item 数组。

**两模式之间的转换代价（必须显式承认）**：

| 方向 | 状态 |
|---|---|
| Chat → Responses | ✅ 无损（一条 message 拆成一个 item；`tool_calls[]` → `function_call` item，补 `call_id`） |
| Responses → Chat | ⚠️ **有损**：`encrypted_content` / `reasoning.summary[]` / 多 item 顺序 / `sequence_number` / 服务端会话引用会丢 |
| Anthropic → Chat | ⚠️ **有损**：`thinking.signature` 丢失 ⇒ **多轮带思考的对话功能降级** |

⇒ **设计要求（已定）**：当入站模式与上游能力组合会导致不可逆丢失时，**在响应体里带显式标记**——响应体顶层字段 **`x_gateway.degradations[]`**，⛔ **不许静默丢**。

**`x_gateway.degradations[]` 字段设计**（响应体顶层字段）：

```json
{
  "choices": [...],
  "usage": {...},
  "x_gateway": {
    "degradations": [
      {
        "field": "thinking_signature",
        "reason": "upstream_shape_mismatch",
        "detail": "Claude thinking.signature 无 OpenAI 形状对应物，已丢弃；多轮带思考对话将降级"
      },
      {
        "field": "encrypted_content",
        "reason": "response_to_chat_conversion",
        "detail": "Responses reasoning item 的 encrypted_content 无法映射到 Chat 消息"
      }
    ]
  }
}
```

| 字段 | 说明 |
|---|---|
| `field` | 被丢失的语义字段名（`thinking_signature` / `encrypted_content` / `previous_response_id` / `reasoning_summary` 等） |
| `reason` | 丢失原因分类（`upstream_shape_mismatch` / `response_to_chat_conversion` / `capability_unsupported`） |
| `detail` | 人可读说明（给排障看） |

**流式时 `x_gateway.degradations[]` 的位置**：在**终止帧**（`chat.completion.chunk` 的 `finish_reason` 非 null 那帧 / `response.completed` 事件）的 payload 里携带；若流中断拿不到终止帧 ⇒ 在取消路径补的终止帧里带上（同 `usage.Estimated` 逻辑）。

### 3.5 会话态口径（默认无状态客户端带全量历史；previous_response_id 仅在上游支持时透传、不支持显式报错 400 unsupported_capability、不静默丢弃；prompt_cache_key 始终透传）

**口径：默认无状态（客户端带全量历史）；`previous_response_id` 仅在上游支持时透传，不支持则显式报错；`prompt_cache_key` 始终透传。**

主路径 = **客户端带全量历史**（与 Chat Completions 完全一致：每次请求带全部 messages）：零状态、零额外依赖，两种入站模式心智模型统一，缓存命中靠前缀稳定而非服务端会话。⛔ 网关不自建 conversation 状态（不产生第二份历史真值，不引入跨实例共享状态依赖）。

**`previous_response_id` 的条件透传**：客户端**显式**用了 Responses 的服务端会话能力时，网关照原样转发，但**只在目标上游支持时**。支持判定以适配器声明的 `SupportsPreviousResponseID` 为准：

| 上游 | 支持 `previous_response_id` |
|---|---|
| OpenAI / Grok / DeepSeek / Kimi / Qwen / 智谱 / MiniMax | ✅ |
| Ollama | ❌ 不支持 |
| Anthropic | ❌ 无 `/v1/responses`（只有 `/v1/messages`） |
| Gemini | ❌ 适配器未声明支持即按不支持处理 |

**上游不支持时的行为 = 显式报错**（`400`，错误码 `unsupported_capability`），**⛔ 不静默丢弃**。错误信息里写明「该上游不支持服务端会话，请改为客户端带全量历史」。`previous_response_id` 是语义字段（丢失会改变答案）⇒ 必须报错。

**缓存命中不依赖会话态**：缓存命中靠「**前缀内容稳定 + 一个稳定的 cache key**」，不靠服务端保存历史 ⇒ **网关始终透传客户端提供的 `prompt_cache_key`**（若上游支持该字段），即便采用全量历史模式，缓存收益也不丢。前提是**历史只追加、不改写**；本地智能体若做上下文压缩，压缩后的历史与上一轮前缀不同 ⇒ 缓存自然失效，这是客户端策略问题。

**实施要点**：

| 要点 | 做法 |
|---|---|
| 能力探测 | `Resolution` 增加 `SupportsPreviousResponseID bool`，由 adapter 声明（⛔ 不靠运行时探测） |
| 透传 | 请求带 `previous_response_id` 且上游支持 ⇒ 原样转发 |
| 拒绝 | 请求带 `previous_response_id` 且上游**不支持** ⇒ 立即返回 `400 unsupported_capability`，错误信息里写明「该上游不支持服务端会话，请改为客户端带全量历史」 |
| cache key | 请求带 `prompt_cache_key` ⇒ 透传给支持该字段的上游（OpenAI / Kimi / xAI / DeepSeek…）；不支持的上游**静默忽略**（纯优化字段，忽略不影响正确性 ⇒ 属允许的静默） |
| `conversation` | 本期不支持 |

**静默的边界**：`previous_response_id` 是**语义字段**（丢了会改变答案）⇒ 必须报错；`prompt_cache_key` 是**优化字段**（丢了只影响成本/延迟，不影响答案）⇒ 可以忽略。两者不可同等对待。

### 3.6 出站：供应商适配器（出站形状选择优先级、适配器接口签名、适配器清单与 SDK 分组、三个必须独立处理的坑）

**出站形状选择优先级**：

```
① 供应商有自己的 SDK → 优先使用（如 Anthropic SDK、Google GenAI SDK、xAI SDK）
② 没有 SDK → 优先 OpenAI Responses API（语义更完整：reasoning/encrypted_content/服务端会话）
③ 不支持 Responses → 用 OpenAI Chat Completions API（最兼容，但有损转换需打 degradation 标记）
```

**请求方法由网关按此链自动选定**：⛔ 调用方不可指定出站请求方法（SDK / Responses / Chat）；调用方只表达意图（模型、消息、参数），走哪条请求方法是网关内部决定。

**`openai-go` 是协议层工具**：不仅服务 OpenAI，也服务 DeepSeek / Kimi / Qwen / 智谱 / MiniMax / MiMo / Ollama 的 OpenAI 兼容端点 ⇒ `openai_sdk` 适配器**服务 8 家**，不是只有 OpenAI。

**适配器接口签名**：

```go
type Adapter interface {
    // BuildRequest 规范 Request → 该供应商的请求体 + 路径 + 鉴权头
    // （SDK 形态下由 SDK 构造；HTTP 形态下自行拼装）
    BuildRequest(ctx context.Context, r *core.Request, res *Resolution) (*Outbound, error)

    // ParseResponse 供应商响应（非流式）→ 规范 Response
    ParseResponse(res *Resolution, body []byte) (*core.Response, error)

    // StreamStart 流式：返回帧迭代器
    StreamStart(ctx context.Context, r *core.Request, res *Resolution) (FrameIterator, error)

    // ParseUsage 从该供应商的 usage 结构归一化
    ParseUsage(raw json.RawMessage) *core.Usage

    // OutboundShape 返回实际出站形状（供 degradation 标记判定）
    OutboundShape() OutboundShape  // SDK / Responses / ChatCompletions / Native
}
```

**SDK 形态的适配器**（`anthropic_sdk` / `openai_sdk` / `gemini_sdk` / `xai_sdk`）内部调用官方 SDK 的流式方法，`BuildRequest` / `ParseResponse` 的 `body []byte` 签名保持不变（SDK 返回值先序列化再传入），**接口不因 SDK 而变**；上层（stream / usage / telemetry）完全无感知。**SDK 依赖只出现在 adapter 层**；无 SDK 的供应商不引入额外依赖。

**适配器清单（按 SDK 依赖分组）**——出站形状按上述优先级判定（SDK > Responses > Chat）。`openai-go` 服务 8 家（OpenAI + 7 家 OpenAI 兼容），不是只有 OpenAI。

2. **Ollama 原生流是 NDJSON**（`application/x-ndjson`），不是 SSE ⇒ 流式解析器要按 adapter 分派，不能全局假设 SSE。
3. **智谱的 `chunk_include_usage`** ≠ OpenAI 的 `include_usage` ⇒ 请求构造按 adapter 分派。

### 3.7 流式与取消（统一帧抽象、取消语义、Responses 流式容错、cancel_grace_period 默认 0 的立即取消口径、延迟取消可配置与限制）

**上游传输恒为流式解析**：网关 → 上游一律发流式请求并逐帧解析（内部行为，⛔ 调用方不可选）；调用方请求的 `stream` 参数只决定调用方 ↔ 网关的返回形态（流式转发，或收完帧后返回完整响应）。

**统一帧抽象**：内部用**供应商无关的帧类型**，各 adapter 负责「供应商帧 → 内部帧」与「内部帧 → 入站模式帧」：

```go
type Frame struct {
    Kind      FrameKind  // TextDelta / ReasoningDelta / ToolCallArgsDelta / Usage / Lifecycle / Done / Error
    Text      string
    Reasoning string
    ToolCallID string
    Arguments string
    // ThinkingSignature 承载 thinking 块签名（signature_delta）：复用 FrameReasoningDelta
    // 携带（Kind=ReasoningDelta 且 ThinkingSignature 非空、Reasoning 为空即签名帧），
    // 一帧收口一个 thinking 块；Chat 出口承载不了 ⇒ x_gateway.degradations[] 标记。
    ThinkingSignature string
    Usage     *core.Usage
    Status    string
    Seq       int64
}
```

⇒ 一套流解析核心 + 每家一个「帧解码器」+ 两个「帧编码器」（Chat 模式 / Responses 模式）。

**取消语义**：

- 客户端断连 ⇒ **取消上游请求**（关闭连接 / cancel context）。
- 取消**不算错误**：usage 里标记 `Estimated=true`（因为末帧 usage 拿不到）。
- **计费边界**：计费至**取消点**、按已生成的**整 token** 计（半截 token 不退不补）；取消越早送达上游越省；客户端断开后**未收到 usage 不代表不计费** ⇒ usage 缺失时按已知信息估算并置 `Estimated=true`，⛔ 不按 0 计。
- **取消后不再发任何帧**；已发出的帧由客户端自行丢弃。
- **取消后不得触发降级或重试**（late cancel race）。
- Trace / 日志中区分取消原因（`client_disconnect` / `upstream_error` / `timeout` / `shutdown`）。

**Responses 模式额外注意**：取消时**可能收不到 `response.completed`** ⇒ 客户端拿不到最终 usage ⇒ 网关应在**取消路径上自己补一个终止帧**（含 `Estimated=true` 的 usage），让客户端知道「结束了，且 token 数是估算的」。

**流式容错与结束判据**，必须容忍：

- 后端**不发 `[DONE]`**（vLLM / llama.cpp）⇒ 以终态事件（`response.completed`/`failed`/`incomplete`）或连接关闭判定结束。
- 后端**跳过 `response.output_item.added`** 直接发 delta ⇒ 解析器不假设事件顺序。
- 事件**乱序 / 缺号** ⇒ 用 `sequence_number` 检测但不因此中断（记录告警）。
- **未知事件类型** ⇒ 忽略但记录。

**Gemini 原生流式**：`streamGenerateContent?alt=sse`，SSE 每帧 `data: {完整 GenerateContentResponse JSON}`，**无 `event:` 行、无 `[DONE]` 哨兵**；终结帧带 `finishReason` 与 `usageMetadata`（部分帧也可能带 usageMetadata）；**流结束而无 `finishReason` ⇒ 按错误处理，⛔ 不冒充正常完成**。

**取消时机**：`cancel_grace_period` 默认 `0`（**立即取消**）；大于 0 时窗口内保持上游连接、显式取消可提前结束；**重挂机制不做**。延迟窗口内上游连接保持打开、引擎继续解码与计费 ⇒ `cancel_grace_period` 必须是显式配置，开启时其开销在观测中可见（`gateway.cancel.deferred_ms`）。

**实施要点**：

| 要点 | 做法 |
|---|---|
| 配置项 | `cancel_grace_period`（秒，默认 `0`）；作用域：全局 + 按 provider 覆盖 |
| 状态机 | 取消注册表新增 `CANCEL_PENDING`（**非终态**）⇒ `RUNNING → CANCEL_PENDING → CANCELLED`；`CANCEL_PENDING` 期间上游连接**保持打开** |
| 显式取消优先 | 处于 `CANCEL_PENDING` 时再次收到**显式取消**（`POST /v1/cancel`）⇒ **立即**取消，不傻等窗口 |
| 定时器清理 | 延迟窗口的定时器必须在「请求结束 / 取消执行 / 进程关闭」三种路径上都被清理 ⇒ ⛔ 定时器泄漏 = 上游连接泄漏 |
| 可观测 | 新增 `gateway.cancel.deferred_ms`（实际延迟多久才关连接）与 `gateway.cancel.pending_count`（当前处于 `CANCEL_PENDING` 的请求数） |
| Trace | 取消仍是 `gen_ai.response.status="cancelled"` + span status 留 `Unset`（**取消不是错误**）；延迟取消额外记 `gateway.cancel.deferred_ms` |
| usage | 延迟窗口结束后仍可能拿不到末帧 usage ⇒ `Usage.Estimated = true`（同立即取消） |

### 4.2 双模式对照：Chat Completions vs Responses（含转换代价，哪些转换不可逆）

#### 4.2.1 双模式的入站 / 出站要求

- **入站（对外）**：必须同时提供 Chat Completions 与 Responses 两套 API 形状。
- **对内**：需要一套能承载两者的规范模型。
- **出站（对上游）**：按供应商能力选择形状（多数供应商原生只有 Chat 形状 ⇒ 需 Chat ↔ Responses 双向转换）。

#### 4.2.2 两模式形状差异对照表

| 维度 | Chat Completions | Responses |
|---|---|---|
| 端点 | `POST /v1/chat/completions` | `POST /v1/responses` |
| 输入载体 | `messages[]`（role + content） | **`input[]` 异构 item 数组**（或纯字符串） |
| 输入 content 元素类型 | `text` / `image_url` / `file` / `input_audio` | `input_text` / `input_image` / `input_file` / `input_audio` |
| 系统提示位置 | `messages[0].role="system"` | **顶层 `instructions`** |
| 输出载体 | `choices[0].message`（**单条**） | **`output[]` 异构联合**（29 种 item 类型） |
| 文本便捷字段 | `choices[0].message.content` | **`output_text`** |
| 推理内容位置 | `message.reasoning_content`（各家扩展） | `output[]` 里的 **`reasoning` item**（含 `encrypted_content`） |
| 工具调用 | `message.tool_calls[]`（`{id,type,function{name,arguments}}`） | `output[]` 里的 **`function_call` item**（`{id,call_id,name,arguments}`，**多 `call_id` 字段**） |
| 终止状态 | `choices[0].finish_reason` | **`status`**（六值）+ `incomplete_details.reason` |
| 终止原因取值 | `stop`/`length`/`tool_calls`/`content_filter`/`function_call` | `status`：`completed`/`failed`/`in_progress`/`cancelled`/`queued`/`incomplete` |
| 输入 token 字段 | `usage.prompt_tokens` | **`usage.input_tokens`** |
| 输出 token 字段 | `usage.completion_tokens` | **`usage.output_tokens`** |
| 缓存命中字段 | `usage.prompt_tokens_details.cached_tokens` | **`usage.input_tokens_details.cached_tokens`** |
| 缓存写入字段 | `usage.prompt_tokens_details.cache_write_tokens` | **`usage.input_tokens_details.cache_write_tokens`**（另有 TTL 细分） |
| 推理 token 字段 | `usage.completion_tokens_details.reasoning_tokens` | **`usage.output_tokens_details.reasoning_tokens`** |
| 会话状态 | ❌ 无（客户端带全部历史） | ✅ **`previous_response_id`** / **`conversation`**（服务端态） |
| 流式帧格式 | **只有 `data:`**（`chat.completion.chunk`） | **`event:` + `data:` 双字段**，带 `sequence_number` |
| 流式事件数 | 1 种有效事件类型 | **59 种具名事件** |
| 流式 usage | 需 `stream_options.include_usage`，仅末帧非 null | **`response.completed` 事件自带完整 usage**，无需开关 |
| 终止哨兵 | `data: [DONE]` | `data: [DONE]`（但部分后端省略） |
| 中断丢 usage | ⚠️ 会（末帧可能不到） | ⚠️ 会（`response.completed` 可能不到） |

#### 4.2.3 两条关键差异（决定转换器的工作量）

1. **Responses 的 `output[]` 是异构联合，不是单一 message。** Chat 的 `choices[0].message` 是「一个 assistant 消息」，Responses 的 `output[]` 是「一串 item」（可能是 reasoning + message + function_call + …）。⇒ **Chat → Responses 转换 = 拆一条 message 成多个 item；Responses → Chat 转换 = 合并多个 item 取第一个 message（其余丢弃或降级）**。这个方向不对称，**有损的一侧是 Responses → Chat**（`function_call` item 要降级成 `tool_calls[]`；`reasoning` item 要降级成 `reasoning_content` 字符串，且 **`encrypted_content` 无处安放** ⇒ Anthropic 的 `signature` 与 OpenAI 的 `encrypted_content` 都只能丢）。

2. **两者都有「服务端会话态」与「客户端会话态」的混用风险。** Responses 支持 `previous_response_id`（服务端存历史），但**只有 OpenAI 真正实现了**；Ollama 明确不支持。⇒ 网关**不能**把 `previous_response_id` 直接透传给非 OpenAI 供应商 ⇒ 必须要么在网关侧维护会话（自建 `conversation`），要么降级为「客户端全量历史」模式。

#### 4.2.4 转换代价（四条转换路径）

| 转换方向 | 代价 | 丢失项 |
|---|---|---|
| Chat → Responses | **低**：一条 message 拆成 `[{type:"message",...}]`；`tool_calls[]` → `function_call` item（补 `call_id`） | 无 |
| Responses → Chat | **高**：多个 item 只能取第一个 message；`function_call` item → `tool_calls[]`；`reasoning` item → `reasoning_content` 字符串 | **`encrypted_content`**、`reasoning.summary[]`、多 item 顺序、`sequence_number`、服务端会话引用 |
| Chat → Anthropic | **中**：`messages` → `messages`（role/content 兼容），`system` 消息提到顶层，`max_tokens` **必填**（OpenAI 侧可选 ⇒ 需给默认值） | `tool_calls[]` → `tool_use` content block（结构转换）；`reasoning_content` 无原生位（Anthropic 用 `thinking` 参数 + 响应侧 thinking block） |
| Anthropic → Chat | **中**：`content[]` 块 → `message.content` / `tool_calls[]` / `reasoning_content` | **`thinking.signature`**（⇒ 多轮推理失效，规范要求原样回传） |

#### 4.2.5 两处不可逆（必须显式告警，不能静默丢）

1. **Anthropic → Chat 丢 `thinking.signature`** ⇒ 多轮带思考的对话在 Chat 模式下**功能降级**（模型拿不到签名，回传的 thinking block 会被拒：thinking block 必须原样回传且保持原顺序，修改即 `400 invalid_request_error`）。

2. **Responses → Chat 丢 `encrypted_content`** ⇒ 同理，OpenAI 的加密推理链在 Chat 模式下不可续（`reasoning` item 含 `encrypted_content` 字段）。

### 4.3 逐家请求/响应 schema 要点（每家一小节：端点路径、鉴权头、关键字段、流式事件形态、已知偏差）

#### 4.3.1 OpenAI（统一格式的基准）

**端点路径**：`api.openai.com/v1`，`POST /chat/completions`；另有 `POST /responses`。

**鉴权头**：`Authorization: Bearer \$OPENAI_API_KEY`。

**Chat 请求体关键字段**：`model` / `messages` / `stream` / `max_completion_tokens` / `temperature` / `top_p` / `tools` / `tool_choice` / `reasoning_effort` / `response_format`；流式可用 `stream_options.include_usage`。

**Chat 响应体关键字段**：`choices[].message.content` / `choices[].delta.content`；`finish_reason` 取值含 `stop` / `length` / `tool_calls` / `content_filter` / `function_call`。

**Chat token 计量**（OpenAI 形状完整 usage 树）：

```json
{
  "usage": {
    "prompt_tokens": 125,
    "completion_tokens": 48,
    "total_tokens": 173,
    "prompt_tokens_details": {
      "text_tokens": 125, "audio_tokens": 0, "image_tokens": 0,
      "cached_tokens": 98
    },
    "completion_tokens_details": {
      "reasoning_tokens": 0, "audio_tokens": 0,
      "accepted_prediction_tokens": 0, "rejected_prediction_tokens": 0
    }
  }
}
```

⚠️ `cached_tokens` 位于 **`usage.prompt_tokens_details.cached_tokens`**（**二级**），⛔ 不在 `usage` 顶层。`prompt_tokens_details.cache_write_tokens` 也是 OpenAI Chat 侧的字段 ⇒ 「缓存写入」在 OpenAI 两种模式下都有计数字段，写入价按 TTL 分 **30m / 12h** 两档。

**Chat 流式事件形态**：需 `stream_options: {"include_usage": true}` ⇒ 在 `data: [DONE]` **之前**追加一个 chunk（`choices: []`、`usage` 在顶层）；其余 chunk 的 `usage` 为 `null`。⚠️ 流被中断或取消时可能收不到最终 usage 块 ⇒ **流中断会丢 usage**。

**Responses 第二模式（`POST /v1/responses`）关键字段**：

- **请求体**：`model` / **`input`** / **`instructions`**（系统提示，独立于 input）/ `tools` / `tool_choice` / `reasoning` / `include` / `store` / **`previous_response_id`** / **`conversation`** / `truncation` / `max_output_tokens` / `max_tool_calls` / `prompt_cache_key` / `prompt_cache_retention` / `prompt_cache_options{mode, ttl, comparison_response_id}` / `text{format}` / `background`。
- **`input` 的形状**：不是 `messages[]`，而是**异构 item 数组**（也接受纯字符串）：

```json
"input": [
  { "type": "message", "role": "user", "content": [{ "type": "input_text", "text": "..." }] }
]
```

- **`reasoning` 对象**：`context`（`auto`/`current_turn`/`all_turns`）/ `effort` / `generate_summary`（deprecated）/ `mode`（`standard`/`pro`）/ `summary`（`auto`/`concise`/`detailed`）。`effort` 取值：`none` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max`。
- **响应体**：`object="response"` / `id` / `created_at` / **`status`** / `model` / **`output[]`** / `usage` / `incomplete_details{reason}` / `error` / `output_text`（便捷字段）/ `parallel_tool_calls` / `metadata` / `previous_response_id` / `conversation` / `service_tier` / `completed_at` / `background` / `moderation` / `prompt_cache_diagnostics`。
- **`status` 取值**：`completed` / `failed` / `in_progress` / **`cancelled`** / `queued` / **`incomplete`**。
- **`incomplete_details.reason` 取值**：`max_output_tokens` / `max_messages` / `content_filter` / `steered`。
- **`output[]` 是异构联合**（29 种 item 类型）：

```
message · reasoning · function_call · function_call_output · file_search_call
computer_call · computer_tool_call_output · code_interpreter_call · local_shell_call
local_shell_call_output · custom_tool_call · custom_tool_call_output
image_generation_call · mcp_call · mcp_list_tools · mcp_approval_request
mcp_approval_response · web_search_call · tool_search_call · tool_search_output
shell_call · shell_call_output · apply_patch_call · apply_patch_call_output
compaction · program · program_output · additional_tools
```

⚠️ **不要假设 `output[0]` 是 message**——应遍历或用 `output_text`。

- **item 内部结构**：
  - `message`：`{id, type:"message", role:"assistant", status, content:[{type:"output_text", text, annotations} | {type:"refusal", refusal}]}`
  - `reasoning`：`{id, type:"reasoning", summary:[{type:"summary_text", text}], content:[{type:"reasoning_text", text}], encrypted_content, status}`
  - `function_call`：`{id, type:"function_call", call_id, name, arguments, status}`

**Responses token 计量**：

```
usage.input_tokens
usage.output_tokens
usage.total_tokens
usage.input_tokens_details.cached_tokens
usage.input_tokens_details.cache_write_tokens
usage.input_tokens_details.cache_write_tokens_details.ttl_30m_tokens
usage.input_tokens_details.cache_write_tokens_details.ttl_12h_tokens
usage.output_tokens_details.reasoning_tokens
```

⚠️ **Chat 与 Responses 的 usage 字段名不同**（`prompt_tokens`/`completion_tokens` vs `input_tokens`/`output_tokens`），**缓存字段层级也不同**（`prompt_tokens_details` vs `input_tokens_details`）⇒ 归一化器需覆盖两套。

**Responses 流式事件形态**：

- **SSE 帧同时带 `event:` 与 `data:` 两个字段**（Chat Completions **只有 `data:`**）；`data` 内的 `type` 与 `event` 名相同（冗余，可任选其一解析）。
- 每个事件带 **`sequence_number`**（单调递增，可用于检测丢事件）。
- **事件总数 59 种具名类型**。
- 事件分类：
  - **生命周期**：`response.created` / `response.in_progress` / `response.completed` / `response.failed` / `response.incomplete` / `response.queued`
  - **输出项**：`response.output_item.added` / `.done`
  - **内容部分**：`response.content_part.added` / `.done`
  - **文本**：`response.output_text.delta` / `.done`
  - **拒绝**：`response.refusal.delta` / `.done`
  - **函数参数**：`response.function_call_arguments.delta` / `.done`
  - **推理**：`response.reasoning_summary_part.added/.done`、`response.reasoning_summary_text.delta/.done`、`response.reasoning_text.delta/.done`
  - **工具族**：`response.code_interpreter_call.*` / `response.file_search_call.*` / `response.web_search_call.*` / `response.mcp_call.*` / `response.image_gen_call.*` / `response.shell_call.*` / `response.custom_tool_call_input.delta/.done` / `response.compaction.compacting` 等
- **usage 携带**：由 **`response.completed` 事件自带完整 `response.usage`** ⇒ **不需要** `stream_options.include_usage`（与 Chat 模式相反）。
- **终止**：**恰好一个**终态事件（`completed` / `failed` / `incomplete`），随后 `data: [DONE]`。
- **顺序约束**：`response.created` MUST 最先；每个 output item 必须先 `output_item.added` 再有 delta；每个 content part 必须先 `content_part.added` 再有 text delta。

**解析器容忍性要求**（实测偏差，Responses 流式解析器必须容忍）：

- 部分后端（vLLM、llama.cpp）省略 `[DONE]`；mistral.rs 发送它。
- `gpt-5.3-codex` 有时跳过 `response.output_item.added`、直接从 delta 开始。
- Ollama：**不支持** `previous_response_id`。
- LiteLLM：Azure passthrough 会剥掉 setup events。
- SGLang：自定义工具在 `/v1/responses` 上返回空 tool call；`tool_choice="required"` 返 400。

⇒ 网关的 Responses 流式解析器**必须容忍缺事件、乱序、缺 `[DONE]`**。

#### 4.3.2 Claude / Anthropic（原生形状，不可压平）

**端点路径**：`POST api.anthropic.com/v1/messages`。

**鉴权头**：`x-api-key: \$ANTHROPIC_API_KEY` + `anthropic-version: 2026-10-21` + `content-type: application/json`。

**版本相关的硬约束**：API version `2026-10-21` 起，请求带 `temperature` / `top_p` / `top_k` **一律返回 400** ⇒ 网关若用统一参数模板，**必须按供应商剔除这些字段**，不能原样透传。

**请求体关键字段**：`model` / `messages` / **`max_tokens`（必填）** / `system`（**顶层参数**，非 `messages[0]`）/ `tools` / `tool_choice` / `stream` / `thinking: {type: "adaptive", display: "summarized"}` / **`cache_control: {type: "ephemeral", ttl: "5m"|"1h"}`**。

**响应体关键字段**：`content[]` 是**内容块数组**，块的 `type` 有 `text` / `thinking` / `redacted_thinking` / `tool_use` / `server_tool_use` / `web_search_tool_result` 等。`stop_reason` 取值：`end_turn` / `max_tokens` / `stop_sequence` / `tool_use` / `pause_turn` / `refusal` / `model_context_window_exceeded`。

**token 计量**（`usage` 对象）：

```json
{
  "usage": {
    "input_tokens": 25,
    "output_tokens": 15,
    "cache_creation_input_tokens": 0,
    "cache_read_input_tokens": 0,
    "output_tokens_details": { "thinking_tokens": 0 },
    "cache_creation": {
      "ephemeral_5m_input_tokens": 0,
      "ephemeral_1h_input_tokens": 0
    },
    "server_tool_use": { "web_search_requests": 0, "web_fetch_requests": 0 },
    "service_tier": "standard",
    "speed": "standard"
  }
}
```

⚠️⚠️ **关键语义（最易算错的一处）**：

$$
\mathrm{total\_input} = \mathrm{cache\_read\_input\_tokens} + \mathrm{cache\_creation\_input\_tokens} + \mathrm{input\_tokens}
$$

⇒ **`input_tokens` 是「新增部分」不是「总数」**（仅最后一个缓存断点之后的部分）。统一口径必须按此公式合成 `total_input`，⛔ 不能把 `input_tokens` 直接当输入总数（否则带缓存的请求会被严重低估）。

**缓存要点**：最多 **4 个** `cache_control` 断点；前缀顺序固定为 **tools → system → messages**；查找窗口 **20 个 block**；缓存写入按 TTL 分档计价：5 分钟档 = 基础输入价 ×1.25、1 小时档 ×2；缓存命中价按模型档位 0.025x / 0.05x / 0.1x（⛔ 不能按固定 0.1x 估算，见 5.4.3）。

**流式事件形态**：

```
message_start            ← 带 usage（input_tokens / cache_* / output_tokens 初始值）
  ├─ content_block_start
  ├─ content_block_delta  ← delta.type ∈ text_delta / thinking_delta / signature_delta / input_json_delta
  ├─ content_block_stop
  └─ （可穿插 ping 事件）
message_delta            ← 带累计 usage（output_tokens 等）
message_stop
```

⚠️ `message_delta` 事件的 `usage` 是**累计值** ⇒ **流式时 usage 取 `message_delta` 的累计值，不能逐帧相加**。

**已知偏差 / 不可压平项**（Anthropic 原生形状压成 OpenAI 形状的后果）：

| Anthropic 原生项 | 压成 OpenAI 形状的后果 |
|---|---|
| `thinking` block 的 `signature` | 规范要求 thinking block **必须原样回传**且保持原顺序，修改即 `400 invalid_request_error` ⇒ 多轮推理直接失效 |
| `cache_control` 断点（顶层 + block 级） | OpenAI 形状无对应物 ⇒ 缓存断点位置丢失，成本上升 |
| `system` 顶层参数 | 位置语义不同 |
| `max_tokens` 必填 | OpenAI 侧可选 |
| `stop_reason` 七值 | OpenAI `finish_reason` 五值，映射有损 |
| `tool_use` 是 content block | OpenAI 是独立 `tool_calls` 数组，结构不同 |
| `redacted_thinking` 块 | 无对应物 |

#### 4.3.3 Gemini

**端点路径**：`POST generativelanguage.googleapis.com/v1beta/models/{model}:generateContent` 与 `:streamGenerateContent`。⚠️ **模型名必须带 `models/` 前缀**：路径参数正则 `^models/[^/]+\$` ⇒ 网关拼 URL 时要自己补前缀。

**鉴权头**：`x-goog-api-key` 头或 `?key=` query。原生鉴权是 query 参数 `key`，官方示例亦用头 `x-goog-api-key`；**OpenAI 兼容层**用 `Authorization: Bearer` ⇒ 三种形态并存。

**请求体关键字段**：`contents` / `generationConfig` / `systemInstruction` / `tools` / `toolConfig` / `safetySettings` / `cachedContent`。

**响应体关键字段**：`candidates[].content.parts[]`（`text` / `functionCall` / `inlineData` …）/ `candidates[].finishReason` / `promptFeedback` / `usageMetadata`。

**`finishReason` 有 21 个取值**：

```
FINISH_REASON_UNSPECIFIED · STOP · MAX_TOKENS · SAFETY · RECITATION · OTHER
BLOCKLIST · PROHIBITED_CONTENT · SPII · MALFORMED_FUNCTION_CALL · MODEL_ARMOR
IMAGE_SAFETY · IMAGE_PROHIBITED_CONTENT · IMAGE_RECITATION · IMAGE_OTHER
UNEXPECTED_TOOL_CALL · NO_IMAGE · MALFORMED_RESPONSE · CONTINUATION
TOO_MANY_TOOL_CALLS
```

⇒ Gemini 的终止原因是**所有家里最宽的**（含图像类与内容策略类），归一化枚举必须容纳。

**token 计量**（`usageMetadata`，驼峰命名，⛔ 与 OpenAI 形状的蛇形不通用）：

```
promptTokenCount              提示中的 token 总数（含 cached content）
candidatesTokenCount          可见输出（候选回复）的 token 总数
thoughtsTokenCount            思考 token（独立加项，不含在 candidates 内）
toolUsePromptTokenCount       工具执行结果回灌给模型的 token
cachedContentTokenCount       缓存命中读取的 token
totalTokenCount               = prompt + candidates + toolUsePrompt + thoughts
promptTokensDetails[] / responseTokensDetails[] / cacheTokensDetails[]
toolUsePromptTokensDetails[]  按模态细分
serviceTier / trafficType
```

**归一化口径**（逐项）：

$$
\begin{aligned}
\mathrm{InputTokens} &= \mathrm{promptTokenCount} + \mathrm{toolUsePromptTokenCount} \\
\mathrm{OutputTokens} &= \mathrm{candidatesTokenCount} + \mathrm{thoughtsTokenCount}
\end{aligned}
$$

- 输入 = `promptTokenCount` + `toolUsePromptTokenCount`；
- 输出 = `candidatesTokenCount` + `thoughtsTokenCount`（思考 token 是**独立加项**，⛔ 不含在 `candidatesTokenCount` 内，也⛔ 不在输出费用之外重复计）；
- 缓存读 = `cachedContentTokenCount`；
- 缓存写 = 无（Gemini 显式缓存按**存储费**计，⛔ 不按写入 token 计）。

**流式事件形态**：`streamGenerateContent?alt=sse`，SSE 每帧 `data: {完整 GenerateContentResponse JSON}`，**无 `event:` 行、无 `[DONE]` 哨兵**；终结帧带 `finishReason` 与 `usageMetadata`（部分中间帧也可能带 usageMetadata）；**流中断判据 = 流结束而无 `finishReason` ⇒ 按错误处理，不冒充正常完成**。

**OpenAI 兼容层** usage 为 OpenAI 形（`prompt_tokens` / `completion_tokens` / `total_tokens` + `prompt_tokens_details.cached_tokens`）。

**端点路径**：`POST api.deepseek.com/chat/completions`；另有 `/responses`、`/messages`、`/completions`。

**鉴权头**：`Authorization: Bearer \$DEEPSEEK_API_KEY`。

**请求体关键字段**：`model`（`deepseek-chat` / `deepseek-reasoner`）/ `messages` / `stream` / `max_tokens` / `temperature` / `top_p` / `tools` / `response_format`。

**响应体关键字段**：`choices[].delta.content` / `choices[].delta.reasoning_content`（**思考模式专有字段**）/ `finish_reason` 取值：`stop` / `length` / `tool_calls` / `content_filter` / `insufficient_system_resource` / `aborted`。

```json
"usage": {
```

⚠️ **DeepSeek 是唯一提供「命中 / 未命中」两个独立字段的**：`prompt_cache_hit_tokens` 与 `prompt_cache_miss_tokens`（顶层），同时又有标准的 `prompt_tokens_details.cached_tokens`（与 `prompt_cache_hit_tokens` **同值**）。⇒ 解析时**取其一，⛔ 不要累加**；`prompt_tokens` = 命中 + 未命中。缓存按**前缀单元命中**（64 token 存储单元，best-effort）。

#### 4.3.5 Grok / xAI

**端点路径**：`POST api.x.ai/v1/chat/completions`（legacy 端点，新特性先上 Responses）；另有 `/v1/responses`（官方推荐）。

**鉴权头**：`Authorization: Bearer \$XAI_API_KEY`。

**请求体关键字段**：`model`（`grok-4.7` / `grok-4`…）/ `messages` / `stream` / `reasoning_effort`（`low`/`medium`/`high`/`xhigh`）/ `tools` / `tool_choice` / `max_output_tokens`。

**响应体关键字段**：`choices[].message.content` / `choices[].delta.content` / `finish_reason`。

**token 计量**：

- Chat Completions（legacy）usage：`prompt_tokens` / `completion_tokens` / `total_tokens` / `reasoning_tokens` / `cached_prompt_text_tokens`（旧形态；现行真实样本与 xAI 文档为 `prompt_tokens_details.cached_tokens`，两形态取其一 ⛔ 不累加）/ `cost_in_usd_ticks`。
- Responses usage：`input_tokens` / `output_tokens` / `total_tokens` + `cost_in_usd_ticks`。
- **`cost_in_usd_ticks` 是实际计费额**（折扣后、含服务端工具费）：$1\ \mathrm{USD} = 10^{10}$ ticks，换算 $\mathrm{cost\_usd} = \mathrm{ticks} / 10^{10}$ ⇒ **优先用供应商自报值**，费率表只做兜底；自报值是**美元**，转人民币同样走 ÷ $10^{10}$ × 7。

**流式事件形态**：SSE（OpenAI 形状）；须 `stream_options.include_usage`，usage 在最终 chunk（`choices: []`）。

**错误码**：400（含错误 key）/ 401 / 403 / 404 / 422 / 429。

**计价边界**：长上下文（≥200K 输入）全价 ×2；费率行带 `region`（Qwen 按地域定价，取华北2（北京）），按实际路由地域取价。

#### 4.3.6 Ollama

**端点路径**：`POST localhost:11434/api/chat`（原生）与 `POST localhost:11434/api/generate`；另有 OpenAI 兼容层 `/v1/chat/completions`。

**鉴权头**：无（本地进程）；`/v1` 兼容层鉴权任意值忽略。

**请求体关键字段**（原生）：`model`（`model:tag` 格式，tag 缺省 `latest`）/ `messages` / `stream` / `tools` / `think`（bool 或 `"low"`/`"medium"`/`"high"`/`"max"`）/ `format` / `options`（temperature 等）/ `keep_alive`。

**响应体关键字段**（原生，**不是** `choices[]`）：`message.role` / `message.content` / `message.thinking` / `message.tool_calls[]` / `done` / `done_reason`（`stop` / `load` / `unload`）/ `created_at` / `context[]`。

**token 计量**（原生，字段名与 OpenAI 形状**完全不同**）：

```
prompt_eval_count          提示中的 token 数（含命中缓存部分）
prompt_eval_cached_count   从缓存读取的提示 token 数   ← Ollama 独有
prompt_eval_duration       评估未缓存提示 token 的耗时（纳秒）
eval_count                 回复中的 token 数
eval_duration              生成耗时（纳秒）
total_duration / load_duration
```

⚠️ **Ollama 是唯一把「缓存命中」放在与输入 token 平级、且不叫 `cached_tokens` 的** ⇒ 适配器必须单独映射。缓存命中**不减少** `prompt_eval_count`，只减少 `prompt_eval_duration` 的评估量 ⇒ 「未缓存新增」需自己算 `prompt_eval_count − prompt_eval_cached_count`。

**`/v1` 兼容层 token 计量**：usage 仅 `prompt_tokens` / `completion_tokens` / `total_tokens`，**无缓存明细** ⇒ 归一化缓存读写记 0。

**流式事件形态**：⚠️ **Ollama 原生流式不是 SSE，是 NDJSON**（响应 media type `application/x-ndjson`，一行一个 JSON 对象），**无 `[DONE]` 哨兵**；且 `/api/chat` **默认就是流式**（`stream` 默认 `true`）。usage **只在最后一帧**（`done: true` 那帧），且 `response` 字段在流式时被清空。

**已知偏差**：Ollama 的 `/v1` 兼容层自 v0.13.3 起也提供 `/v1/responses`，但**仅无状态 flavor**（不支持 `previous_response_id`）；兼容层**不支持** `tool_choice` / `n` / `user` / `logit_bias`。

#### 4.3.7 Qwen / DashScope

**端点路径**：兼容模式 `POST {base_url}/chat/completions`；原生 `POST {WorkspaceId}.cn-beijing.maas.aliyuncs.com/api/v1/services/aigc/text-generation/generation`。

**base URL 地域**：`{WorkspaceId}.cn-beijing.maas.aliyuncs.com/compatible-mode/v1`（只用国内地域）。

⚠️ **API Key 与地域强绑定**：用北京 Key 调弗吉尼亚 endpoint 返回 401 / `invalid_api_key` ⇒ 网关识别供应商时**不能只看 host 后缀，还要看 WorkspaceId 与地域的组合**。

**鉴权头**：`Authorization: Bearer`。

**请求体关键字段**：OpenAI 形状 + 两个**非标准**参数：`enable_thinking`（bool）、`enable_search`。

**响应体关键字段**：`choices[].delta.reasoning_content`；`finish_reason` 兼容页口径只列 `null` / `stop` / `length` 三种。

**token 计量**：

- 兼容模式：`usage.prompt_tokens` / `usage.completion_tokens` / `usage.total_tokens` / **`usage.prompt_tokens_details.cached_tokens`** / `usage.prompt_tokens_details.cache_creation_input_tokens` / `usage.completion_tokens_details.reasoning_tokens`

⚠️ **原生模式的字段名与兼容模式完全不同**（`input_tokens` vs `prompt_tokens`）⇒ 同一个供应商的两种模式也需要两套解析。原生 text-generation 的 usage 不提供缓存明细字段时，归一化缓存读写记 0。

#### 4.3.8 智谱 GLM / BigModel

**端点路径**：`POST open.bigmodel.cn/api/paas/v4/chat/completions`。

**鉴权头**：`Authorization: Bearer YOUR_API_KEY`（也支持 JWT 方式）。

**请求体关键字段**：`thinking.type`（`enabled`/`disabled`）/ **`thinking.clear_thinking`**（bool，默认 `true`；Preserved Thinking 须置 `false`）/ `reasoning_effort`（`max`/`xhigh`/`high`/`medium`/`low`/`minimal`/`none`）/ **`stream_options.chunk_include_usage`**（**不是** `include_usage`！）/ `tools` / `tool_choice`（**仅 `auto`**）/ `response_format`（仅 `text`/`json_object`，**无 `json_schema`**）。

**响应体关键字段**：`choices[].message.reasoning_content` / `choices[].delta.reasoning_content`；`finish_reason` 取值：`stop` / `length` / `tool_calls` / **`sensitive`**（内容安全拦截）/ **`network_error`** / **`model_context_window_exceeded`**（超上下文，非标准取值，必须纳入 finish_reason 超集）。

**流式事件形态**：SSE `data: {chunk}` + **`data: [DONE]` 结束**；`stream_options.chunk_include_usage` 控制逐块累计 usage —— 默认**仅最后一个数据块**返回 usage；开 `chunk_include_usage=true` 后**逐块返回累计 usage**，累计值**不能相加**。⚠️ 参数名 `chunk_include_usage` 与 OpenAI 的 `include_usage` 不同 ⇒ 照搬会**静默拿不到 usage**。

#### 4.3.9 Kimi / Moonshot

**端点路径**：`POST api.moonshot.cn/v1/chat/completions`。

**鉴权头**：`Authorization: Bearer \$MOONSHOT_API_KEY`。额外可选 `X-Msh-Request-Nonce` 头 —— 携带后服务端回 `Msh-Request-Timestamp` / `Msh-Request-Signature`（前缀 `reqsigv1_`）用于溯源验签。

**思考控制跨代不同**：K3 系列用**顶层 `reasoning_effort`**（`low`/`high`/`max`，默认 `max`），**不用** `thinking`；K2.6/K2.7 用 `thinking.type` + `thinking.keep`。

**token 计量**：

⚠️ **Kimi 是唯一在 `prompt_tokens_details` 里同时给「读取」与「写入」两个字段的**。**输入 = 未命中 + 命中 + 缓存写入**（三者相加才等于 `prompt_tokens` 口径，三者互斥、已包含在 `prompt_tokens` 中，⛔ 不要重复累加）。`usage.cached_tokens`（顶层）与 `usage.prompt_tokens_details.cached_tokens` 语义相同、重复存在，解析时任选其一。

#### 4.3.11 MiniMax

**端点路径**：OpenAI 形状 `POST api.minimax.io/v1/chat/completions`；Anthropic 形状 `POST api.minimax.io/anthropic/v1/messages`；原生 V2 `POST api.minimax.io/v1/text/chatcompletion_v2`。

**鉴权头**：仅 `Authorization: Bearer`，**无 GroupId**（⛔ 不传 `GroupId` / `group_id`，属旧版遗留口径，沿用会引入无效参数）。

**请求体关键字段**：`thinking.type`（`disabled`/`adaptive`）/ `reasoning_effort` / **`reasoning_split`**（bool）/ `service_tier`（`standard`/`priority`）/ `stream_options.include_usage` / `max_completion_tokens` / `tools` / `tool_choice`（**仅 `auto`**）。

**token 计量**：

*OpenAI 形状 / 原生 V2（chatcompletion_v2）*：`usage.prompt_tokens`（总输入）/ `usage.completion_tokens` / `usage.total_tokens` / `usage.total_characters` / `usage.completion_tokens_details.reasoning_tokens`。⚠️ chatcompletion_v2 的 usage **无缓存命中 / 写入字段** ⇒ 归一化缓存读写记 0。

*Anthropic 形状*：`usage.input_tokens`（⚠️ **新增部分**，与 Claude 同语义）/ `usage.output_tokens` / **`usage.cache_creation_input_tokens`** / **`usage.cache_read_input_tokens`**。

⚠️ **MiniMax 的 Anthropic 端点与 Claude 的 `input_tokens` 语义一致**（都是「新增部分」）⇒ 这条口径可跨供应商复用。

**缓存要点**：缓存门槛：输入 token 数 **≥ 512** 才触发；前缀匹配顺序为 system prompt → tool 列表 → user 消息；缓存写入价官方未单列 ⇒ `CacheWriteCNY = 0`（见 5.2）。

**流式事件形态**：OpenAI 形状 `stream_options.include_usage` → 末帧；Anthropic 形状 `message_delta` 携带。

### 4.4 token 用量归一化（三条固化规则、逐家字段对照总表、输入 token 语义对照——归一化最容易错处）

token 用量口径是各家差异最大的地方，差异集中在三处：缓存字段的**层级**、输入 token 的**语义**（总数 vs 新增）、流式 usage 的**携带方式**。⇒ **必须按供应商做 usage 适配器，⛔ 不能写一个通用 struct 硬解。**

#### 4.4.1 三条必须固化的归一化规则

**R1 —— 输入 token 分两类，字段名必须区分。**
一类是「**总输入**」（OpenAI 形状全部、Qwen 兼容、智谱、Kimi、MiMo、MiniMax OpenAI、Ollama、Gemini 的 `promptTokenCount`）；另一类是「**新增部分**」（Claude / MiniMax-Anthropic 的 `input_tokens`）。
⇒ 归一化必须产出**两个字段**而不是一个：`input_tokens`（总输入）与 `input_tokens_uncached`（未缓存新增）。后者对 Anthropic 系 = `input_tokens`，对 OpenAI 系 = `prompt_tokens − cached_tokens − cache_write_tokens`：

$$
\mathrm{input\_tokens\_uncached} = \mathrm{prompt\_tokens} - \mathrm{cached\_tokens} - \mathrm{cache\_write\_tokens}
$$

**R2 —— 缓存读与缓存写是两个字段，不是同一个。**
Qwen（`cache_creation_input_tokens`）、Kimi（`cache_write_tokens`）、Claude / MiniMax-Anthropic（`cache_creation_input_tokens`）都把「写入」单列。⇒ 只统计命中量会**低估写入成本**（写入通常是溢价计费：Claude 5m 档 ×1.25、1h 档 ×2）。响应未提供缓存明细字段时，归一化缓存读 / 缓存写记 0。

**R3 —— 流式 usage 有三种模式，必须枚举化。**

| 模式 | 触发方式 | 语义 |
|---|---|---|
| `IncludeUsage` | 请求带 `stream_options.include_usage=true` | 末帧（`choices: []`）带完整 usage；其余帧 `usage: null`（OpenAI / Qwen / Kimi / MiniMax / Grok） |
| `ChunkIncludeUsage` | 请求带 `stream_options.chunk_include_usage=true` | **逐帧**带**累计** usage（⛔ 不可相加）（智谱） |
| `Implicit` | 无需开关 | 末帧自动带 usage（MiMo / Ollama）；或**每帧自带**（Qwen 原生） |
| `EventCumulative` | 协议事件自带 | `message_start` 初始 + `message_delta` **累计**（Claude / MiniMax-Anthropic） |

#### 4.4.3 输入 token 语义对照（归一化时最容易错的一处）

| 供应商 | 字段 | 语义 | 总输入怎么算 |
|---|---|---|---|
| OpenAI Chat | `prompt_tokens` | **总输入** | 直接用 |
| OpenAI Responses | `input_tokens` | **总输入** | 直接用 |
| Qwen 兼容 / 智谱 / Kimi / MiMo / MiniMax(OpenAI) / Grok | `prompt_tokens` | **总输入** | 直接用 |
| Gemini | `promptTokenCount` | **总输入**（设了 `cachedContent` 时**含**缓存 token） | `promptTokenCount + toolUsePromptTokenCount` |
| Ollama | `prompt_eval_count` | **总输入**（含命中缓存部分） | 直接用 |
| **Claude / MiniMax(Anthropic)** | `input_tokens` | ⚠️ **仅「最后一个缓存断点之后的新增部分」** | **`input_tokens` + `cache_creation_input_tokens` + `cache_read_input_tokens`** |

**Anthropic 系的总输入合成公式**：

$$
\mathrm{total\_input} = \mathrm{cache\_read\_input\_tokens} + \mathrm{cache\_creation\_input\_tokens} + \mathrm{input\_tokens}
$$

⇒ 归一化模型必须输出**两个**输入字段：

- `input_tokens` —— **总输入**（对 Anthropic 系需合成）
- `input_tokens_uncached` —— **未缓存的新增部分**（对 OpenAI 系 = `prompt_tokens − cached_tokens − cache_write_tokens`；对 Anthropic 系 = `input_tokens`）

$$
\mathrm{input\_tokens\_uncached} = \mathrm{prompt\_tokens} - \mathrm{cached\_tokens} - \mathrm{cache\_write\_tokens}
$$

⚠️ **Ollama 的坑**：缓存命中**不减少** `prompt_eval_count`，只减少 `prompt_eval_duration` 的评估量 ⇒ Ollama 的「未缓存新增」需自己算 `prompt_eval_count − prompt_eval_cached_count`：

$$
\mathrm{input\_tokens\_uncached} = \mathrm{prompt\_eval\_count} - \mathrm{prompt\_eval\_cached\_count}
$$

#### 4.6.3 识别歧义与消解

| 冲突场景 | 消解规则 |
|---|---|
| 同一 host 提供多个 API 形状（如 DeepSeek 的 `/chat/completions` 与 `/anthropic/v1/messages`；Qwen 的兼容与原生） | **由路径决定形状**，host 只定供应商 |
| 模型名像别家（Ollama 本地跑 `deepseek-r1`） | **host 优先**；host 识别失败才回退 model 前缀 |
| 用户只给 base URL 不给模型 | 按 host 定向，请求体里模型名由用户给 |
| base URL 是**代理/网关**（如自建 LiteLLM） | host 不可识别 ⇒ 走 **OpenAI 兼容兜底**（标低置信度） |
| 自建 vLLM / SGLang（OpenAI 兼容但非官方 host） | 同上 ⇒ 走 **OpenAI 兼容兜底**（标低置信度） |

#### 4.6.4 兜底（不做用户显式覆盖）

识别优先级：**host > 路径 > model 前缀 > OpenAI 兼容兜底**。host 不可识别（代理 / 网关 / 自建 vLLM / SGLang）时走 **OpenAI 兼容兜底**并标低置信度；⛔ 不提供用户显式覆盖 provider —— 指定供应商的诉求通过注册表端点表达（每条端点在注册表里即绑定供应商）。

模型清单**不做动态发现**：对外 `GET /v1/models` 由注册表生成（返回 `context_window` / `capabilities` 等）；注册表是模型的唯一真源。

### 4.7 归一化设计要点汇总

1. **统一格式以 OpenAI Chat Completions 为骨架**，但必须是**超集**，额外承载：`reasoning_content`、`thinking_signature`、`cache_control` 断点信息、`cache_write` 与 `cache_read` 分列、`finish_reason` 超集。
2. **出站用各家原生形状**：每个供应商一个适配器，负责「统一格式 → 供应商请求体」与「供应商响应 → 统一格式」双向映射。
3. **usage 必须按供应商做适配器**，⛔ 不能一个 struct 硬解（缓存层级、输入语义、流式携带三处差异）。
4. **流式 usage 模式枚举化**（4 种）：`IncludeUsage`（末帧携带，需 `stream_options.include_usage=true`）/ `ChunkIncludeUsage`（逐帧累计，`stream_options.chunk_include_usage=true`，不可相加）/ `Implicit`（无需开关，末帧自动带或每帧自带）/ `EventCumulative`（协议事件自带，初始 + 累计）。
5. **原始 usage 原文保留**：归一化值用于统计，原始 JSON 用于账单核对与协议排障。
6. **推理内容有三个落点**，归一化时都要能接：OpenAI 形状的 `reasoning_content`（Qwen / Kimi / MiMo / MiniMax / 智谱）、MiniMax `reasoning_split=false` 时退回 `content` 的 `<think>` 包裹、Anthropic 形状的 `content[].type=="thinking"` 块 + `thinking_delta`。
7. **鉴权头三种形态**：`Authorization: Bearer`（绝大多数）、`api-key:`（MiMo 独有）、`x-api-key:` + `anthropic-version`（Claude / 智谱 Anthropic 兼容）。
8. **中断与取消的 usage 口径**：流中断可能收不到最终 usage；客户端断开后**未收到 usage 不代表不计费**（计费至**取消点**、按已生成的**整 token** 计，半截 token 不退不补；取消越早送达上游越省）；usage 缺失时按已知信息估算并置 `Estimated=true`，⛔ 不按 0 计；流中断不得产生负数 token。
9. **三类 token 必准**：输入 / 输入缓存命中 / 输出；缓存写入单列、⛔ 不与命中累加。
10. **归一化 token（限流与预算计数口径）**：$\mathrm{normalized} = \mathrm{InputTokens} + \mathrm{OutputTokens}$（缓存命中与缓存写入均计入 InputTokens，不打折）；费用预算按 5.2 计得的费用计；token 限流用归一化 token 计。
11. **归一化 usage 的对外命名对齐 OTel GenAI 语义约定**：`gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens` / `gen_ai.usage.cache_read.input_tokens` / `gen_ai.usage.cache_creation.input_tokens`；span 必备 `gen_ai.provider.name` / `gen_ai.operation.name`，另有 `gen_ai.request.model` / `gen_ai.response.model` / `gen_ai.response.id` / `gen_ai.response.finish_reasons` / `gen_ai.output.type` / `gen_ai.conversation.id`。

## 第五编 费用计量

> 费用字段结构、计算规则、公式与口径；费率数据内联于 5.4 费率总表（快照 2026-11-13），该表是费率的唯一数据源。

### 5.1 统一费用结构（字段定义逐个给出：币种、单价单位、各 token 类别费用字段等）

**币种**：主币种为人民币（CNY）；美元（USD）仅作参考币种，输出 `CostUSD = CostCNY / 7`。

**单价单位**：元 / 1M tokens（每 1,000,000 tokens 的人民币元价格），保留 4 位小数；费用字段单位为人民币元，保留 4 位小数。

**统一结构（Go 形态）**：

```go
type Cost struct {
    // ---- 人民币（主币种）----
    CostCNY  float64   // 本次调用总费用（人民币元），保留 4 位小数
    // ---- 美元（参考）----
    CostUSD  float64   // 本次调用总费用（美元），按固定汇率换算，保留 4 位小数
    // ---- 明细（人民币元，均保留 4 位小数）----
    InputCostCNY       float64  // 未缓存输入费用
    CacheReadCostCNY   float64  // 缓存命中读取费用（显式 / 隐式按对应档单价）
    CacheWriteCostCNY  float64  // 缓存写入费用（按 TTL 分档：5m / 1h、30m / 12h 等）
    OutputCostCNY      float64  // 输出费用（含 reasoning / thinking token）
    // ---- 来源与可信度 ----
    Source        CostSource  // ProviderReported / Estimated / Unknown
    RateSnapshot  string      // 使用的费率快照标识（如 "deepseek-flash@2026-11-13-peak"）
    PeakApplied   bool        // 是否应用了峰谷加价
    Estimated     bool        // true = 估算值（provider 未提供费用）
}
```

**字段语义（逐个）**：

| 字段 | 语义 |
|---|---|
| `CostCNY` | 人民币总费用（主输出字段），保留 4 位小数 |
| `CostUSD` | 美元参考值（`CostCNY / 7`），保留 4 位小数 |
| `InputCostCNY` | 未缓存输入（`InputTokensUncached`）费用 |
| `CacheReadCostCNY` | 缓存命中（`CacheReadTokens`）读取费用（显式 / 隐式按对应档单价） |
| `CacheWriteCostCNY` | 缓存写入（`CacheWriteTokens`）费用；写入按 TTL 分档计价（Anthropic / Kimi 分 5m / 1h，OpenAI 分 30m / 12h） |
| `OutputCostCNY` | 输出（`OutputTokens`）费用，含 reasoning / thinking token |
| `Source` | 费用来源枚举 `CostSource`：`ProviderReported` = 供应商返回了费用（如 xAI 的 `cost_in_usd_ticks`）；`Estimated` = 按 5.4 费率总表计算；`Unknown` = 既无费率也无供应商数据 |
| `RateSnapshot` | 费率快照标识，可追溯用了哪张费率表、哪个时段（峰 / 谷），形如 `deepseek-flash@2026-11-13-peak` |
| `PeakApplied` | 峰谷定价模型（DeepSeek）本次是否应用了峰时加价 |
| `Estimated` | `true` = 估算值（供应商未提供费用）；与 `Usage.Estimated` 联动透传 |

四个明细字段（全精度）之和即总费用；明细与总费用的展示值各自四舍五入到 4 位小数（舍入口径：全精度计算、最后统一舍入一次，见 5.2 与 5.7 的公式与实现）。

### 5.2 费用计算规则（LaTeX 公式给出，含缓存命中/缓存写入/输出/推理 token 的计价方式）

**符号**：

- $n_{\mathrm{in}}$：`InputTokensUncached`，未缓存新增输入 token 数
- $n_{\mathrm{cr}}$：`CacheReadTokens`，缓存命中 token 数
- $n_{\mathrm{cw}}$：`CacheWriteTokens`，缓存写入 token 数
- $n_{\mathrm{out}}$：`OutputTokens`，输出 token 数（含 reasoning / thinking token）
- $p_{\mathrm{in}}$、$p_{\mathrm{cr}}$、$p_{\mathrm{cw}}$、$p_{\mathrm{out}}$：对应单价，单位 元 / 1M tokens，取自 5.4 费率总表
- $m$：峰谷倍率（无峰谷定价或谷时 $m = 1$；DeepSeek 峰时 $m = 2$）

**分项公式**（缓存命中 / 缓存写入 / 输出 / 推理 token 的计价方式）：

$$
\begin{aligned}
C_{\mathrm{in}} &= \frac{n_{\mathrm{in}} \cdot p_{\mathrm{in}} \cdot m}{10^{6}} \\
C_{\mathrm{cr}} &= \frac{n_{\mathrm{cr}} \cdot p_{\mathrm{cr}} \cdot m}{10^{6}} \\
C_{\mathrm{cw}} &= \frac{n_{\mathrm{cw}} \cdot p_{\mathrm{cw}} \cdot m}{10^{6}} \\
C_{\mathrm{out}} &= \frac{n_{\mathrm{out}} \cdot p_{\mathrm{out}} \cdot m}{10^{6}}
\end{aligned}
$$

**总费用与舍入**：

$$
S = C_{\mathrm{in}} + C_{\mathrm{cr}} + C_{\mathrm{cw}} + C_{\mathrm{out}}
$$

$$
\mathrm{round}_4(x) = \frac{\mathrm{round}\left( x \times 10^{4} \right)}{10^{4}}
$$

$$
C_{\mathrm{CNY}} = \mathrm{round}_4(S), \qquad C_{\mathrm{USD}} = \mathrm{round}_4\left( \frac{S}{7} \right)
$$

其中 $7$ 为换算系数（1 USD = 7 CNY，暂定、可配置）。各明细展示值为 $\mathrm{round}_4(C_{\mathrm{in}})$、$\mathrm{round}_4(C_{\mathrm{cr}})$、$\mathrm{round}_4(C_{\mathrm{cw}})$、$\mathrm{round}_4(C_{\mathrm{out}})$；总费用由**全精度**分项求和后舍入一次，⛔ 不对已舍入的分项再相加。

**计价口径（逐条）**：

1. **输入计价用 `InputTokensUncached`（未缓存新增）而非 `InputTokens`（总输入）** —— 缓存命中的部分单独按 `CacheReadTokens` 计，否则重复计费。Anthropic 与 MiniMax（Anthropic 兼容端点）的 `input_tokens` 本身即「最后缓存断点之后」的残值 ⇒ 费用计算必须用 `InputTokensUncached`，⛔ 不用 `InputTokens`。
2. **缓存写入单独计费**，⛔ 不与缓存命中合并。官方单列缓存写入价的按价计（Kimi 按 TTL 5m / 1h、Anthropic 按 TTL 5m / 1h、OpenAI 按 TTL 30m / 12h、Qwen 显式缓存创建价见 5.4.9 表内换算值）；官方未单列写入价的（MiniMax、DeepSeek）取 `CacheWriteCNY = 0`。
3. **缓存命中 token 只按命中价计一次**：命中部分 ⛔ 不重复计缓存写入、⛔ 不计入未缓存输入价（Kimi 口径：缓存命中自动按原 TTL 免费续期、续期不收费；命中部分不再收 Cache Write 费）。
4. **reasoning / thinking token 计入输出**：reasoning token 不单独计费，但计入 $n_{\mathrm{out}}$（DeepSeek / Kimi / 智谱 / Gemini 口径）；Gemini 输出价已含 thinking token，⛔ 不得再单独加一次。
5. **单价来源口径**：国内供应商（DeepSeek / Kimi / 智谱 / Qwen / MiniMax / MiMo）取官方人民币原生价；海外供应商（OpenAI / Anthropic / Gemini / xAI）用美元价 × 7 换算值（1 USD = 7 CNY，暂定、可配置）。
6. **阶梯 / 分档计价**：Qwen 阶梯模型按**单次请求的输入 Token 总量**选档，该请求所有 token 按对应档单价结算 ⇒ 整请求同价、⛔ 不分段、⛔ 不用 `InputTokensUncached` 选档，且输出价随档位变。Anthropic `claude-haiku-5.5` 按 prompt 长度分档（prompt >100K 时全部价 ×5），选档依据是**完整 prompt 长度**（含缓存读写）、逐请求定价（先前的请求不追补）。
7. **按次计费项不走本公式**：搜索 / 抓取 / 代码执行等工具按次计费，与 token 计价分开；按次价格见 5.4 各家费率表注记。
8. **缓存价是每模型独立的绝对单价**：缓存命中（显式 / 隐式）与缓存写入按费率总表 5.4 各行的**绝对单价**计价，⛔ 运行期不做比例推算。官方以比例定价的（Qwen：显式命中 = 输入单价 × 10%、隐式命中 = × 20%、显式创建 = × 125%）在**入库期**换算为绝对价（同 USD×7 的入库换算口径），表内即可直接计价。`CachePriceUnknown = true` 的模型（`qwen3.8-max` / `qwen3.8-max-0902` / `qwen3.8-flash` / `qwen3.8-2.4t-a95b`，官方「见控制台」）缓存**命中**费按 0 计并置 `Estimated = true`，⛔ 不猜价；其创建写入价仍按表内换算值计。
9. **缓存存储费**：Gemini 显式缓存按存储费计（按小时，与缓存读取价分开，见 5.4.4）；智谱缓存存储限时免费（快照口径）⇒ 存储费 0；MiniMax 缓存写入价官方未单列 ⇒ 计 0。
10. **费率时效**：以快照日期为唯一依据（快照 2026-11-13）；带 `PriceValidUntil` 的限价行过期须重取。

### 5.3 峰谷定价（DeepSeek：北京时间时段口径、峰谷倍率、如何在计算里落）

**时段口径**：北京时间周一至周五（不含中国法定节假日）9:00 - 12:00、14:00 - 18:00 为高峰时段；其余时段，包括周末及中国法定节假日全天均为空闲时段。UTC 等价表述：01:00–04:00、06:00–10:00（周一至周五、排除中国法定节假日）——两个口径是同一时段的两种时区表述（北京时间 9–12 / 14–18 = UTC 1–4 / 6–10）。

**峰谷判定**：

| 条件 | 时段 |
|---|---|
| 周一至周五 且 北京时间 09:00–12:00 或 14:00–18:00 且**非**中国法定节假日 | **峰时** |
| 其余（周末 / 中国法定节假日 / 其他时段） | **谷时** |

**峰谷倍率**：空闲时段价格为高峰时段价格的一半 ⇒ **峰时 = 谷时 × 2**，即峰时 $m = 2$、谷时 $m = 1$。

**如何在计算里落**：

- 峰谷倍率 $m$ 乘在全部四类分项上（输入 / 缓存命中 / 缓存写入 / 输出同式）：$C = n \cdot p \cdot m / 10^{6}$。
- 判定时间取 `callTime`（调用发起时间），⛔ 不是响应完成时间（与官方按请求时段计费的口径一致）。
- 仅对声明了峰谷定价的模型生效（费率行 `PeakMultiplier > 1`，DeepSeek = 2.0）；其余模型 $m = 1$、`PeakApplied = false`。
- `RateSnapshot` 记录时段，形如 `deepseek-flash@2026-11-13-peak`。
- **中国法定节假日**：`holiday_calendar` 默认 `cn-fixed`（周末 + 中国法定节假日固定近似，含元旦 / 春节 / 清明 / 劳动节 / 端午 / 中秋 / 国庆），可配置替换为真实日历文件；`RateSnapshot` 记录所用 `holiday_calendar` 取值。

#### 5.4.12 费率表使用规则

- **快照日期是费率时效的唯一依据**（快照 2026-11-13，个别行的行级快照日期见各行注记）；费率随时会变，使用前按快照日期判断是否重取，带 `PriceValidUntil` 的限价行过期必须重取。

#### 5.4.13 费率数据结构（ModelRate / PriceTier）

**ModelRate schema 字段清单与字段语义**：

| 字段 | 类型 | 语义（单位 / 取值） |
|---|---|---|
| `Model` | string | 模型名（如 `deepseek-flash`） |
| `Provider` | string | 供应商 |
| `InputPriceCNY` | float64 | 未缓存输入单价，元 / 1M tokens，4 位小数 |
| `CacheReadExplicitCNY` | float64 | 缓存命中（显式缓存）读取单价，元 / 1M tokens，4 位小数 |
| `CacheReadImplicitCNY` | float64 | 缓存命中（隐式缓存）读取单价，元 / 1M tokens，4 位小数；单一命中价的供应商两字段同值 |
| `CacheWriteCNY` | float64 | 缓存写入单价，元 / 1M tokens，4 位小数（Qwen = 显式创建价的入库换算值）；官方未单列时为 0 |
| `OutputPriceCNY` | float64 | 输出单价（含 reasoning），元 / 1M tokens，4 位小数 |
| `PeakMultiplier` | float64 | 峰时倍率；1.0 = 无峰谷；DeepSeek = 2.0 |
| `InputTiers` | []PriceTier | 阶梯 / 分档；空 = 单档 |
| `LongContextMultiplier` | float64 | 长上下文档倍率（OpenAI：输入 >272K 时为短上下文的 2 倍；xAI：prompt >200K 时输入 / 输出 / 缓存全部 ×2） |
| `LongContextThreshold` | int | 长上下文档阈值（tokens）：OpenAI 272K、xAI 200,000 |
| `PriceValidUntil` | string | 限价有效期（YYYY-MM-DD）；Gemini 多个模型有时间限价，过期须重取官方价 |
| `Region` | string | 定价地域；费率行带 `region`，按实际路由地域取价（百炼按地域分别定价，本表取华北2（北京）） |
| `CachePriceUnknown` | bool | 缓存**命中**绝对单价官方未给、取控制台实价的模型为 true（`qwen3.8-max` / `qwen3.8-max-0902` / `qwen3.8-flash` / `qwen3.8-2.4t-a95b`）⇒ 命中费按 0 计并置 `Estimated = true`，写入价照表计 |
| `BatchDiscount` | float64 | Batch 折扣倍率；本期不做 Batch 计价，值为空 = 不支持 |
| `LocalDeployment` | bool | 本地部署标记（Ollama：`CostCNY = 0`，无 API 费用但有硬件成本） |
| `ContextWindow` | int | 上下文长度（tokens） |
| `Currency` | string | 官方原始币种（`"CNY"` / `"USD"`） |
| `PriceSource` | string | `"OfficialCNY"`（官方人民币原生价）/ `"Converted"`（USD × 7 换算） |
| `SnapshotDate` | string | 快照日期（YYYY-MM-DD） |

配置文件另带汇率字段 `usd_to_cny`（1 USD = 7 CNY，暂定、可配置）。

**`PriceSource` 的语义与自检**：`PriceSource` 决定该行单价是官方人民币原生价还是美元换算价 —— 国内供应商的行必须为 `OfficialCNY`；国内供应商的行若标 `Converted` ⇒ 视为数据错误，启动自检时直接报错而非照用。

**PriceTier（分档维度）**：分档维度取**输入长度 × 输出长度双维度并集**（`MaxInputTokens` × `MaxOutputTokens`），单维度模型只用输入维度：

```go
type PriceTier struct {
    MaxInputTokens   int     // 输入维度档位上限（含）
    MaxOutputTokens  int     // 输出维度档位上限（含）；仅输入维度分档时为 0（不限）
    InputPriceCNY    float64 // 该档输入单价（元 / 1M tokens，4 位小数）
    OutputPriceCNY   float64 // 该档输出单价（元 / 1M tokens，4 位小数）
}
```

- 选档规则（Qwen 等单维度阶梯）：按**单次请求的输入 Token 总量**落档（`MaxInputTokens`），整请求按所在档单价结算、⛔ 不分段；输出价随档位变。
- 双维度分档（智谱部分模型）：按**输入长度 × 输出长度**双维度落档（`MaxInputTokens` × `MaxOutputTokens`）。

**覆盖与变体**：token 单价字段之外的计价变体（缓存 TTL 分档 5m / 1h、30m / 12h；长上下文分档；Batch 折扣；地域 / 集群价；数据驻留与速度档加价；时间限价）以 5.4 费率总表为准；schema 已带长上下文倍率与阈值、峰谷倍率、Batch 折扣、地域、限价有效期等字段，其余变体接入对应通道时按 5.4 对应费率表注记取数。

### 5.5 币种与精度规则（官方原生价原则、USD×7 换算口径、小数位规则）

**官方原生价原则**：国内供应商（DeepSeek / Kimi / 智谱 / Qwen / MiniMax / MiMo）一律用**官方人民币原生价**，⛔ 不用美元价 × 汇率换算。官方人民币价与「美元价 × 汇率」的换算值并不相同（如 `deepseek-flash` 谷时输入官方 **¥1**，而美元价 \$0.15 × 7 = ¥1.05；`MiniMax-M3.1-Flash` 输入官方 **¥1**，美元价同为 \$0.15 × 7 = ¥1.05；`qwen3.8-max` 国内官方 **¥12**，国际站美元价 \$2 × 7 = ¥14）⇒ 换算会引入偏差并掩盖官方定价结构；实现上对国内供应商的行禁止走换算路径（`PriceSource` 必须为 `OfficialCNY`，否则启动自检报错）。

**USD×7 换算口径**：海外供应商（OpenAI / Anthropic / Gemini / xAI）官方只给美元价 ⇒ 按 **1 USD = 7 CNY**（暂定、可配置，配置字段 `usd_to_cny`）换算为人民币单价；换算在费率表入库时完成（`PriceSource = Converted` 的行单价已是 USD × 7 的结果），运行期 ⛔ 不再乘汇率、不做币种判断。汇率只作用于海外供应商 ⇒ 改汇率只需重算海外四家的换算价，国内单价不动。美元参考值 `CostUSD = CostCNY / 7`。

**小数位规则**：单价（元 / 1M tokens）与各分项、总费用均**四舍五入保留 4 位小数**；先按全精度算完分项与总和，最后统一舍入一次，⛔ 不对每个分项先舍入再相加（逐项先舍入会引入累计误差，四舍五入边界上可能差 1 个最小单位）。

### 5.6 费用来源优先级（上游返回的费用 vs 本地按费率表计算的优先级）

优先级从高到低：

```
① 供应商自报费用（如 xAI 的 cost_in_usd_ticks）→ Source = ProviderReported
② 供应商返回 usage + 费率总表计算 → Source = Estimated
③ usage 缺失（流中断）→ 估算 usage × 费率总表 → Source = Estimated, Estimated = true
④ 费率总表也没有该模型 → Source = Unknown, CostCNY = 0
```

- **① 供应商自报费用优先**：xAI 提供 `cost_in_usd_ticks`（$1\ \mathrm{USD} = 10^{10}$ ticks，是折扣后、含服务端工具费的**实际计费额**）⇒ 优先用供应商自报值，5.4 费率总表只做兜底；⚠️ 自报值是**美元** ⇒ 转人民币走 ÷ $10^{10}$ × 7（与费率总表同一条换算路径），⛔ 不是「原样就是人民币」。
- **② ③ 本地按费率总表计算**：供应商返回 usage 时按实际 usage 算（`Source = Estimated`）；usage 缺失（流中断）时先估算 usage 再按费率总表计算，`Source = Estimated` 且 `Estimated = true`。
- **`Estimated` 标志必须透传给调用方**：与 `Usage.Estimated` 联动 —— usage 是估算的 ⇒ 费用也是估算的。
- **④ 未知费率**：费率总表没有该模型 ⇒ `Source = Unknown`、`CostCNY = 0`，⛔ 不猜价。
- **取消不等于免单**：客户端主动取消或断开连接后，已产生的输入和输出用量仍会正常计费；计费至**取消点**、按已生成的**整 token** 计（半截 token 不退不补）⇒ 取消路径上 ⛔ 不可把费用清零；客户端断开后**未收到 usage 不代表不计费**。

### 5.7 Go 实现要点（Money/精度处理、四舍五入口径、未知费率的处理）

**精度处理（Money）**：金额与单价用 `float64` 承载，统一精度函数 `round4`。⚠️ `float64` 二进制表示不了精确的 0.0001 ⇒ 「四舍五入到 4 位」必须**先做 $v \times 10^{4}$ 再取整**（`math.Round(v*1e4)/1e4`），避免先除后乘在边界上差一个最小单位。费率表里 4 位小数的单价本身也不是二进制精确值 ⇒ 乘以 token 数后误差量级远小于 $10^{-4}$，不影响 4 位小数的正确性。

**四舍五入口径**：分项按全精度计算（⛔ 计算途中不舍入）；各明细展示值与总费用各自 `round4` 一次；总费用由全精度分项求和后舍入，⛔ 不由已舍入的分项相加得到。

```go
// round4 四舍五入到 4 位小数（费用与单价的统一精度口径）。
// 先乘后取整，避免"先除后乘"在边界上差一个最小单位。
func round4(v float64) float64 {
    return math.Round(v*1e4) / 1e4
}

func CalculateCost(usage *Usage, rate *ModelRate, callTime time.Time) Cost {
    // 1. 峰谷判定（仅 DeepSeek 等有 PeakMultiplier > 1 的模型）
    //    isPeakHour 按 holiday_calendar（默认 cn-fixed）判定中国法定节假日
    multiplier := 1.0
    peakApplied := false
    if rate.PeakMultiplier > 1.0 && isPeakHour(callTime, rate.Provider) {
        multiplier = rate.PeakMultiplier
        peakApplied = true
    }

    // 2. 阶梯计费（仅 Qwen 等有 InputTiers 的模型）
    //    选档依据 = 单次请求的输入 Token 总量（官方口径），⛔ 不是 InputTokensUncached
    inputPrice := rate.InputPriceCNY
    outputPrice := rate.OutputPriceCNY
    if len(rate.InputTiers) > 0 {
        inputPrice, outputPrice = selectTier(rate.InputTiers, usage.InputTokens)
    }

    // 3. 缓存价取档与未知处理：命中价按显式 / 隐式档取（CacheReadExplicitCNY / CacheReadImplicitCNY）；
    //    CachePriceUnknown=true 时命中费按 0 计并置 Estimated=true，⛔ 不猜价；写入价照表
    cacheReadPrice := cacheReadPriceFor(rate, usage) // 显式命中取 Explicit 档，隐式命中取 Implicit 档
    cacheWritePrice := rate.CacheWriteCNY
    estimated := usage.Estimated
    if rate.CachePriceUnknown {
        cacheReadPrice = 0
        estimated = true
    }

    // 4. 分项计算（单位：元 / 1M tokens → 元），保持全精度，⛔ 不在此处舍入
    inputCost := float64(usage.InputTokensUncached) * inputPrice * multiplier / 1e6
    cacheReadCost := float64(usage.CacheReadTokens) * cacheReadPrice * multiplier / 1e6
    cacheWriteCost := float64(usage.CacheWriteTokens) * cacheWritePrice * multiplier / 1e6
    outputCost := float64(usage.OutputTokens) * outputPrice * multiplier / 1e6

    // 5. 求和后统一舍入一次（⛔ 不要对每个分项先舍入再相加）
    total := inputCost + cacheReadCost + cacheWriteCost + outputCost

    return Cost{
        CostCNY:         round4(total),
        CostUSD:         round4(total / usdToCNY),
        InputCostCNY:    round4(inputCost),
        CacheReadCostCNY: round4(cacheReadCost),
        CacheWriteCostCNY: round4(cacheWriteCost),
        OutputCostCNY:   round4(outputCost),
        Source:          estimatedSource(estimated),
        RateSnapshot:    rate.SnapshotID(callTime),
        PeakApplied:     peakApplied,
        Estimated:       estimated,
    }
}
```

**要点**：

- 峰谷判定用 `callTime`（调用发起时间），⛔ 不是响应完成时间；法定节假日按 `holiday_calendar`（默认 `cn-fixed`）判定。
- 阶梯 `selectTier` 按 `usage.InputTokens`（总输入）选档，⛔ 不按 `InputTokensUncached`（该请求所有 token 按所在档单价结算）。
- 运行期只有「算钱」和「舍入」两件事，⛔ 不做币种判断：`OfficialCNY` 的行单价已是人民币直接用；`Converted` 的行单价已是 USD × 7 的结果，⛔ 运行期不再乘汇率；币种校验放在费率表加载期自检（国内供应商的行标 `Converted` ⇒ 报错）。
- **缓存价未知的处理**：`CachePriceUnknown = true`（Qwen 等「见控制台」口径的模型）⇒ 缓存**命中**费用按 0 计并置 `Estimated = true` 透传，⛔ 不猜价；**写入价照表计**。
- **缓存命中档位**：显式缓存命中取 `CacheReadExplicitCNY` 档、隐式命中取 `CacheReadImplicitCNY` 档，由适配器按该家缓存形态标记；单一命中价的供应商两档同值。
- **未知费率的处理**：费率总表没有该模型 ⇒ `Source = Unknown`、`CostCNY = 0`，⛔ 不猜价、⛔ 不借用相似模型的价；usage 缺失（流中断）时先估算 usage 再计费，`Estimated = true` 并透传。

### 6.2 Span 与属性清单（逐字段列出要落的字段、含义、取值）

**span 结构**

- 每次**上游执行**（网关对某一个具体端点的一次调用，含其重试）一个 CLIENT span；降级链上每个端点**各自独立 span**，属性对应各自 provider（「这次到底打了谁」在 Trace 里一目了然）。
- span 名 = `{gen_ai.operation.name}`；`gen_ai.operation.name` = `chat`。
- 自动重试**合并进同一个 span**；span 覆盖该逻辑操作的完整时长（含全部重试），从请求发起开始，到响应完全收到、或因错误 / 取消终止为止。

**逐字段清单**

| 字段 | 含义 | 取值 |
|---|---|---|
| `gen_ai.operation.name` | 操作名；span 名 = `{gen_ai.operation.name}` | `chat`（本设计的 chat 入口）。枚举另含 `create_agent` / `invoke_agent` / `invoke_workflow` / `plan` / `invoke_runner` / `execute_tool` / `retrieval` / `embeddings` / `text_completion` / `generate_content` / `realtime_inference` / `fetch_response` / `create_memory_store` / `search_memory` / `create_memory` / `update_memory` / `upsert_memory` / `delete_memory` / `delete_memory_store` |
| span kind | span 种类 | `CLIENT` |
| `gen_ai.provider.name` | 实际落到的 provider | 如 `openai` / `deepseek`；可与客户端配置的 provider 不同 |
| `gen_ai.operation.name` 的必备同伴字段 | GenAI span 必备 | `gen_ai.provider.name` 与 `gen_ai.operation.name` 为 GenAI span 必备字段 |
| `gen_ai.request.model` | 请求的模型 | 客户端请求的模型名（别名） |
| `gen_ai.response.model` | 实际响应模型 | 上游返回的模型标识 |
| `gen_ai.response.id` | 响应标识 | 上游返回的响应 ID |

| `gen_ai.usage.input_tokens` | 输入 token 数 | 取消场景下记**取消点前**的实际值 |

### 6.3 取消的 Trace 口径（取消不记为错误；含逐行口径表）

**三情形口径表**：

| 情形 | span status | `error.type` | `gen_ai.response.status` |
|---|---|---|---|
| 正常完成 | `Unset` | 不设 | `completed` |
| **用户点停止（取消）** | **`Unset`** | **不设** | **`cancelled`** |
| 上游 5xx / 超时 | `Error` | 设 | `failed` |

规则：操作无错结束时 span status 保持 `Unset`；被重试消化或被优雅处理的错误不记在该操作的 span / 指标上；同一异常不重复记录。**取消不记为错误、不计入错误率指标**（取消是不可清晰归类为错误的条件，与 404 同类）。

**取消场景逐行口径表**（span 生命周期：请求发起时创建 → **取消发生的那一刻结束**（不等上游自然结束）⇒ 取消后立即能在 Trace 里查到这条调用已收口，**不是悬挂 span**）：

| 属性 | 值 |
|---|---|
| `gen_ai.operation.name` | `chat` |
| `gen_ai.provider.name` | 实际落到的 provider（如 `openai` / `deepseek`），可与客户端配置的 provider 不同 |
| `gen_ai.request.model` / `gen_ai.response.model` | 请求模型 / 实际响应模型 |
| `gen_ai.request.stream` | `true`（仅流式设） |
| `gen_ai.request.stream_cursor` | 最后一个 SSE 事件游标（用于断点续传） |
| `gen_ai.usage.input_tokens` / `output_tokens` | **取消点前**的实际值 |
| `gen_ai.response.status` | **`cancelled`** |
| `gen_ai.response.finish_reasons` | `["error"]` |
| **span status** | **`Unset`（不设 ERROR）** |
| **`error.type`** | **不设** |
| `gateway.cancel.reason` | `client_disconnect` / `upstream_error` / `timeout` / `shutdown` |
| `gateway.cancel.detected_latency_ms` | 从检测到断连到关闭上游的延迟 |
| `gateway.cancel.upstream_closed` | 是否真的关了上游连接 |
| `gateway.cancel.tokens_after_cancel` | 取消后仍产生的 token 数（应为 0） |

**自定义属性命名空间**：`gen_ai.` 是封闭的语义命名空间，自定义属性不进该命名空间，一律用 `gateway.*` 前缀。

**自定义属性含义**：

| 属性 | 含义 |
|---|---|
| `gateway.cancel.reason` | 取消原因四类枚举：`client_disconnect`（用户点了停止）/ `upstream_error` / `timeout` / `shutdown` |
| `gateway.cancel.detected_latency_ms` | 从检测到断连到关闭上游的延迟 |
| `gateway.cancel.upstream_closed` | 是否真的关了上游连接（bool） |
| `gateway.cancel.tokens_after_cancel` | 取消后仍产生的 token 数（应为 0） |

### 6.4 内容采集默认关闭与采样

**内容采集**：

- prompt 全文 / 响应全文 / 工具参数 / 工具结果的采集由**显式 opt-in** 开启。
- 开关经环境变量配置时必须命名为 `OTEL_INSTRUMENTATION_GENAI_CAPTURE_CONTENT`。
- 取值：`NO_CONTENT`（**默认**）/ `SPAN_ONLY` / `EVENT_ONLY` / `SPAN_AND_EVENT`；非法或不可识别的取值回落 `NO_CONTENT`。
- 本设计默认 `NO_CONTENT`；**不采集** prompt 全文 / 响应全文 / 工具参数 / 工具结果。trace 中不得出现 prompt / 响应全文。

**脱敏位置**：敏感内容的遮蔽在**出口层**（采集 / 导出侧）完成，敏感内容不落存储；遮蔽决策随记录留存。

**采样**：head sampling 无法保证保留未来才出错的 trace（取消即「未来的失败」）⇒ 取消事件必须有**独立计数指标**（不受 trace 采样影响），至少：

- `gateway.requests`（按 provider / 模型 / 结果标签）
- `gateway.cancelled`（按原因）
- `gateway.tokens`（按方向）
- `gateway.cancel.detected_latency`（直方图）

**内容采集与「复原完整请求」的显式取舍**：复原「发给模型的完整请求」的**责任主体是调用方应用的事件日志**，不是网关 trace —— 网关默认只记元数据（请求 / 响应的形状、token、耗时、状态），⛔ 不把 prompt 与补全文本默认写进 trace。需要端到端排查时**显式打开**内容采集（环境开关），且采集内容在出口层按 `[REDACTED:<类型>]` 统一脱敏。该取舍显式记录，⛔ 不以「默认关闭」静默缺位。

### 6.5 三层证据链（怎么确认网关真的做了取消）

确认「网关真的做了取消」分三层，逐层都有可执行的验收要求。

**L1 网关自证（可自动断言）**：

| 断言 | 手段 |
|---|---|
| 上游连接已关闭 | fake upstream 记录 `closed` 标志；断言为 true |
| 取消后再无读取 | 取消后上游读取计数不再增长 |
| 取消已写入 Trace | span 已结束 + `gen_ai.response.status=cancelled` + `gateway.cancel.*` |
| 无分片泄漏到客户端 | 取消后客户端收到的帧数 == 取消点前的帧数 |

**L2 传输层确认**：反向代理 / 负载均衡可能在客户端离开后保持到网关的连接、吞掉断连 ⇒：

- 验收时确认断连能穿透代理到达网关（代理开启 client-abort 处理）。
- 代理侧 client-abort 计数与网关侧取消计数**对账**。

**L3 外部可核对（关键，不能只信自证）**：

- **判定口径两条同时看**：① 重试额外制造的上游执行数；② 客户端最终真正收到的调用数。
- **请求合并（coalescing）**：`client_request_id`（一次用户轮次对话的唯一标识，由客户端提供或网关生成）**贯穿该轮全部尝试**（含重试 / 降级 / 第二跳），每次尝试携带同一标识。
- **重试预算**：作为治理配置存在（丢弃超额重试）。
- **OC-1**：网关须暴露「重试额外制造的上游执行数」与「客户端真正收到的调用数」两个口径 —— 取消率单独看会骗人。
- **OC-2**：对自建上游（vLLM 等），须能取到调度器侧的 aborted 计数与**实际计算量**，与网关侧记录对账；provider 自报的 token 数不得作为唯一依据。

### 6.6 流式取消全链路：五个动作、时间线与 SC 验收要点

**场景事实链**（「用户点停止」全链路）：

发起一段流式请求 → 收到几段内容 → 用户点停止 → ①前端停止追加内容 ②网关取消这次上游请求 / 关闭上游响应流 ③Trace 能查到这次调用 ④可以取消结束。

**协议层的标准形状**：

- 取消通知语义（借鉴 MCP）：fire-and-forget、无 ack、必须容忍竞态；只引用同方向先前发出且仍在处理中的请求；接收方停止处理、释放资源、不响应该请求；发送方忽略迟到响应；双方记录取消原因；UI 提示取消状态。
- SSE 侧没有对应标准 ⇒ 事实标准是**客户端 abort ⇒ 连接断开**。
- 浏览器侧：服务端监听请求 / 响应关闭事件并 abort 对上游的请求，否则模型继续生成、继续计费；`EventSource` 仅支持 GET，POST + 自定义头场景须走 fetch + ReadableStream。

**网关该做的五个要求**：

**要求 1 —— 断连检测：watcher + 轮询双路并行**。不得只依赖「下一次写入失败」检测断连（写失败要等下一个分片才出现）⇒ 两条路并行：独立 watcher 监听传输层断连事件并取消主任务；轮询检查客户端连接状态。**非流式路径必须自挂 watcher**（框架默认不取消普通请求处理器）；流式路径虽会被框架取消生成器，**但不能依赖它去关上游**。检测延迟上界可配置，**默认 1s**。

**要求 2 —— 取消传播到上游并关闭**：显式关闭上游响应，或取消上游请求。不做这一步的后果：上游继续解码、继续计费，产生无人读取的输出，形成「客户端连接已死、上游请求仍开着直到 finish_reason 或硬超时」的孤儿流。

**要求 3 —— 清理两道闸，独立于 body 迭代**：清理逻辑不得只挂在响应体生成器上（框架可能不消费该生成器：挂起或从未启动）⇒ **两道闸**：① 生成器 `finally`（正常路径）② 请求级 `finally`（生成器从未启动 / 挂起时的兜底）。否则上游连接与后台任务**静默泄漏**，表现为连接数缓慢上涨而非报错。

**要求 4 —— 取消原因四分类**：`client_disconnect`（用户点了停止）/ `upstream_error` / `timeout` / `shutdown` ⇒ 分类写入 `gateway.cancel.reason`；用户主动与系统故障分开统计。

**要求 5 —— 客户端职责**：前端停止追加必须由前端状态机自己保证（每条流一个 generation id，每次写入携带产生它的流 id，id 非当前活跃即丢弃），不能等网关通知 —— 客户端已断开时网关发不出任何额外帧。网关侧职责：不再发新分片 + 正常收口 + 在 Trace 留证据。

**时间线**：

| 时刻 | 事件 |
|---|---|
| $t_0$ | 流式请求发起，span 创建 |
| $t_1$ | 上游产出若干分片并转发到客户端 |
| $t_2$ | 用户点停止 ⇒ 客户端 abort ⇒ 连接断开 |
| $t_3$ | 网关检测到断连并关闭上游连接；检测延迟上界可配置（默认 1s） |
| $t_4$ | 上游连接关闭 / 上游请求取消；`gateway.cancel.detected_latency_ms` 记录 $t_2 \rightarrow t_4$ |
| $t_5$ | span 在取消发生的那一刻结束：`gen_ai.response.status=cancelled`、span status `Unset`、不设 `error.type` |
| $t_6$ | 取消之后：不再向客户端转发任何分片、迟到分片丢弃、同 `client_request_id` 的后续尝试被拒绝或替换 |
| $t_7$ | 计费边界：按取消点**之前**实际生成的整 token 计费，取消点之后的不产生 |

**验收要点（SC-1 … SC-8 摘要）**：

| 编号 | 验收条款 | 判定方式 |
|---|---|---|
| **SC-1** | 客户端断连后，网关在**有界延迟**内关闭上游连接 | 断言上游 `closed` 标志为 true；且关闭延迟 ≤ 配置上界（默认 1s） |
| **SC-2** | 上游响应对象已关闭，且关闭后**不再有读取** | 断言上游读取计数在取消后不再增长 |
| **SC-3** | Trace 中该 span **已结束**、`gen_ai.response.status == "cancelled"`、**span status 不是 ERROR**、未设 `error.type` | 断言 span 的 `end_time` 已设置 + 上述属性（用 `InMemorySpanExporter`） |
| **SC-4** | 取消后**不再向客户端转发任何分片** | 断言客户端收到的帧数 == 取消点前的帧数；且 `gateway.cancel.tokens_after_cancel == 0` |
| **SC-5** | 取消**不触发**降级或重试 | 断言：断连后无新的上游请求发起（上游请求计数 == 1）；同 `client_request_id` 的后续尝试被拒 |
| **SC-6** | 断连检测延迟**有上界且可测** | socket 级测试：读 N 帧后突然关闭 → 断言取消在 ≤ 上界内发生；且测出**实际延迟值**（进 `gateway.cancel.detected_latency_ms`） |
| **SC-7** | **非流式**路径客户端断开，同样被取消 | socket 级测试：非流式请求的客户端断开后，上游请求在 ≤ 上界内被取消（框架默认不取消普通请求处理器，须自挂 watcher） |
| **SC-8** | 客户端断连与网关主动取消**原因可区分** | 断言 `gateway.cancel.reason` 在两条路径上分别为 `client_disconnect` 与 `upstream_error`（或 `timeout`） |

**实现清单**：

| 能力 | 要求 |
|---|---|
| 断连检测 | watcher + 轮询双路（SC-6 / SC-7） |
| 上游取消 | 显式关闭上游响应 / 取消上游请求（SC-1 / SC-2） |
| 取消原因分类 | 四类枚举进 `gateway.cancel.reason`（SC-8） |
| 取消注册表 | `client_request_id → 上游执行句柄` 映射（fire-and-forget 语义） |
| Trace | 属性名集中在单一映射层（SC-3） |
| 重试抑制 | 进入取消终态的 id 拒绝后续尝试（SC-5） |

## 第七编 治理：错误、限流、重试、降级、熔断

### 7.1 错误分类（4xx/5xx 必须分开；错误对象保留上游状态码与请求 ID）

**七类分类**：`invalid_request`（4xx 类，含请求畸形 / 上下文超限 / 内容策略）/ `auth` / `rate_limit` / `upstream_error`（5xx 类）/ `timeout` / `budget_exceeded` / `cancelled`。

- **4xx 与 5xx 分开归类**：⛔ 不许把「端点校验更严导致 400」记成「模型没能力」。400（请求不合法）与「模型答不出」是两类完全不同的失败，不许被同一个统计口径吞成一类。
- 错误对象**同时携带**：对外归一分类 + **原始上游状态码** + **上游端点名** + **上游请求 ID**（若有）。
- **归一是对外的，原始信息必须对内保留。** 错误对象不得只有归一分类而无原始上游信息 —— 否则「端点校验更严」「模型没能力」「上游故障」事后无法区分。

### 7.2 限流与预算（按归一化 token 计，不只按请求）

**归一化 token 公式**（限流 / 预算计数口径）：

$$
\mathrm{normalized} = \mathrm{InputTokens} + \mathrm{OutputTokens}
$$

- 缓存命中与缓存写入按**自然 token 数**计入 $\mathrm{InputTokens}$（限流 / 预算的 token **计数**不按价格折扣折算成等效 token）；**计价独立执行** —— 各类 token 按 5.4 费率总表各自的**独立单价**（输入 / 输出 / 缓存命中 / 缓存写入）计价，与本计数口径无关。
- token 限流用归一化 token 计；费用预算按费用计量口径计得的费用计（单价取费率总表，用量取归一化口径）。

**限流与预算规则**：

- **令牌桶按归一化 token 计**（不是只按请求数）：桶的容量以 token 为单位，补充速率以 token/秒为单位；跨 provider 的计量采用统一的归一化 token 口径，使不同上游的消耗可比。
- **锚点分离（限流 vs 过载保护）**：**限流**锚定**上游套餐契约** —— 配额数字只来自契约登记（端点 `rate_limit` 的 tpm/rpm/burst_s、`caller_rate_limits` 按 key 登记），**未登记的维度不限流**，⛔ 不设拍脑袋默认值（无锚点默认值实测会造出隐藏吞吐天花板）；**过载保护**锚定**实测容量** —— 全局 `max-in-flight` 在途上限，超限 `429` + `Retry-After`。二者分账，⛔ 不混用锚点。
- **并发是一等限流维**：`concurrency_limit` 限制该端点（或共享组）的**在途上游请求数**（计量单位 = 在途上游尝试：发起 +1 / 收口 −1，流式长调用占位到流收口；⛔ 不按 TCP 连接数计）。与令牌桶（tpm/rpm）**并联判定**，任一不足即拒。
- **配额共享组 `limits_group`**：同组端点共享同一份 rate_limit / concurrency_limit 计数（对应供应商配额池的真实 scope：同供应商多模型 / 多 key / 多部署可能共享一个配额池）；同组声明必须逐字一致，否则启动报错。缺省 = 端点自成一组。
- **上游多 key 契约配额（`credential_rate_limits`）**：同供应商多 key 池（一个 `credential_ref` 的环境变量值 = 逗号/换行分隔多 key）按三层登记配额 —— `per_key` 每 key 一份桶（N 个 key = N 份套餐容量）、`shared` 全池共享一份桶（org/项目级配额池）、`key_limits` 逐 key 覆盖（按池内顺序，null 项用 per_key 缺省，不同订阅档混池）。选键 = 先探后扣、桶空溢出下一槽（fill_first）；429 精确冷却命中的那个 key；全池受限才整体 429。未登记 ⇒ 不限流。⚠️ **两域解耦**：调用方令牌（外部项目签发、管理本系统消费额度）与上游自有令牌（发给供应商）互不相通，⛔ 调用方凭据永不进上游请求头。
- 限流超限 → `429`，**带 `Retry-After`**（含并发维拒绝；本地闸拒绝的 `Retry-After` = 最短等待）。
- **预算上限**：每调用方（`client_request_id` 的调用主体）有 token 预算上限，**触顶即拒绝**（不是只做报表）；超限 → `429`（分类 `budget_exceeded`），**在发起上游请求之前**拒绝。
- 虚拟密钥与计费报表为 non-goal；注册表的**凭据来源引用字段**必须就位。

**计费边界规则**：

- 计费至**取消点**，按已生成的**整 token** 计（半截 token 不退不补）。
- 客户端断开后**未收到 usage 不代表不计费**：断连后输入照常计费、输出按已生成计费。
- usage 缺失时网关按已知信息估算并置 `Estimated=true`，⛔ 不按 0 计。
- 取消能省的只是**取消点之后**的 token，已生成的照付 ⇒ 取消**越早送达上游越省**（断连检测延迟必须有界）。

### 7.3 熔断与冷却

**状态机三态**：`CLOSED` →（连续失败达阈值）→ `OPEN` →（冷却期满）→ `HALF-OPEN`（放行探测请求）→ 成功回 `CLOSED` / 失败回 `OPEN`。

**默认值**（全部可配置）：

| 配置项 | 默认值 | 语义 |
|---|---|---|
| `breaker.failure_threshold` | 连续 **5** 次可归因失败 | 同一端点连续 5 次可归因失败（5xx / 超时 / 连接失败）⇒ 熔断打开 |
| `breaker.cooldown_s` | **30** 秒 | 熔断打开时长；到期转半开 |
| `breaker.probe` | 半开放行 **1** 个探测请求 | 探测成功闭合，失败重新计 30 秒 |

**规则**：

- 触发信号：连续超时与错误计数（可归因失败 = 5xx / 超时 / 连接失败）。
- 熔断期间跳过该端点，转降级链上的其他端点；冷却期内该端点被跳过。
- 阈值、冷却时长、探测数**均可配置**，默认值如上表。

### 7.4 重试与降级分别设上限（⛔ 不合成兜底循环）

**基本口径**

- **降级 ≠ 重试**：重试打同一个端点（换一次可能成功），降级换端点（换一次可能成功）—— 两者的次数**必须分别有上限**，⛔ 不许合成一个「兜底循环」。
- 重试：打同一端点，上限 = `Endpoint.max_retries`；降级：换端点，上限 = 独立配置。任一上限用尽即**显式失败**。
- 重试在「级」内、降级在「级」间，**两者各自计数**（`RetryCount` 与 `FallbackCount` 分开统计，⛔ 不混成一个数）。

**按失败类型分链**

- 输入为主端点 + 失败类型（`general` / `context_window` / `content_policy` / `budget` / `rate_limit` / `timeout` / `upstream_error`）；输出为该类型下的降级链（显式有序）。
- 某类型无降级端点 ⇒ **显式报错**，⛔ 不静默回落到通用链。
- 上下文越界判定：请求的估算输入 token + 请求 `max_tokens` 与 `context_window` 比较；越界 ⇒ 走 `context_window` 降级链；无该链 ⇒ 显式报错并告知「上下文超限且无可用的大窗口端点」（⛔ 不许截断后悄悄发出去）。

### 7.5 取消后抑制重试（late cancel race）

**抑制口径**

- **取消不触发降级或重试**：断连后不得发起新的上游请求（同轮上游请求计数保持不变）。
- `client_request_id`（一次用户轮次对话的唯一标识，由客户端提供或网关生成，**贯穿该轮的全部尝试**——含重试 / 降级 / 第二跳）进入**取消终态**后，同 id 的后续尝试（重试 / 降级 / 第二跳）**必须被拒绝或替换**，由取消注册表（`client_request_id → 上游执行句柄` 的映射）判定。
- **幂等收口**：取消与「上游刚好完成」并发 ⇒ 只记一次取消。
- **竞态容忍**：取消通知可能在处理完成后甚至响应已发出后到达；取消注册表查不到 / 已收口 ⇒ 静默忽略（不报错）；取消后到达的迟到分片**丢弃**，不追加到客户端。

## 第八编 安全

### 8.1 网关是凭据集中点：凭据只从来源引用读取，遮蔽形态统一 [REDACTED:<类型>]

- 注册表 `Endpoint.credential_ref` 只存**来源引用**（环境变量名 / 密钥别名），⛔ 不存明文；注册表因此可以安全地进日志、进快照、进文档。
- 凭据只从环境变量或密钥管理服务读取（`.env` 只作本地开发便利，真值由环境注入），不入库。
- **两段式凭据**：调用方凭据 → 网关凭据；网关**用自己的凭据**打上游，⛔ 不透传调用方的凭据，⛔ 不接受或转发任何其他 token（防 confused deputy）。
- **出口层统一遮蔽**：日志 / 轨迹 / 异常序列化处统一遮蔽为 `[REDACTED:<类型>]`（如 `[REDACTED:api_key]` / `[REDACTED:authorization]`），⛔ 不许各写各的（`***` / `xxx` 之类）—— 形态不统一，下游就无法只靠一个正则把它们全筛掉。
- ⛔ 不把凭据当参数在函数之间层层传递（传递链越长泄露点越多）；凭据经当前请求上下文获取，请求结束时显式清空。
- 自签发的调用方凭据沿用「每调用方一密钥、不共享」的原则（虚拟密钥体系为 non-goal，字段一步到位）。
- 访问令牌 ⛔ 不放进 URI 查询串；鉴权错误按语义返回：401（未认证或 token 无效）/ 403（scope 无效或权限不足）/ 400（鉴权请求畸形）。

### 8.2 出网管控（私网地址拒绝 403 egress_denied；shadow access）

- 上游 URL 在**单一控制点**校验（协议白名单 + 默认拒绝私网 / 链路本地地址），防 SSRF 与 shadow access。
- **协议白名单**：仅允许 `https`；**环回地址（127.0.0.0/8、::1）放行的端点允许 `http`**（本地推理服务），且环回放行**可配置、不限定端口**。
- **失败语义**：校验不通过 ⇒ 显式报错 **`403 egress_denied`**，⛔ 不静默改投其他端点。
- 动态出现的后端 URL（被诱导出的 elicited URL）同样过这个控制点：validate, sandbox, observe，从单点完成。
- 直连 provider 端点的出网只允许从网关发出。

### 8.3 成本攻击面

- 只限请求数的网关挡不住按 token 放大的成本与滥用 ⇒ 防线是 **token 级限流 + 触顶即拒的预算上限**（按归一化 token 计），并在发起上游请求之前拒绝。
- 每调用方独立预算与模型白名单（有 owner、有到期），一个密钥不共享给多个调用方。
- 取消能省的只是**取消点之后**的 token，已生成的照付（计费边界见 7.2）⇒ 取消**越早送达越省**（断连检测延迟必须有界）。

### 8.4 上游鉴权头注入（api-key: / x-api-key / Authorization 按 provider）

- 网关以**自己的凭据**打上游（两段式：调用方凭据 → 网关凭据）；⛔ 不透传调用方凭据。
- 上游鉴权头**按 provider 分派**，支持三种形态：`api-key:` / `x-api-key` / `Authorization`。头名是 provider 适配层的注册表字段，⛔ 不许全局硬编码一种头名。
- 凭据值来自 `credential_ref` 指向的环境变量 / 密钥别名，在出站请求构造处解析注入；不在函数间层层传递明文。
- 该凭据值在日志 / 轨迹 / 异常序列化中一律遮蔽为 `[REDACTED:api_key]` 或 `[REDACTED:authorization]`（统一形态 `[REDACTED:<类型>]`）。
- 头名选择错误表现为上游 401/403 且错误信息未必点名头部 ⇒ 头名映射必须逐 provider 明确登记、可核对。
- 逐 provider 的具体头名映射登记在 provider 适配层的注册表字段中；本编只定注入口径与遮蔽规则。

### 8.5 管理面默认不绑定公网

- 数据面（`/v1/chat/completions` 等业务入口）与管理面（注册表查看等）**不同端口 / 不同进程**。
- 管理面默认**不绑定公网**；默认 master key 不存在于可公网触达的面。
- 管理面的公网暴露必须是显式动作，不是默认状态。

## 第九编 配置与注册表

### 9.1 端点注册表必备字段 schema（名称、base_url、upstream_model、credential_ref、capabilities、context_window、输出上限、默认超时、重试次数、priority 等；字段语义逐条定义）

**模型映射（调用方唯一可见面）**：注册表即映射表 —— 列表名 `model` → `upstream_model` + 端点 + 请求形状（形状按 3.6 优先级链选定）。`GET /v1/models` 由注册表生成（返回 `context_window` / `capabilities`）；请求的 `model` **必须是列表内名称**，列表外 ⇒ 显式报错 `404 model_not_found`，⛔ 不透传任意模型名、⛔ 调用方不选模型之外的任何路由要素。

端点注册表的 `Endpoint` schema（Go 落地）：

```go
type Endpoint struct {
    Name         string        // 全局唯一
    BaseURL      string
    Model        string        // 客户端请求的模型名（别名）
    UpstreamModel string       // 实际上游模型标识（对齐 LiteLLM 的两层语义）
    ProviderName string        // OTel gen_ai.provider.name 取值
    ContextWindow int
    MaxOutputTokens int
    Capabilities Capabilities  // {SupportsTools, SupportsStream, SupportsVision}
    CredentialRef string       // 环境变量名或密钥别名，⛔ 不存明文
    TimeoutS     float64
    MaxRetries   int
    Priority     int           // 数值越小越优先
    RateLimit    *RateLimit    // 可选：套餐契约配额 {TPM, RPM, BurstS}；未登记 ⇒ 不限流
    ConcurrencyLimit int64     // 可选：在途上游请求数上限；0 = 不限
    LimitsGroup  string        // 可选：配额共享组名；空 = 端点自成一组
}

type RateLimit struct {
    TPM    float64 // 每分钟归一化 token 配额（<=0 ⇒ token 维不限）
    RPM    float64 // 每分钟请求数配额（<=0 ⇒ 请求维不限）
    BurstS float64 // 桶深折算秒数（桶深 = 速率/60 × burst_s，按真实客户端扇出登记，⛔ 不猜）
}
```

**可选配额字段（锚点分离，7.2）**：`RateLimit` / `ConcurrencyLimit` / `LimitsGroup` 均为可选 ——
未登记 ⇒ 该维度不限流（⛔ 不造默认值）。同 `LimitsGroup` 各端点的配额声明必须**逐字一致**
（共享一份计数；不一致 ⇒ 启动报错）。顶层 `caller_rate_limits`（可选）按调用方 key 登记契约配额
（`key_ref` = 环境变量名，⛔ 不存明文；`tpm` / `rpm` / `burst_s` 同口径），命中者以契约为准、
未登记的 key 不限流。

字段语义逐条：

| 字段 | 语义 |
|---|---|
| `Name` | 端点名称，**全局唯一** |
| `BaseURL` | 上游 base URL（识别层按 host 规则表判定供应商） |
| `Model` | **客户端请求的模型名（别名）**——调用方看到的模型标识 |
| `UpstreamModel` | **实际上游模型标识**：别名与真实上游模型分离，路由按别名命中、请求按 `UpstreamModel` 发出 |
| `ProviderName` | OTel `gen_ai.provider.name` 取值（可观测字段名与实际配置逐字一致） |
| `ContextWindow` | 上下文长度上限（token）；越界判定与 `/v1/models` 输出都用它 |
| `MaxOutputTokens` | 输出上限（token）；越界判定用「估算输入 + `max_output_tokens` > `context_window`」 |
| `Capabilities` | 能力标记 `{SupportsTools, SupportsStream, SupportsVision}`（tools / stream / vision 三项） |
| `CredentialRef` | **凭据来源引用**（环境变量名 / 密钥别名），⛔ 不存明文 |
| `TimeoutS` | 默认超时（秒） |
| `MaxRetries` | 重试次数上限（⛔ 与降级次数分开计） |
| `Priority` | 优先级，**数值越小越优先** |

**必备字段完整性**：`upstream_model` / `capabilities` / `credential_ref` 缺失 ⇒ **启动报错**（⛔ 不用默认值静默补齐）。注册表是路由的唯一真源，字段缺失不允许被静默补齐掩盖。

**能力声明**：`SupportsPreviousResponseID bool` 等上游能力由 adapter 声明（⛔ 不靠运行时探测），随 `Resolution` 传递，供会话态透传判定使用。

### 9.2 配置文件结构（对照 config/gateway.example.json 的实况）

配置文件为 JSON。顶层结构：

| 键 | 语义 |
|---|---|
| `strategy` | 路由策略：`priority`（优先级）/ `round_robin`（轮转） |
| `endpoints` | 端点数组，每项对应 9.1 的 `Endpoint` schema |

端点项字段与 9.1 同名同义；`model` 为客户端别名、`upstream_model` 为实际上游模型（两层语义分离），`priority` 数值越小越优先。

结构与校验规则：

- **未知字段拒绝**：配置解析遇到未知字段即报错，不静默忽略。
- **必备字段完整**：`upstream_model` / `capabilities` / `credential_ref` 为必备字段；`config/gateway.example.json` 的每个端点项须补齐 `upstream_model` / `capabilities` / `credential_ref` / `provider_name` / `max_output_tokens`，缺失 ⇒ **启动报错**（⛔ 不用默认值静默补齐）。
- **出网一致性**：示例中的本地端点走环回地址（127.0.0.1），须与出网白名单的环回可配置放行口径一致；私网地址默认拒绝。

### 9.3 费率表的关系（费用数据单一数据源是费率总表，配置只引用、不复制价格）

费用数据的**单一数据源**是费率总表（见 5.4）：设计文档与实现代码都从这里取数，⛔ 不在多处硬编码同一份费率。端点注册表 / 网关配置**只引用费率，不复制价格**——⛔ 配置里不写单价数字。

费率表与配置的关系逐条：

- **费率的唯一真源**：费率总表（见 5.4，每条带快照日期）。⛔ 不在设计文档、配置、代码里重复维护价格。
- **费率数据驱动**：费率以 JSON 配置文件存储（`config/rates.json`），数据驱动、不硬编码在逻辑里；`config/rates.json` 的数据**必须与费率总表一致**，费率总表更新后同步更新该文件，⛔ 不许两处不一致。
- **币种与汇率**：国内供应商（DeepSeek / Kimi / 智谱 / Qwen / MiniMax / MiMo）一律用**官方人民币原生价**，⛔ 不用美元价 × 汇率换算；海外供应商（OpenAI / Anthropic / Gemini / xAI）官方只给美元价 ⇒ 按 `USD × 7` 换算；汇率存在 `config/rates.json` 的 `usd_to_cny` 字段（可配置，当前取值 1 USD = 7 CNY）。
- **精度**：单价与总费用均四舍五入保留 4 位小数。
- **价格来源标记**：`PriceSource` 区分 `OfficialCNY`（官方人民币原生价）与 `Converted`（USD × 7 换算）；国内供应商的行若标 `Converted` ⇒ 视为数据错误，直接报错而非照用。
- **`config/rates.json` 的性质**：它是**运行时费率数据载体（生成物）**，由费率总表生成 / 同步（带 `SnapshotDate` 与 `PriceSource`），⛔ 不是手抄价格的第二份真源；生成与对账走可重跑脚本。

## 第十编 模块与目录结构、依赖

### 10.1 逻辑模块划分与依赖方向（core 不依赖 adapter/codec；detect 为纯函数；单向下沉）

包名用逻辑名，实施时映射到实际仓库路径。模块边界规则（避免职责渗漏，依赖方向单向下沉）：

- `core` **不依赖**任何 adapter / codec ⇒ 规范模型是纯数据结构。
- `adapter` 依赖 `core`，**不依赖** `codec` ⇒ 供应商适配只跟规范模型打交道。
- `codec` 依赖 `core`，**不依赖** `adapter` ⇒ 形状编解码与供应商无关。
- `detect` **不依赖** `core` 以外的任何包 ⇒ 识别是纯函数（可独立测试）。
- `usage` 依赖 `core` ⇒ usage 归一化独立成一层，便于单测与口径审计。
- `errors` **不依赖** `adapter` / `codec` ⇒ 错误分类与供应商无关（分类靠状态码 + 错误体模式，不靠供应商名）。
- `routing` 依赖 `core` + `detect` ⇒ 路由判定消费识别结果，⛔ 不自己做识别。
- `policy` 依赖 `core` ⇒ 治理层只看规范模型的 usage / 调用方标识，⛔ 不看供应商细节。
- `security` **不依赖** `core` 以外的业务包 ⇒ 凭据解析与出网校验是独立安全层（⛔ 不许被业务代码绕过）。
- `telemetry` 依赖 `core` ⇒ 观测层只看规范模型，⛔ 不直接读供应商响应（那会绕过归一化）。

要点归纳：**`core` 不依赖 `adapter`/`codec`；`detect` 为纯函数；依赖方向单向下沉**。

| **协议** | 11 家请求 schema | 每家 adapter 的 `BuildRequest` 产出的请求体 / 路径 / 鉴权头与官方文档逐字一致 |
| **协议** | 注册表字段完整性 | `upstream_model` / `capabilities` / `credential_ref` 缺失 ⇒ 启动报错（⛔ 不用默认值静默补齐） |
| **路由** | 可复现性 | 同一 `base_url` + `model` 识别 100 次 ⇒ 结果完全一致 |
| **路由** | 上下文越界 | 估算输入 + max_output > context_window ⇒ 走专用降级路径；无路径 ⇒ 报 `400 context_exceeded` |
| **路由** | `/v1/models` | 响应含 `context_window` / `capabilities`，且值与注册表一致 |
| **错误** | 七类归类 | 400/401/403/404/429/500/503/超时/取消 各自映射到正确类别 |
| **错误** | 原始信息保留 | 错误对象含 `UpstreamStatus` / `UpstreamRequestID` / `UpstreamBody`（脱敏后） |
| **错误** | 重试与降级分别计数 | 模拟「同一端点重试 2 次 + 降级到另一端点」⇒ `RetryCount=2`、`FallbackCount=1`（⛔ 不混成 3） |
| **治理** | token 级限流 | 按归一化 `InputTokens+OutputTokens` 限流（⛔ 不按请求数）；超限 ⇒ `429` + `Retry-After` |
| **治理** | 预算触顶 | 预算用尽 ⇒ **在发起上游请求之前**拒绝（上游调用计数 == 0） |
| **可观测** | 取消不是错误 | span status == `Unset`（⛔ 不是 `ERROR`）；`error.type` 不存在 |
| **安全** | 凭据不落明文 | 日志 / Trace / 异常序列化中搜索真实 key ⇒ 0 命中 |
| **安全** | 私网拒绝 | 私网地址端点（10.0.0.1:8000）⇒ `403 egress_denied`；环回地址端点（127.0.0.1:11434，Ollama）⇒ 允许 |
| **安全** | 三种鉴权头 | MiMo 请求头含 `api-key:`（非 `Authorization`）；Claude 请求头含 `x-api-key` + `anthropic-version`；其余含 `Authorization: Bearer` |

### 11.4 端到端测试

- 用 Go 标准库测试服务器起本地假供应商，返回**真实录制的响应样本**（⛔ 不用手写合成 JSON）。
- 流式：断言帧序列、末帧 usage、终止哨兵。
- 取消：客户端断连 ⇒ 断言上游连接被关闭、无后续帧、无重试。

### 11.5 断言有效性自检（每条断言要验证「错误实现会红」）

- 每条断言落笔前先造两个样本：**恒真样本**（错误实现也通过）与**恒假样本**（错误实现会红）；确认断言在**错误实现上真的会红**，再用它下结论。
- 断言的观测量必须是会变的量，不能是常量，也不能是恒量。
- 示例：断言「Anthropic 归一后总输入 = 200050」⇒ 配一版「直接取 `input_tokens`」的错误实现，确认断言红。
- 示例：断言「取消后上游被关闭」⇒ 配一版「不关闭上游响应」的错误实现，确认断言红。

## 第十二编 验收标准

> 三级验收：**A 级 = 功能验收**、**D 级 = 五域覆盖验收**、**SC 级 = 流式取消专项验收**。每条关键断言都必须做过「错误实现会红」的验证（11.5）。

## 12.1 功能验收（A1–A14）

| 编号 | 验收口径 |
|---|---|
| A1 | 11 家供应商的 base URL 各自命中正确 provider 与 shape（表驱动单测） |
| A2 | 入站两套入口（Chat / Responses）都能完整跑通非流式与流式 |
| A3 | Claude 出站走 **Anthropic 原生**（`/v1/messages`），⛔ 不经 OpenAI 形状中转 |
| A4 | 统一 Usage 的三个字段（输入 / 缓存命中 / 输出）逐家对齐真实响应样本 |
| A5 | 缓存**写入**单列，不与命中量累加 |
| A6 | Anthropic 残值语义正确（`InputTokens` = 三项之和） |
| A7 | 流中断时 `Estimated=true`，且不产生负数 token |
| A8 | 不可逆的转换（签名 / 加密推理链丢失）**必定**产生 `x_gateway.degradations[]` 标记，⛔ 不静默丢 |
| A9 | 每条关键断言都做过「错误实现会红」的验证 |
| A10 | `core` 不依赖 `adapter`/`codec`；`detect` 为纯函数（依赖方向单向下沉） |
| A11 | **会话态口径**：带 `previous_response_id` 的请求打到**不支持**该能力的上游 ⇒ 返回 `400 unsupported_capability`（⛔ 不是静默丢弃，也不是静默改写为全量历史） |
| A12 | **会话态口径**：`prompt_cache_key` 在支持的上游被透传；**取消时机口径**：`cancel_grace_period` 默认 0 ⇒ 断连后上游连接**立即**关闭（延迟路径默认不触发） |
| A13 | **取消时机口径**：`cancel_grace_period > 0` 时上游连接在窗口内**保持打开**；窗口到期后关闭；显式取消可**提前**结束等待；定时器无泄漏（请求结束后计数归零） |
| A14 | 语义字段丢失（`signature` / `encrypted_content` / `previous_response_id`）**必定**产生 `x_gateway.degradations[]` 标记或错误；优化字段丢失**不**产生标记 |

## 12.2 五域覆盖验收（D1–D5）

| 编号 | 域 | 验收口径 |
|---|---|---|
| D1 | 协议/注册/执行 | 11 家上游的请求 schema 各自正确（表驱动单测）；注册表字段完整（含 `upstream_model` / `capabilities` / `credential_ref`）；流式三种格式（SSE / NDJSON / 事件流）各自跑通 |
| D2 | 路由/上下文 | 识别结果**可复现**（同输入 ⇒ 同 Provider/Shape）；上下文越界走专用降级路径；越界且无路径 ⇒ 显式报错（⛔ 不静默截断）；`/v1/models` 返回 `context_window` / `capabilities` |
| D3 | 错误/治理 | 七类错误各自归类正确；4xx 与 5xx **分开**；错误对象保留原始上游状态码与请求 ID；重试与降级**分别计数**（⛔ 不合成兜底）；token 级限流按**归一化 token** 计 |
| D4 | 可观测 | OTel GenAI span 齐全；取消 ⇒ `gen_ai.response.status="cancelled"` + span status 留 `Unset`；`gateway.*` 自定义属性不进 `gen_ai.`；`gateway.usage_missing_rate` 有值 |
| D5 | 安全 | 注册表与日志中**无明文凭据**（遮蔽形态统一 `[REDACTED:<类型>]`）；不透传调用方凭据；私网地址被拒（`403 egress_denied`）；管理面默认不绑定公网；`api-key:` / `x-api-key` / `Authorization` 三种鉴权头按 provider 正确注入 |

## 12.3 流式取消专项验收（SC-1–SC-8）

| 编号 | 验收口径 |
|---|---|
| SC-1 | 客户端断连后，网关在有界延迟内关闭上游连接（关闭延迟 ≤ 配置上界，默认 1s） |
| SC-2 | 上游响应对象已关闭，且关闭后不再有读取 |
| SC-3 | Trace 中该 span 已结束、`gen_ai.response.status == "cancelled"`、span status 不是 ERROR、未设 `error.type` |
| SC-4 | 取消后不再向客户端转发任何分片（取消点后帧数为 0） |
| SC-5 | 取消不触发降级或重试（无新的上游请求发起；同 `client_request_id` 的后续尝试被拒） |
| SC-6 | 断连检测延迟有上界且可测（socket 级测试实测延迟值进 `gateway.cancel.detected_latency_ms`） |
| SC-7 | 非流式路径客户端断开同样被取消（⛔ 不依赖框架默认行为） |
| SC-8 | 客户端断连与网关主动取消原因可区分（`gateway.cancel.reason` 分别为 `client_disconnect` 与 `upstream_error` / `timeout`） |

## 第十三编 风险与必须实现的缓解

| 风险 | 必须实现的缓解 |
|---|---|
| Responses ↔ Chat 的有损转换（`encrypted_content` / `thinking.signature` 丢失） | 响应体 `x_gateway.degradations[]` 显式标记，⛔ 不静默丢（3.4） |
| 服务端会话态（`previous_response_id`）只有 OpenAI 真支持 | 默认无状态 + 条件透传 + 不支持时显式报错 `400 unsupported_capability`（3.5） |
| `usage` 口径随供应商与模式漂移（11 家 × 2 模式） | 归一化器 + 口径单测逐家钉死（4.4）；字段名集中在 `core` 单一模块；升级供应商 SDK 时跑一次口径回归 |
| Qwen 原生 / Ollama 原生 / Gemini 原生非 SSE 或非 OpenAI 形状 | 适配器分派流式解析器（3.6、4.1）；⛔ 不全局假设 SSE |
| 供应商 API 变更（字段增删、端点废弃、参数约束变化） | host / 前缀规则表数据驱动（配置文件）不硬编码，带「最后核对日期」；参数白名单按 provider 声明 |
| provider 自报 token 不准 | `Usage` 标 `Estimated` 且保留 `Raw`（3.2）；⛔ 不把 provider 自报值当账单真值（5.6） |
| 延迟取消的重挂机制未实现 | 暂不实现（列入后续项）；`cancel_grace_period` 默认 0 ⇒ 默认路径不受影响（3.7） |
| 客户端断连与取消竞态（late cancel race） | 终态 id 拒绝/替换后续尝试、幂等收口、迟到分片丢弃、取消抑制重试（7.5） |
| 断连后计费边界争议 | 计费至取消点、按已生成整 token；usage 缺失置 `Estimated` 并估算，⛔ 不按 0 计（7.2、8.3） |
| 缓存价格不全（个别模型官方未列） | `CachePriceUnknown=true` 时缓存**命中**费按 0 计并置 `Estimated`、写入价照表，⛔ 不猜价（5.4） |

## 附录 A 术语表

| 术语 | 含义 |
|---|---|
| 规范模型 | 网关内部统一请求 / 响应结构（OpenAI 骨架的超集），承载双模式与语义字段（3.1） |
| Shape | 出站协议形状（Responses / Chat Completions / 原生），按端点选择（3.6） |
| 适配器（adapter） | 每供应商的出站实现：请求映射、流式解析、usage 归一 |
| 编解码（codec） | 入站双模式 ⇄ 规范模型的转换层（3.4） |
| 识别（detect） | 由 base URL + model name 判定供应商与形状的纯函数（3.3、4.6） |
| Usage | 统一 token 用量：输入 / 输入缓存命中 / 输出 + 缓存写入 + 估算标志 + 原始快照（3.2） |
| Cost | 统一费用结构：分 token 类别费用、来源、快照、峰谷标志（5.1） |
| 归一化 token | 限流与预算计数口径：输入 + 输出（缓存命中与写入计入输入）（7.2） |
| 重试 / 降级 | 重试 = 打同一端点；降级 = 换端点；分别计数、分别设上限（7.4） |
| 熔断 / 冷却 | 端点连续失败后暂摘除、冷却后半开探测（7.3） |
| `x_gateway.degradations[]` | 响应体内的降级标记数组：记录不可逆转换等语义损失（3.4） |
| 语义字段 / 优化字段 | 丢失会变答案的字段 vs 只影响成本延迟的字段（1.4.1） |
| `cancel_grace_period` | 取消时机配置项：默认 0（立即取消）（3.7） |
| late cancel race | 取消与重试 / 降级的竞态：取消后必须抑制重试（7.5） |
| 五域 | 协议/注册/执行、路由/上下文、错误/治理、可观测、安全（2.3） |
