W0 场景与需求

给跨境设备卖家做一个 **personal agent**：业务员在对话框里说要办的事，agent 自己去查、去算、去起草，写动作经人确认才发生。12 周只做这一个产品，一层比一层深。

## 去年大水漫灌，今年修修补补

大家是不是觉得今年面试变难了。先说今年的两个要求，再看市场对人的要求在哪四条线上变了。

// 今年的两个要求

既要

商业业务场景 make sense

，又要

技术深度足够深

。这两件事相辅相成：只有足够深的业务场景，才撑得起足够深的技术呈现。

会做 demo 的人太多了，真有系统级落地经验的人太少了。去年你有一个就行，今年要两个都满足。市场在出清只会 RAG demo、只会搭一个工作流的人。这也是我们开 S6 的目的：用一个真实的跨境设备业务场景，把这两件事同时做到。

变化在哪

四条线，都是从"能跑通"到"能上线、能运营、能进化"

每一条的"去年"都还能找到工作，"今年"是面试官追问三层之后你得接得住的东西。

01 · 交付形态

#### 从简单的 Workflow 到端到端的 Agent Runtime 产品化

去年

拖一个工作流、接一个 RAG，能跑通一个 demo 就算交付

今年

从一句话需求做到一个能用、能卖的产品：Agent Runtime、后端、数据、运行时、交付、商业化，整条线自己走完

02 · 服务等级

#### 从 Demo 到生产级的 Agent 长链路服务

去年

单次对话跑对就行，挂了重来，谁都能用，什么都能做

今年

长链路稳定运营：挂起续跑、检查点、幂等与一致性；安全与权限：权限分层、沙箱执行、租户隔离；满足 SLA，高并发、高可用

03 · 上线之后

#### 从搭完不管到系统化的评估和进化

去年

上线即结束，好不好靠感觉，坏了靠改 prompt

今年

数据回流、评测集、判定器、Badcase 根因分析、回归门禁，agent 越用越好，每次改动能量化

04 · 能力闭环

#### 从会搭一个 RAG / Agent 到 Agent 全栈架构师

去年

会调框架、会接模型，拿到需求不知道该做成什么样

今年

场景理解 → 架构设计 → 落地 → 优化的闭环，一个人能从业务痛点推到技术方案，再推回业务指标

一个真实业务场景从 Agent Runtime 做到上线、稳定运行、商业化，每一层都有拿得出手的落地细节，面试时每一句都能往下追三层。

> **// 进入正题**
> 手上已经有 Codex、WorkBuddy ，
> *为什么还要自己做一个*跨境数字员工？
> 先想 30 秒。把 Codex 直接丢给业务员用，下面四件事每一件都会发生。
> **接不上业务系统**它不知道 ERP 里哪单延迟了、SCRM 里客户上周说了什么。通用 agent 面对的是文件和终端，不是你的订单、台账和会话记录。
> **写动作没有业务闸门**它的确认停在"这段改动要不要合"。报价该按哪张价格表、台账重复记了一条、补偿该按哪版政策，这些规则它不懂，出了事没记录可查。
> **没法给一个团队用**没有工作空间、租户隔离、额度和计费、运行监控。四个业务员一个主管一起用，华南就能看到华东；更没法卖。
> **不可评测、不会进化**没有案例集、判定器、Badcase 回流。好不好靠感觉，政策换版就引错，改了 prompt 不知道是好是坏。
> 通用 agent 解决的是"怎么跑起来"。一个产品要回答的是：**跑对了没有、谁来负责、出了事怎么查、能不能给团队用、能不能收钱。**Agent Runtime 只是第一周，后面十一周都在回答这些问题。

先看清我们要做什么：一个对话入口，能力按插件装，接的是公司自己的 ERP 和 SCRM，写动作经人确认才发生。下面十二个画面就是最终形态，点任意画面放大。

// 产品功能一览 · 跨境业务员的一天，它能接哪些活

### 一个跨境设备卖家的数字员工

它不是客服机器人，不替你和客户说话。它是坐在业务员身边的同事：查系统、算价格、出文件、盯进度，写动作经你确认才发生。下面这些活，12 周把它们一件件做出来。

- **一句话出报价单** "给 Jakarta 客户按 300 m³/h、扬程 40 m 出 X 系列报价"。它查规格、查库存交期、按报价规程算价，报价单 PDF 落到工作目录，你点确认台账才记上
- **做营销素材** 给型号和平台，出主图、场景图、A+ 模块、尺寸图，每张先过平台规范检查；卖点数字从规格工作簿取，不会编
- **新客户先摸底** 一份背调报告：这家公司是谁、做什么、以前有没有在我们这下过单、回款怎么样、公开信息里有什么风险，最后给一个付款条件建议
- **老板看销售过程有没有问题** 一句话让它翻 SCRM：这周的询盘哪些没人跟、谁回复慢、哪些线索该升级、哪些快丢了，出一张复盘表
- **看发货有没有滞留** 翻 ERP：哪些订单过了承诺日还没签收、物流停更多久了、按政策该不该给补偿方案，顺手建售后工单
- **文档、周报和重复的事** 技术方案书、合同草稿按模板出，数字全从系统取；每天早上新询盘和待跟进推飞书群，每周一出询盘复盘，不用再手工汇总

1.3 · 本地系统

业务员每天打开的两个系统：ERP 和 SCRM

数字员工接的就是这两个。课程项目接不到企业真实系统，所以本地模拟，会出错、记真账；飞书和搜索 API 真实接入。

ERP · Enterprise Resource Planning · 企业资源计划

### 管"货和钱"的系统

公司内部的账本。产品有哪些型号、每个型号的规格；仓库里有多少货、什么时候能交；客户下了哪些订单、发了没有、物流到哪了；报价记在台账里、售后开了哪些工单、备件怎么计费；客户之前付过多少钱、有没有欠款。业务员查库存交期、查订单物流、记报价台账、建工单，都在 ERP 里。常见的产品是用友、金蝶、SAP。

SCRM · Social CRM · 社交化客户关系管理

### 管"人和聊天"的系统

公司对外的客户本。每个客户是谁、联系人是谁、哪个业务员在跟；客户发来的每一条询盘；B2B 平台、邮件、WhatsApp 上的聊天记录全部归档在这里；业务员每次跟进写一条记录；线索按冷热分级。业务员看客户聊过什么、写跟进、判断哪些线索快丢了，都在 SCRM 里。常见的产品是销售易、纷享销客、企业微信的客户管理。

为什么 agent 要接这两个：

一句话任务背后要查的数据都在这里，办完的事也要写回这里。不接 ERP 它不知道订单到哪了，不接 SCRM 它不知道客户上周说了什么。

业务员、主管、老板，各自卡在哪

同一件事，三个人要的东西不一样。产品要同时解决这三个人的问题，不是只给业务员省时间。

- 业务员

2.4 · 为什么是 personal agent

两种产品都用大模型，站的位置不同

客服机器人站在客户面前；personal agent 站在业务员身边。

不做

### 客服机器人

实时多轮，客户会施压，几秒内决定承诺什么。难点是对话控制、承诺边界、人工接管时谁说了算。

做

### personal agent

客户消息先到业务员，agent 起草，业务员确认。难点是把事办对：查全、引用准、算对、该停的时候停、办了的事有据可查。三个理由：主管要的是能办事的同事；业务员确认这一步天然是闸门，查询可以完全放开；Codex 和 Accio Work 已经验证过这个形态：输入框上一个"询问 / 自动"开关，能力按插件装。

# 深维工作台：一个对话，一个 agent

Chapter 3 · 产品定义 · 带 UI 的 PRD

03

产品只有一个人机界面：业务员和它的 agent 对话。没有角色、没有"员工团队"，所有能力都在工具层和技能层，按插件安装。它接的是公司自己的 ERP 和 SCRM。

// 一句话定义

一个

只会做跨境设备生意的 Personal Agent

：一句话任务、过程可看、写动作经人确认、能后台跑、能定时跑、能装插件、按额度计费。

形态照 Codex 和 Accio Work，业务照深维设备的出海团队。下面五层是它的骨架，八个插件是它的手脚。

3.1 · 五层结构

对话与运行时、工具、技能、知识、平台

对话是唯一入口；工具按插件打包；技能把工具串成有步骤的工作流；知识带版本；平台让它能多人用、能上线、能收钱。

| 层 | 是什么 | 例子 |
| --- | --- | --- |
| 对话与运行时 | 唯一入口是对话。每条请求起一个 Run，agent 在循环里选工具、调用、观察、继续，直到停止。流式回传过程。需要人时挂起 | 会话页是对话，Run 详情是一次 Run 的轨迹与产物 |
| 工具层 | 原子动作，每个标读或写、权限档位。按插件打包：一个插件 = 一组工具 + 若干技能 + 一个连接 | ERP 连接器：查规格、查库存交期、查订单、查物流、查客户与回款、写报价台账、建工单。SCRM 连接器：查客户、读会话记录、查询盘、写跟进、更新线索分级、导入会话记录。通用：检索知识库、搜索抓网页、沙箱执行、生成文件、起草消息、发飞书、建定时任务 |
| 技能层 | 把工具组合成有步骤、有约束、有产出格式的工作流，相当于 Codex 的 skills | 选型推荐、报价单、客户背调、技术方案书、合同草稿、询盘回复、告警诊断、备件询价与工单、经营周报、询盘复盘、出口合规检查、营销图 |
| 知识层 | 业务员自己的文档，通过检索工具进入上下文 | 产品手册、政策、规程、模板等资料，带版本与生效状态 |
| 平台层 | 多人用、跑后台、扛并发、上线、收钱 | 工作空间与成员、队列与 Worker、缓存与限流、监控、部署、套餐与额度 |

3.3 · 读是自由的，写要过闸

产品最重要的一条规则，从 W2 第一个工具起执行

读的全自动；写的先变成变更集等你确认；价格由规程算；跨空间一律 404。

!

读是自由的，写要过闸。

agent 的产出先是草案。写动作先以变更集出现在对话里，业务员点确认才发生。输入框上的"询问 / 自动"开关是全局默认：询问模式所有写都问；自动模式内部写不问、对外写仍问。没有审批环节，每一次确认、修改、拒绝都进事件日志。

— 从 W2 第一个工具起执行；对应 Codex 的 diff 审核后才 merge、Accio 的询问 / 自动

| 跨工作空间的任何访问 | 禁止 | 返回 404 |

三条不变式

### 从第一周就成立

- 模型看到的每条上下文都已记录在事件日志里，任取一步都能复原当时发给模型的完整请求
- 工具调用先落日志再执行，被拒的、等确认的也记
- 价格由报价规程计算，报价工具没有自由金额参数；超权限那一档必须带理由

3.5 · 用 Jakarta 那单把页面串起来

一次 Run 走完六步

点修改会生成变更集 v2，v1 失效；价格这类来自规程的字段不可改。没有任何人替他批，也不需要。

1

**起 Run。**任务中心输入工况，模式开关在"询问"，跳到会话页，右栏出现轨迹：解析工况参数。

2

**先看客户。**调 SCRM 查 Jakarta：新客户，两轮会话，没有历史订单。agent 提一句"建议先做背调"，然后继续。

3

**查。**选型推荐技能依次调用查规格、查库存交期、检索知识库。折叠行自动执行，不问人。

4

**结论。**推荐 X200-Pro，引用选型指南 3.2。价格按报价规程算出，有效期 30 天。

5

**变更集。**三个写动作：报价单 PDF 放工作目录、写 ERP 报价台账、SCRM 写跟进。Run 进入等待确认，Worker 释放。

6

**确认。**业务员点确认全部。ERP 账本多一条报价，SCRM 多一条跟进，PDF 自己发给客户。终态 resolved。
