## 二、依赖方向（统一 SDD 10.1）

`core` 为纯数据结构，不依赖 adapter / codec；`detect` 为纯函数（只依赖 core）；`codec` 依赖 core + stream + usage（归一化单一真源，见偏差 11）；`adapter` 依赖 core + stream + usage + errors；`usage` / `cost` / `telemetry` 依赖 core；`errors` 依赖 core + security（遮蔽单点）；`security` 不依赖业务包；`routing` 依赖 core + detect；`registry` 依赖 routing（`FailureKind` 单一真源）；`policy` 依赖 core；`server` 装配以上全部。依赖单向下沉、无环。

## 四、与统一 SDD 的偏差及理由

1. **适配器已引入官方 SDK（第二轮落实，本条初版的「不引 SDK」口径作废）**：`openai-go/v3`（OpenAI + 7 家兼容端点，Tier 1：SDK typed 构造 + SDK 流式执行）、`anthropic-sdk-go`（Claude，Tier 1）、`google.golang.org/genai`（Gemini，Tier 2：typed 构造/解析 + 既有 HTTP 执行——genai 流解析与执行耦合、错误体/usage 原文在 SDK 内丢失，降级有据）。⚠️ xAI **无官方 Go SDK**（检索核实 `xai-org/xai-sdk-go` 不存在）⇒ Grok 走 Responses REST（3.6 优先级②，SDD 10.3 已事实修正）。SDK 序列化合法差异（空 messages 整键省略、SDK 请求头、键序规范化）已在测试报告登记。
2. **codec 只保留 chat / responses 两个包**（对照 10.2 的 codec/anthropic、codec/gemini、codec/ollama）：Anthropic / Gemini / Ollama 的形状转换并入各供应商适配器（统一 SDD 2.2「每家的请求构造、响应解析由该适配器独立承载」）；入站只有 Chat / Responses 两种形状（1.2），codec 只服务入站双模式与客户端侧帧编码。
3. **错误分类按九值枚举**（7.1 正文说「七类」，2.3 错误表列九行）：`context_exceeded` / `content_policy` 独立成类 —— 7.4 按失败类型分链需要它们独立。
4. **配置 schema 增加 `fallback_chains`**（7.4 的按失败类型降级链需要承载，9.2 schema 未列）：键为失败类型、值为有序端点名数组；未知字段仍拒绝。
5. **契约层字段增补**（承载统一 SDD 已要求但 3.1 结构未列的语义）：`core.Request.PromptCacheKey`（3.5 始终透传）、`core.OutputItem.{EncryptedContent, ThinkingSignature, ReasoningText}`（3.4/4.2.5 语义字段必须保留）、`core.Usage.CacheReadMode`（5.7 缓存命中档位取价）、`core.ErrorDetail.Code`（对外错误码 `unsupported_capability` / `model_not_found` 等）。
6. **`SupportsPreviousResponseID` 由适配器声明**（3.5），`routing` 不建 capability 表（10.2 目录中的 routing/capability.go 不再单列）。
7. **遮蔽实现单点在 `internal/security/redact.go`**（10.2 在 errors/ 与 security/ 两处列 redact.go）：防双真值，`errors` 序列化复用它。
8. **`config/rates.json` 由 5.4 费率总表逐行转录，对账由单测承担**（每行逐价断言、注释标出处小节）；md → json 生成脚本列入后续项。
9. **可观测不引入 OTel SDK**：属性名集中在 `internal/telemetry` 单一映射层（6.1），span 抽象 + InMemory exporter 供测试断言（SC-3）；OTLP 导出器列入后续项。
10. **`specs/001` 的 Python 技术栈表述作废**：统一 SDD 0.2 声明其为唯一设计口径且 `go.mod` 为 Go 1.27，实现语言 Go。
11. **codec 依赖 `usage`**（对照 §二初版「codec 依赖 core + stream」）：`ParseChunk`/`ParseEvent` 产出 `core.Usage`，4.4 逐家归一口径的单一真源是 `usage.Normalize`——本地再实现一份即口径双真值（SDD 风险表点名的坑）；依赖仍单向无环。
12. **适配器增加 `DegradationAware` 可选接口**（`BuildRequestWithDegradations`）：降级发生在请求构造期，而 `ParseResponse(res, body)` 看不到请求侧事实 ⇒ 降级记录随 `Outbound` 返回、由上层合并进 `x_gateway.degradations[]`（SDD 3.4）。
13. **凭据注入通道**：`Adapter.StreamStart` 内部发 HTTP 且 `Outbound.Headers` 不含凭据值 ⇒ server 按 `AuthScheme` 构造鉴权头，经请求上下文 + `RoundTripper` 在出网点注入（不改适配器、不在函数间传递明文，规则 21）。
14. **运行时配置走 `cmd/gateway` 标志**（cancel_grace / 断连检测上界 / 治理参数 / 环回放行）：`config`（registry JSON）保持 9.2 schema 不扩键（未知字段拒绝口径），运行期行为参数与注册数据分离。
15. **`config/rates.json` 对账由单测承担**（见 8）；`RateSnapshot` 带 `-cn-fixed` 后缀（5.3 要求记录 holiday_calendar 取值）。
16. **DeepSeek / Kimi / 智谱 / MiMo / Qwen 出站改走 Chat Completions**（原按 3.6 优先级②走 Responses）：真实 API 方法 A/B 裁定（`20261114-realkeys-mimo-flash-bench/raw/method_ab.json`）——五家 `/chat/completions` 端点兼容性与功能全面胜过 `/responses`（智谱无 /responses 端点、Qwen/MiMo 的 tools 或 stream 在 Responses 法丢失，Chat 法 4/4 全通）⇒ 出站统一 Chat；OpenAI key 区域封锁无法实测，保留 Responses（其官方原生即 Responses，SDD 3.6 优先级②）。SDD 3.6 适配器清单已同步。
17. **Frame 增 `ThinkingSignature` 槽位**（3.7 结构增补）：流式 `signature_delta` 打通全链路（帧 → OutputItem → Responses `signature` 出口无损 / Chat 出口 degradation 标记），入站回传方向同步解析；SDD 3.7 已同步。
18. **归一化按真实样本修正 3 处**（SDD 4.4.2 已同步）：Grok Chat 缓存命中两形态取其一（`cached_prompt_text_tokens` 旧 / `prompt_tokens_details.cached_tokens` 现行）、Qwen 原生读 `prompt_tokens_details.cached_tokens`、MiMo 读 `completion_tokens_details.reasoning_tokens`。
