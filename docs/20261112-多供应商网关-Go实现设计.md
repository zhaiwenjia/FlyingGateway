## 一、目标与范围

### 1.0 本文档的性质（先说清哪些是查来的、哪些是本仓自定）

> **本文档的设计决策全部是本仓自定**，不是任何供应商或开源项目的既有方案。
> 文档中引用的「调研 §x.y」是**来自搜索的事实**（有一手源 URL）；其余章节的
> 类型定义、模块划分、识别顺序、转换规则、目录结构**都是本项目自己的设计**。
> 标注约定：**【调研】** = 有出处的外部事实；**【本仓自定】** = 本设计的选择。

**已有公开参照，可作为设计合理性佐证**（**【调研】**，非本仓独创）：

- **Open Responses** 规范（`https://www.openresponses.org/specification`）—— 一个**开源的、厂商中立的**「以 OpenAI Responses API 为基础」的统一 LLM 接口规范，目标正是「One spec, many providers」。⇒ 本设计的「规范模型 + 适配器」思路与业界方向一致；但**本设计的具体类型字段不是照抄它**。
- agentgateway（Solo.io / Linux Foundation）—— LLM + MCP + A2A 三协议统一的代理数据面，证明「多协议适配器」形态可行。
- MaaS Usage 规格（`https://wener.me/notes/ai/maas/spec/usage`）—— 给了跨供应商 usage 归一化的字段建议（含 `input_tokens` / `output_tokens` / `cached_tokens` / `cache_write_tokens` / `reasoning_tokens` / `provider_usage` / `estimated`），本设计的 `core.Usage` 与它口径对齐。

### 1.1 一句话目标

给定 **base URL + model name**，自动识别供应商 ⇒ 自动套用该供应商的请求 schema ⇒ 收到回复后归一化成**统一格式**供本地智能体消费 ⇒ **精确记录输入 / 输入缓存命中 / 输出**三类 token。

### 1.2 老宅拍板的三条硬约束

| 编号 | 决策 | 落地含义 |
|---|---|---|
| D1 | **同时支持 OpenAI Chat Completions 与 OpenAI Responses 两种模式** | 对外（入站）**两套 API 形状**都要有：`POST /v1/chat/completions` + `POST /v1/responses` |
| D2 | **Claude 肯定要使用自己的格式** | 出站（上游）**各家原生形状**：Claude 走 `/v1/messages`，⛔ 不用 OpenAI 形状硬转 |
| D3 | **统一输出以 OpenAI Chat Completions 为基准** | 内部规范模型以 OpenAI 骨架为基线，但必须是**超集**（承载 reasoning / signature / cache_control / finish_reason 超集） |

### 1.3 不做什么（non-goals）

- 不做 MCP / A2A 协议网关（调研已覆盖语义，实现另立 spec）。
- 不做语义缓存 / prompt cache 命中优化（只**计量**缓存 token，不主动优化）。
- 不做计费报表 / 预算阻断的完整实现（先保证 usage **计量准确**，治理另议）。
- 不做多租户虚拟密钥体系（先保证凭据只从**来源引用**读取，不落明文）。
- 不做前端。

### 2.1 为什么是「适配器」而不是「一套 struct」

调研已证：usage 字段在**缓存层级、输入语义、流式携带**三处不一致；响应体在**输出结构、终止原因、推理位置**三处不一致。⇒ **每个供应商一个适配器**，接口统一、内部自便。

## 三、核心类型设计

> Go 伪代码，仅示意形状与字段名（实施时按最终包名调整）。

### 3.1 内部规范模型（承载双模式）

```go
// core 包的规范模型：OpenAI 骨架的超集
type Request struct {
    Model    string
    Messages []Message       // Chat 形状的消息序列
    // Instructions 是 Responses 形状的系统提示；Chat 侧由 messages[0] 承载
    Instructions string
    Tools      []Tool
    ToolChoice *ToolChoice
    MaxOutputTokens int
    Temperature *float64
    TopP       *float64
    Stop       []string
    Reasoning  *ReasoningConfig
    Stream     bool
    // CacheControl 是 Anthropic 的缓存断点（Chat 形状无对应物）
    CacheControl *CacheControl
    // PreviousResponseID / Conversation 是 Responses 的服务端会话态
    PreviousResponseID string
    Conversation        string
    // Extra 承载供应商特有的非标准参数（enable_thinking / prompt_cache_options / ...）
    Extra map[string]any
}

type Message struct {
    Role    string          // system / user / assistant / tool / developer
    Content []ContentPart   // 统一的多模态 part
    // ReasoningContent 承载各家推理文本
    ReasoningContent string
    // ThinkingSignature 承载 Anthropic thinking.signature（不可压平，D2）
    ThinkingSignature string
    // EncryptedContent 承载 OpenAI reasoning item 的 encrypted_content
    EncryptedContent string
    ToolCalls  []ToolCall
    ToolCallID string        // role=tool 时
    Name       string
}

type ContentPart struct {
    Type     string          // text / image_url / input_text / input_image / file / ...
    Text     string
    ImageURL string
    MIMEType string
    Data     string          // base64
}

type ToolCall struct {
    ID       string
    CallID   string          // Responses 的 call_id（与 ID 不同）
    Name     string
    Arguments string         // JSON 字符串
    Type     string          // "function"
}

type Response struct {
    ID     string
    Model  string
    Status string             // completed / failed / incomplete / cancelled / in_progress / queued
    // OutputItems 是异构联合，承载 Chat 的单条 message 与 Responses 的多 item
    OutputItems []OutputItem
    // Text 是便捷字段（对应 Responses 的 output_text）
    Text string
    FinishReason string       // 超集枚举（见调研 §4.2）
    Usage *Usage
    Error *ErrorDetail
}

type OutputItem struct {
    Type    string           // message / reasoning / function_call / ...
    ID      string
    Role    string
    Content []ContentPart
    // Reasoning 相关
    Summary  []SummaryPart
    // FunctionCall 相关
    CallID    string
    Name      string
    Arguments string
    // Refusal
    Refusal string
}
```

### 3.2 统一 Usage（老宅点名的三类 token 都要准）

```go
type Usage struct {
    // ---- 老宅要求的三项 ----
    InputTokens        int64   // 总输入 token（对 Anthropic 系 = input + cache_creation + cache_read 合成）
    CacheReadTokens    int64   // 输入缓存命中（从缓存读取）
    OutputTokens       int64   // 输出 token

    // ---- 补充维度（必需，否则成本算不准）----
    CacheWriteTokens   int64   // 写入缓存（Qwen / Kimi / Claude / OpenAI 都有）
    InputTokensUncached int64  // 未缓存的新增输入
    ReasoningTokens    int64   // 推理 token
    TotalTokens        int64   // provider 原报的总值（保留，不重算）
    ToolUsePromptTokens int64  // Gemini 的 tool_use_prompt_token_count

    // ---- 可信度标记 ----
    Estimated bool     // true = usage 缺失/被截断，用估算值
    // ---- 原始数据 ----
    Raw json.RawMessage // provider 原始 usage JSON（账单核对 / 协议排障）
}
```

**字段口径的三条硬规则**（来自调研 §4.1 / §4.3）：

1. `InputTokens` 是**总输入**。Anthropic 系必须合成：`input_tokens + cache_creation_input_tokens + cache_read_input_tokens`（官方公式）。
2. `CacheReadTokens` 与 `CacheWriteTokens` **分列**。只统计命中量会**低估写入成本**（Claude 5m 写入 ×1.25、1h ×2）。
3. `Estimated` 必须有。流中断时末帧 usage 可能不到（Kimi 原文、OpenAI 官方注释都明说），⇒ **未收到 usage 不代表不计费**。

## 四、供应商识别（base URL + model name）

### 4.1 识别顺序（**host 优先**）

调研已证前缀有歧义（`deepseek-r1` 既是 DeepSeek 官方模型也是 Ollama 常见本地模型名；`qwen2` 同理）⇒ **base URL 优先级高于 model name**。

```
1. 解析 base URL → host + path
2. host 精确匹配规则表 → 命中则 provider 确定，confidence=high
3. host 未命中：
   3a. model name 前缀匹配 → provider 确定，confidence=medium
   3b. 都未命中 → provider=Unknown，shape=OpenAIChat（兜底），Fallback=true
4. path 后缀判定 shape：
   /chat/completions        → OpenAIChat
   /responses               → OpenAIResponses
   /messages                → AnthropicMessages
   /v1/text/chatcompletion_v2 → 原生（MiniMax V2）
   :generateContent / :streamGenerateContent → Gemini 原生
   /api/chat                → Ollama 原生
```

### 4.2 host 规则表（数据源：调研 §5.1）

| 规则（host 后缀 / 精确匹配） | Provider | Shape |
|---|---|---|
| `api.openai.com` | OpenAI | Chat 或 Responses（按入站模式） |
| `api.anthropic.com` | Anthropic | **AnthropicMessages** |
| `api.deepseek.com` | DeepSeek | Chat 或 Responses |
| `api.moonshot.cn` / `.ai` | Moonshot | Chat 或 Responses |
| `open.bigmodel.cn` | Zhipu | Chat |
| `*.maas.aliyuncs.com` / `dashscope*.aliyuncs.com` | Qwen | Chat 或 Responses（原生 text-generation 单独处理） |
| `api.minimax.cn` / `.io` | MiniMax | Chat / AnthropicMessages / 原生 V2 |
| `api.xiaomimimo.com` / `batch-api-cn.*` / `token-plan-cn.*` | Xiaomi | Chat |
| `api.x.ai` | XAI | Chat（legacy）或 Responses（推荐） |
| `generativelanguage.googleapis.com` / `aiplatform.googleapis.com` | Gemini | 原生 generateContent |
| `localhost:11434` / `127.0.0.1:11434` | Ollama | 原生 `/api/chat` 或 `/v1/chat/completions` |

⚠️ **两条实现约束**（来自调研）：

- **Qwen 的地域绑定**：API Key 与地域强绑定，跨地域调用返回 401 `invalid_api_key` ⇒ 识别时**不能只看 host 后缀**，还要看 WorkspaceId 与地域的组合；识别失败时应给出**明确报错**而非默默换端点。
- **MiMo 的非标准鉴权头**：`api-key:` 而非 `Authorization: Bearer` ⇒ 鉴权注入按 provider 分派。

### 4.3 用户显式覆盖

允许调用方在请求里指定 provider（如 `X-Gateway-Provider: anthropic`）⇒ **显式指定优先于自动识别**。理由：自建代理 / 私有部署的 host 不可识别时，自动识别会落到兜底；显式指定让用户能覆盖。

## 五、入站双模式（D1）

### 5.1 两个入口的职责

| 入口 | 请求解析 | 响应序列化 |
|---|---|---|
| `POST /v1/chat/completions` | `codec/chat` ⇒ 规范 `Request` | 规范 `Response` ⇒ `chat.completion` / `chat.completion.chunk` |
| `POST /v1/responses` | `codec/responses` ⇒ 规范 `Request` | 规范 `Response` ⇒ `response` 对象 / `response.*` 事件 |

### 5.2 Chat ⇄ 规范模型

- **入站 Chat**：`messages[]` ⇒ 规范 `Messages[]`；`messages[0].role=system` ⇒ 规范 `Messages[0]`（**保留 system 角色**，不提升为 Instructions，转换在出站时做）。
- **出站 Chat**（对 OpenAI 形状供应商）：规范 ⇒ `messages[]`（system 消息还原成 `messages[0]`）。

### 5.3 Responses ⇄ 规范模型

- **入站 Responses**：`input[]` ⇒ 规范 `Messages[]`：
  - `input` 是字符串 ⇒ 规范 `Messages[0]{Role:"user"}`；
  - `input` 是 item 数组 ⇒ 逐 item 映射（`type:"message"` → Message；`type:"reasoning"` → Message{ReasoningContent, EncryptedContent}；`type:"function_call"` → Message{ToolCalls}；`type:"function_call_output"` → Message{Role:"tool", ToolCallID}）。
  - ⚠️ **`reasoning` item 的 `encrypted_content` 必须保留** ⇒ 规范模型有 `Message.EncryptedContent` 字段。
- **出站 Responses**（对有 Responses 的供应商）：规范 `Messages[]` ⇒ `input[]` item 数组。

### 5.4 两模式之间的转换代价（必须在设计里显式承认）

调研 §3.14 的结论直接约束实现：

| 方向 | 状态 |
|---|---|
| Chat → Responses | ✅ 无损（一条 message 拆成一个 item；`tool_calls[]` → `function_call` item，补 `call_id`） |
| Responses → Chat | ⚠️ **有损**：`encrypted_content` / `reasoning.summary[]` / 多 item 顺序 / `sequence_number` / 服务端会话引用会丢 |
| Anthropic → Chat | ⚠️ **有损**：`thinking.signature` 丢失 ⇒ **多轮带思考的对话功能降级** |

⇒ **设计要求**：当入站模式与上游能力组合会导致不可逆丢失时，**必须在响应里带一个显式标记**（如 `x_gateway.degradations[]` 或响应头 `X-Gateway-Degraded: thinking_signature`），⛔ **不许静默丢**。

理由（对齐本仓 `AGENTS.md` 规则 2「字段名不许撒谎」与规则 22）：静默丢字段 ⇒ 下游看到「模型没思考」而实际是「网关把签名扔了」⇒ 排障方向直接跑偏。

## 六、出站：供应商适配器（D2）

### 6.1 适配器接口

```go
type Adapter interface {
    // BuildRequest 规范 Request → 该供应商的请求体 + 路径 + 鉴权头
    BuildRequest(ctx context.Context, r *core.Request, res *Resolution) (*Outbound, error)

    // ParseResponse 供应商响应（非流式）→ 规范 Response
    ParseResponse(res *Resolution, body []byte) (*core.Response, error)

    // StreamStart 流式：返回帧迭代器
    StreamStart(ctx context.Context, r *core.Request, res *Resolution) (FrameIterator, error)

    // ParseUsage 从该供应商的 usage 结构归一化
    ParseUsage(raw json.RawMessage) *core.Usage
}
```

### 6.2 适配器清单（11 家 + 通用）

| 适配器 | 请求形状 | 流式形状 | usage 解析要点 |
|---|---|---|---|
| `openai_chat` | `/chat/completions` | `chat.completion.chunk` | `prompt_tokens_details.cached_tokens` + `cache_write_tokens` |
| `openai_responses` | `/responses` | `event: response.*` + `data:` | `input_tokens_details.*`；usage 在 `response.completed` |
| `anthropic_messages` | `/v1/messages` | `message_start`/`content_block_delta`/`message_delta`/`message_stop` | **`input_tokens` 是残值** ⇒ 须合成总输入；**无 `[DONE]`**；usage **累计** |
| `deepseek` | `/chat/completions` | 同 OpenAI Chat | `prompt_cache_hit_tokens`（顶层）或 `prompt_tokens_details.cached_tokens`（**二选一，不累加**） |
| `moonshot` | `/chat/completions` | 同 OpenAI Chat | `prompt_tokens_details.cached_tokens` + `cache_write_tokens` |
| `zhipu` | `/chat/completions` | 同 OpenAI Chat | ⚠️ 请求参数是 **`chunk_include_usage`** 不是 `include_usage` |
| `qwen_compat` | `/compatible-mode/v1/chat/completions` | 同 OpenAI Chat | `prompt_tokens_details.cached_tokens` + `cache_creation_input_tokens` |
| `qwen_native` | `/api/v1/services/aigc/text-generation/generation` | 须加头 `X-DashScope-SSE: enable`；帧 `data:{...}`（**无空格**）、**每帧带 usage**、**无 `[DONE]`** | `usage.input_tokens` / `output_tokens`（**与兼容模式字段名不同**） |
| `minimax_openai` | `/v1/chat/completions` | 同 OpenAI Chat | `prompt_tokens_details.cached_tokens`；`reasoning_split=false` 时思考在 `content` 的 `<think>` 里 |
| `minimax_anthropic` | `/anthropic/v1/messages` | Anthropic 事件 | `input_tokens` **也是残值**（与 Claude 同语义） |
| `xiaomi` | `/v1/chat/completions` | 同 OpenAI Chat | 末帧**自动**带 usage（无需开关） |
| `xai` | `/v1/chat/completions` 或 `/v1/responses` | 同 OpenAI | 与 OpenAI Chat 一致 |
| `gemini` | `:generateContent` / `:streamGenerateContent` | 逐帧 `GenerateContentResponse` | `usageMetadata.*`（**驼峰**）；`totalTokenCount` **含 thoughts/tool-use** |
| `ollama` | `/api/chat` | **`application/x-ndjson`**（一行一个 JSON），**无 `[DONE]`** | usage **平铺在顶层**：`prompt_eval_count` / `prompt_eval_cached_count` / `eval_count` |

⚠️ **DeepSeek 官方另提供 `/anthropic` 端点、智谱 / Kimi / MiMo / MiniMax 也提供 Anthropic 兼容端点**（调研 §1.2）⇒ 适配器可**复用 Anthropic 解析器**，但各家的 usage 语义仍需各自核对（尤其 MiniMax 的 `input_tokens` 也是残值）。

### 6.3 三个「必须独立处理」的坑（来自调研）

1. **Qwen 原生 SSE 必须加 `X-DashScope-SSE: enable`**，且帧格式是 `data:{...}`（冒号后**无空格**）⇒ SSE 解析器要容忍两种分隔。
2. **Ollama 原生流是 NDJSON**（`application/x-ndjson`），不是 SSE ⇒ 流式解析器要按 adapter 分派，不能全局假设 SSE。
3. **智谱的 `chunk_include_usage`** ≠ OpenAI 的 `include_usage` ⇒ 请求构造按 adapter 分派。

## 七、流式与取消

### 7.1 流式帧的统一抽象

内部用**供应商无关的帧类型**，各 adapter 负责「供应商帧 → 内部帧」与「内部帧 → 入站模式帧」：

```go
type Frame struct {
    Kind      FrameKind  // TextDelta / ReasoningDelta / ToolCallArgsDelta / Usage / Lifecycle / Done / Error
    Text      string
    Reasoning string
    ToolCallID string
    Arguments string
    Usage     *core.Usage
    Status    string
    Seq       int64
}
```

⇒ 一套流解析核心 + 每家一个「帧解码器」+ 两个「帧编码器」（Chat 模式 / Responses 模式）。

### 7.2 取消语义（承接本仓 `specs/001` 的流式取消设计）

沿用已定的口径（见 [调研 §七 的姊妹文档](../docs/20261112-多供应商API-Schema-调研-接口与用量口径.md) 与 `specs/001`）：

- 客户端断连 ⇒ **取消上游请求**（关闭连接 / cancel context）。
- 取消**不算错误**：usage 里标记 `Estimated=true`（因为末帧 usage 拿不到）。
- **取消后不再发任何帧**；已发出的帧由客户端自行丢弃。
- **取消后不得触发降级或重试**（late cancel race）。
- Trace / 日志中区分取消原因（`client_disconnect` / `upstream_error` / `timeout` / `shutdown`）。

⚠️ **Responses 模式额外注意**：取消时**可能收不到 `response.completed`** ⇒ 客户端拿不到最终 usage ⇒ 网关应在**取消路径上自己补一个终止帧**（含 `Estimated=true` 的 usage），让客户端知道「结束了，且 token 数是估算的」。

### 7.3 Responses 流式的容错（来自调研 §3.1 的已知偏差）

必须容忍：
- 后端**不发 `[DONE]`**（vLLM / llama.cpp）⇒ 以终态事件（`response.completed`/`failed`/`incomplete`）或连接关闭判定结束。
- 后端**跳过 `response.output_item.added`** 直接发 delta ⇒ 解析器不假设事件顺序。
- 事件**乱序 / 缺号** ⇒ 用 `sequence_number` 检测但不因此中断（记录告警）。
- **未知事件类型** ⇒ 忽略但记录（规范原文：「your code should handle unknown event types gracefully」）。

## 八、可观测（与本仓既有设计衔接）

- 每次上游执行一个 span（OTel GenAI 语义约定口径）。
- span 属性：`gen_ai.operation.name`（`chat`）/ `gen_ai.provider.name` / `gen_ai.request.model` / `gen_ai.response.model` / `gen_ai.request.stream` / `gen_ai.usage.input_tokens` / `gen_ai.usage.output_tokens` / `gen_ai.response.status`。
- ⚠️ **取消 ⇒ `gen_ai.response.status="cancelled"`，span status 留 `Unset`、不设 `error.type`**（取消不是错误）。
- 额外自定义属性（`gateway.*` 命名空间，⛔ 不塞进 `gen_ai.`）：`gateway.provider` / `gateway.shape` / `gateway.detect_confidence` / `gateway.fallback` / `gateway.degradations[]` / `gateway.cache_read_tokens` / `gateway.cache_write_tokens` / `gateway.usage_estimated`。
- **usage 缺失要有指标**：`gateway.usage_missing_rate`。

### 10.2 转换测试（双模式）

| 测试 | 断言 |
|---|---|

### 10.3 端到端测试

- 用 **httptest** 起本地假供应商，返回**真实录制的响应样本**（⛔ 不用手写合成 JSON —— 本仓口径）。
- 流式：断言帧序列、末帧 usage、终止哨兵。
- 取消：客户端断连 ⇒ 断言上游连接被关闭、无后续帧、无重试。

### 10.4 断言有效性自检（规则 22）

每条断言落笔前先造两个样本：**恒真样本**（错误实现也通过）与**恒假样本**（错误实现会红）。典型：
- 断言「Anthropic 归一后总输入 = 200050」⇒ 写一版「直接取 `input_tokens`」的错误实现，确认它**红**。
- 断言「取消后上游被关闭」⇒ 写一版「不调 `aclose()`」的错误实现，确认它**红**。

## 十一、风险与未决事项

| 编号 | 风险 / 未决 | 缓解 / 需确认 |
|---|---|---|
| R1 | **Responses ↔ Chat 的有损转换**（`encrypted_content` / `thinking.signature` 丢失） | 显式打 degradation 标记，⛔ 不静默丢；需老宅确认标记的呈现方式（响应头 vs 响应体字段） |
| R2 | **服务端会话态**（`previous_response_id`）只有 OpenAI 真支持 | 网关要么自建 `conversation` 映射，要么降级为客户端全量历史；**需老宅定产品口径** |
| R3 | **`usage` 口径随供应商与模式漂移**（11 家 × 2 模式 ≈ 22 套） | 归一化器 + 口径单测逐家钉死；字段名集中在 `core/usage.go`；升级供应商 SDK 时跑一次口径回归 |
| R4 | **Qwen 原生 / Ollama 原生 / Gemini 原生** 三家非 SSE 或非 OpenAI 形状 | adapter 分派流式解析器；⛔ 不全局假设 SSE |
| R5 | **供应商 API 变更**（如 MiniMax 移除 GroupId、xAI 把 Chat 标 legacy） | host/前缀规则表做成**数据驱动**（配置文件），不硬编码在逻辑里；规则表带「最后核对日期」 |
| R6 | **xAI 官方文档域名从本机不可达**（调研已标注） | xAI 适配器的 usage 字段以官方 SDK proto 为准；实施时若仍不可达，标注为「按 SDK proto 实现，待 REST 侧实测」 |
| R7 | **代码落点未定** | 本设计不绑定路径；包名映射表见第九章，实施时一次性决定 |
| R8 | **成本核算精度** | provider 自报 token 可能不准（arXiv 2611.08684 实测 vLLM 漏掉 1/3–1/2）⇒ 网关侧 `Usage` 标 `Estimated` 且保留 `Raw`，**不把 provider 自报值当账单真值** |

## 十二、与本仓既有工作的衔接

- 本仓 `specs/001-网关能力分层与流式取消/spec.md` 是 **Python 版**网关的规格（httpx + FastAPI + Pydantic + OTel）。
- 本设计是 **Go 版**、面向**多供应商 + 双模式**的独立设计。两者**共享**流式取消语义与 OTel 口径，但**不共享代码**。
- ⚠️ 二者的**取舍不一致**，实施时不要混用：
  - 本仓 `specs/001` 假定「统一格式 = OpenAI Chat Completions」；本设计因 D1 增加了 Responses 模式 ⇒ **规范模型必须升级为能承载两种形状的超集**。
  - 本仓 `specs/001` 的 provider 层是「配置驱动的一组端点」；本设计是「**按 base URL + model 自动识别**」⇒ 识别层是新增的核心。
- 迁移建议：**若 Go 版落地，Python 版的 `specs/001` 标记为「已被 Go 版取代」或保留为「Python 参考实现」**，二者不要同时演进（规则 31：单一数据源 / 避免双份真值）。
