# 20261114 超高并发等价模拟：FlyingGateway vs LiteLLM（真打 10 万级在途）

> 等价模拟：假上游把每个请求按住 30s，让 1k / 5k / 10k / 25k / 50k / 100k 档的目标并发**同时在途**，
> 对比 FlyingGateway（本仓 Go 网关）与 LiteLLM 的资源曲线、拒绝语义与恢复力。

---

## 一、问题与方法

### 1.1 问题

单进程开源 LLM 网关在**超高在途并发**（数万到十万级长连接，每条被上游按住 30s）下的表现：
- 各档能否达成目标在途、成功率如何；
- 每 1k 在途的 RSS / fd 成本与外推；
- 风暴过后的恢复力；
- 极限档的拒绝语义（谁先崩、崩成什么样）。

对比对象：FlyingGateway（Go，本仓）与 LiteLLM（Python/uvicorn，1.83.9）。

### 1.2 等价模拟与等价性边界

真实 LLM 请求的在途时长 = 模型生成时长（数秒到数十秒）。等价模拟用**假上游按住连接 30s** 复现
「长连接在途」：客户端按爬坡速率发起请求，假上游对 `ultra-hold` 请求先回响应头 + 首个 SSE 块
（TTFB = 网关转发开销，有意义），再按住 30s 才收口 ⇒ 连接在途时长 = 30s，同时在途数逼近目标档。

**等价性边界（诚实声明）**：
1. **只等价「连接级在途」，不等价「模型级负载」** —— 假上游不真正推理，故 CPU / 内存里
   模型权重、KV cache、批调度等真实推理侧成本**不在测量范围**；本测聚焦**网关代理层**的
   连接 / 内存 / fd 成本与并发处理。
2. **单机环回**：客户端、网关、假上游同机，走 127.0.0.1 环回 ⇒ 无真实网络延迟 / 丢包 / NAT。
   TTFB 是纯软件栈转发开销，不含 WAN。
3. **流式为主**：风暴用 `stream:true`（首字节早发测 TTFB、按住测在途）；恢复探针用非流式短请求。
4. **资源口径**：RSS/fd 是**进程级**快照（`ps`/`lsof`），含 Go/Python 运行时基线；不拆到每请求对象。
5. **公平性（同风暴强度）**：两网关用**同一爬坡速率**（ramp=2000/s）与同一假上游，风暴强度一致。
   LiteLLM 各档「达成在途」偏低是其**真实突发承受力**（Python/uvicorn 单 worker 突发 accept ≈ 200/s，
   连不上的被 RST）—— **非人为设限**。若把爬坡调到 LiteLLM 跟得上的速率（如 200/s），其可持有在途会升高
   （Little 定律 ≈ accept率×hold），但仍远逊网关、且 TTFB ~700ms、每连接 RSS ~3× 是 Python 固有成本、与爬坡无关。
   本测保留同一爬坡以回答「同风暴下谁先崩」（见 3.3）。

### 1.3 为什么用多端口而非多环回 IP（环境约束）

任务书原设想「多环回 IP 乘算」（客户端 `net.Dialer{LocalAddr}` 绑 127.0.0.x、7 源 IP × 16384 ≈ 114k）。
实测本机：**lo0 只有 127.0.0.1，绑定 127.0.0.2 报 `can't assign requested address`；加环回 alias 需
`sudo`，而 `sudo -n` 要密码（非交互不可用）⇒ 无法配多环回 IP。** 故客户端 / 上游的端口乘算改走
**多端口**（同一 127.0.0.1 上多个 dstPort，各自独立临时端口空间），见下节。

## 二、系统天花板与 fd 预算账

### 2.1 实测系统参数

| 项 | 值 | 来源 |
|---|---|---|
| fd 软上限（ulimit -n） | 1,048,575 | `ulimit -n` |
| 每进程 fd 硬上限 | 245,760 | `kern.maxfilesperproc` |
| 系统 fd 总上限 | 491,520 | `kern.maxfiles` |
| 临时端口区间 | 49152–65535 = **16,384** | `net.inet.ip.portrange` |
| accept 队列 | **128** | `kern.ipc.somaxconn` |

### 2.2 fd 预算账（每 100k 在途）

每条在途请求 = 1 条客户端连接 + 1 条网关→上游连接：

| 进程 | 每连接 fd | 100k 在途 | 每进程上限 245,760 |
|---|---|---|---|
| 客户端 ultraload | 1 | 100k | 内 |
| 网关（入站+出站） | **2** | **200k** | 内（紧） |
| 假上游 | 1 | 100k | 内 |

合计约 **400k** < 系统 `kern.maxfiles` 491,520 ⇒ **fd 预算不构成 100k 瓶颈**（实测 fd/连接：
网关 ≈ 2、上游 ≈ 1，见数据表）。

### 2.3 真正的天花板：出站本地端口（实测关键发现）

⭐ **实测决定性结论**：把客户端用**显式非临时源端口**（20000–49151，绕开临时池）把并发推过 16384 后，
网关在 **~16384 处划线** —— 25k 档 hold=30 实测 `200=16302, 502=8484`，即网关成功在途封顶 ≈ 16384，
溢出的 8484 个返 **502**。

**机制**：网关出站连接的**本地源端口 bind 是排他的**（Go `net.Dialer` 默认不设 SO_REUSEADDR）⇒
单源 IP（127.0.0.1）下，网关→上游的**并发连接数 = 可用临时源端口数 = 16384**。即便假上游监听
8 个端口（9102–9109）、网关 round_robin 到 8 个 dst，**本地源端口不按四元组复用 ⇒ 8 端口并不能乘算**
（实测 25k 档只成功 16302，非 8×16384）。

**推论**：
- **FlyingGateway 单进程单源 IP 的在途上限 = 16384**（出站本地端口墙），与 fd 预算无关。
- 客户端能推得更高（显式端口 23741+ 并发，证明瓶颈在网关、非客户端）。
- **100k 在途在本环境到不了**（需多源 IP / SO_REUSEPORT，见「部署建议」）⇒ 按红线如实记，不伪造。

### 3.3 「极限档拒绝语义」：谁先崩、崩成什么样

| | FlyingGateway | LiteLLM |
|---|---|---|
| 成功在途封顶 | **~16–17k**（出站临时端口墙 16384） | **~2k**（Python/uvicorn 突发 accept 上限） |
| 超出时的行为 | **优雅 502**（明确 bad-gateway，进程存活） | **连接 reset + 大量客户端失败**（重置连不上的连接） |
| 进程是否崩溃 | 否（100k 档后恢复探针仍 200，123ms） | 否（存活但严重退化，恢复 4.7s） |
| 拒绝语义 | **显式、干净**（502 与成功分流） | **隐式、脏**（RST 丢连接，成功率掉到 2%） |

⭐ 关键差异：FlyingGateway 在端口墙处**优雅拒绝（502）并保持可用**；LiteLLM 在 ~2k 就**大量 RST 丢连接**、
成功率暴跌到 2%、且事后恢复需数秒。**先崩的是 LiteLLM（突发承受力），且崩成「静默丢连接」而非显式拒绝。**

## 四、资源成本与外推

### 4.1 每 1k 在途成本（干净区 1k–10k，网关 100% 达成）

| 指标 | FlyingGateway | LiteLLM | 倍数 |
|---|---|---|---|
| RSS / 成功连接 | **~146 KB**（163MB/1k、1459MB/10k 线性） | **~450 KB**（490MB/1062、868MB/2000） | LiteLLM ≈ 3× |
| fd / 连接 | **2.00**（2011/1k、20011/10k 线性） | ~2.1–2.6 | 相当 |
| TTFB P50（转发开销） | **1.7–2.4 ms** | **654–721 ms** | LiteLLM ≈ **300–400×** |

- **fd 线性**：网关 2 fd/连接（1 入站 + 1 出站），上游 1 fd/连接，客户端 1 fd/连接 —— 与 2.2 节预算账逐字吻合。
- **RSS 线性**：网关每连接约 146 KB（Go 运行时 + 每请求遥测/usage 缓冲）；LiteLLM 每成功连接约 450 KB
  （Python/asyncio + 未成功尝试的处理开销，实际更高）。
- **TTFB**：网关热态转发首字节 ~2ms；LiteLLM 即便 1k 档也 ~650ms（Python 单 worker 事件循环 + 路由层开销）。

### 4.2 外推到 100k 在途（若端口墙被打破，见部署建议）

| 指标 | FlyingGateway | LiteLLM |
|---|---|---|
| RSS（100k × 每连接） | **~14.6 GB** | **~45 GB** |
| fd（100k × 2 + 基线） | **~200k**（< 每进程上限 245,760） | ~250k（触每进程上限） |
| 结论 | **单机大内存可承载**（需先破端口墙） | **单机不可行**（内存 + fd 双撞墙） |

⚠️ 外推是**线性外推**（基于 1k–10k 干净区实测斜率），非实测 100k —— 100k 在本环境到不了（端口墙），
按红线如实记、不伪造。**fd 预算不是 100k 的瓶颈**（400k < 491,520），**出站本地端口才是**。

## 六、结论与开源部署建议

### 6.1 结论

1. **在途并发上限**：单进程单源 IP 下，FlyingGateway 成功在途封顶 **~16–17k**（出站本地端口墙，非 fd）；
   LiteLLM 封顶 **~2k**（Python/uvicorn 突发承受力）。**FlyingGateway ≈ 8× LiteLLM 的可承载在途。**
2. **转发开销**：FlyingGateway TTFB ~2ms vs LiteLLM ~700ms（**300×+**），长连接代理场景差距悬殊。
3. **资源效率**：每成功连接 RSS 网关 ~146KB vs LiteLLM ~450KB（**~3×**）；fd 两者相当（~2/连接）。
4. **拒绝语义**：FlyingGateway 超限**优雅 502、进程可用**；LiteLLM 超限**RST 丢连接、成功率暴跌、事后退化数秒**。
   ⭐ 规则 24「不许静默 fallback / 显式报错」在实测中兑现：网关显式 502，LiteLLM 静默 RST。
5. **恢复力**：网关风暴后 ~ms 级恢复（重过载后 ~120ms）；LiteLLM 劣化到数秒。

### 6.2 系统天花板的成因（最重要的一条）

⭐ **100k 在途在本环境到不了，卡点不是 CPU/内存/fd，而是「出站本地端口 bind 排他」**：
网关→上游的每条连接要独占一个临时源端口（49152–65535 = 16384），且 bind 不按四元组复用 ⇒
单源 IP 上限 16384，多上游端口也无法乘算（实测 25k 档只成功 16288，非 8×16384）。

### 6.3 开源部署建议（如何真正打到 10 万级）

1. **多源 IP / 多网卡（首选）**：让网关出站绑定多个源 IP（多环回 alias / 多网卡 / IPv4+IPv6 双栈），
   每源 IP 独立 16384 端口空间 ⇒ 7 源 IP ≈ 114k。⚠️ 需 `sudo ifconfig lo0 alias ...`（本机无 sudo，故未实测）。
2. **SO_REUSEADDR/REUSEPORT + 按四元组复用源端口**：在网关出站 `net.Dialer` 设 `Control` 设 SO_REUSEADDR，
   使同一源端口可对不同 dstPort 复用 ⇒ 8 上游端口真正乘算到 8×16384。属**代码级优化**（本测不改 internal/cmd）。
3. **横向扩展（多实例 + 负载均衡）**：单进程 16k ⇒ N 实例 ≈ N×16k。这是最省事的生产做法。
4. **客户端侧**：压测器/客户端同样受临时端口限制，需多源 IP 或显式宽源端口区间（本测已用 20000–49151）。
5. **调大 accept 队列**：`kern.ipc.somaxconn=128` 偏浅，突发爬坡易溢出（实测 reset）；生产建议调到 1024+。
6. **LiteLLM 作为高并发 LLM 网关不推荐**：Python/uvicorn 单 worker 在 ~2k 在途即劣化、转发开销 ~700ms、
   超限静默丢连接；高并发长连接代理应选 Go/Rust 系（如 FlyingGateway）。
