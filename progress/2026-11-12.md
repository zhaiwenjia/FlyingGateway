针对老宅点名的场景，调研得出四个可落到实现层的结论：**MCP 取消规范是 fire-and-forget、无 ack、必须容忍竞态**（接收方 SHOULD 停止处理 + 释放资源 + 不发响应，MAY 忽略未知/已完成/无法取消，发送方 SHOULD 忽略迟到响应）；**OTel GenAI 的 `gen_ai.response.status` 有 `cancelled` 这个合法枚举值，但取消不算错误**（recording-errors 规范要求 span status 留 `Unset`、不设 `error.type`，语义约定编写指南亦点名 cancellations 属无法清晰归类为错误的条件）；**「取消成功」不是完整的运营指标**（arXiv 2611.08684 实测：开着重试时单靠传播取消在任何一次运行中都没恢复服务，过载后只有 12–38% 的调用被送达，被上游中止的执行已消耗其 prompt token 的 79–85%，而 vLLM 自己的 prompt-token 计数器漏掉三分之一到一半）；**取消清理必须独立于 SSE body 生成器**（OpenViking issue #6888 实测三组 ASGI 模拟用例中，生成器从未启动时只关闭 body 迭代器并不能关闭上游）。

## 二、为什么这么做

**2026-11-12 20:47:04.576**

本轮**只出文档、不写实现代码**，是老宅 2026-11-12 问卷中明确拍板的交付深度。理由有三：其一，调研结论里有多处尚未验证（agentgateway 与 Envoy 的取消传播实现未逐行核源码、各家 provider 断连即停的计费差异未逐家确认、Uvicorn+Starlette 的断连实测数据来自单一第三方实测文而非本仓实测），在未验证项上写实现会把推测固化成代码；其二，「取消」这个场景牵涉协议层、执行层、治理层、可观测层四处，先把口径与验收条款钉死再动手，比边写边改口径便宜；其三，`AGENTS.md` 规则 11 要求调研结果持久化成独立文档并逐条带出处，这件事本身就该独立成文，不该混在代码提交里。

技术栈方面，老宅授权引入 `httpx` + `FastAPI/Starlette` + `Pydantic` + `opentelemetry-sdk`，这是对规则 6「除非必要不引新依赖」的明确例外（网关要发流式 HTTP 请求、要接 OTel，标准库不够）。但**本轮不动 `pyproject.toml` 与 `uv.lock`**：这两个文件属规则 10 的排除清单、必须走 PR，且在代码尚未落地时先声明依赖会造成「配置宣称了能力、实现却不存在」的脱节。

范围切分上，MCP 与 A2A 的**协议语义**在调研文档里完整覆盖，但**实现**列入后续 spec：第一阶段的参照系是 OpenAI 兼容 HTTP 网关（这是老宅举例的「流式大模型对话网关」本体），而 MCP/A2A 是 agent-to-tool 与 agent-to-agent 的另一条轴，硬塞进第一阶段会让垂直切片失焦。同理，请求合并（coalescing）与「立即取消 vs 延迟取消」的取舍虽然 arXiv 2611.08684 给了明确证据（延迟 10 秒再取消能让重试重新挂到活着的执行上、恢复服务），但两者强耦合且需老宅定产品口径，留作未决事项而非自行拍板。

## 三、从过程和结果中学到了什么

**2026-11-12 20:47:05.624**

四条可复用的经验：

1. **「取消成功」不是完整的运营指标** —— 一个请求可以在 API 层被标成 cancelled，而引擎已经把大部分算力花掉了（arXiv 2611.08684 实测：被中止的执行已消耗其 prompt token 的 79–85%）。⇒ 判定取消是否有效，必须**同时**看「重试额外制造了多少次上游执行」与「客户端最终真正收到了多少调用」两条，不能只看取消计数；provider 自报的 token 数也不能当唯一依据（论文实测 vLLM 自己的计数器漏掉三分之一到一半）。
2. **取消传播的清理不能只挂在 body 生成器上** —— Starlette 可能在生成器挂起或尚未启动时停止消费它，此时上游连接与后台任务会泄漏，而且**泄漏得静默**（表现为连接数缓慢上涨而非报错）。⇒ 清理必须挂在独立于 body 迭代的生命周期上，做成「生成器 `finally` + 请求级 `finally`」两道闸。
3. **语义约定会搬家且未 stable，字段名要集中在一处管理** —— OTel core semconv v1.42.0（2026-06-12）把所有 `gen_ai.*` 定义迁到了独立仓 `open-telemetry/semantic-conventions-genai`，旧页面变成跳转，且全部属性仍是 Development（`gen_ai.system` 已改名 `gen_ai.provider.name`）。⇒ 所有 `gen_ai.*` 字段名集中在单一映射模块管理，升级时跑一次字段 diff。
4. **框架对普通 handler 不取消、对流式生成器才取消** —— 实测（Uvicorn 0.54 + Starlette 1.7，客户端 1 秒离开）：普通 request-response handler 跑满 5 秒不被取消；StreamingResponse 的生成器在 0.5 秒内被取消；`is_disconnected()` 轮询 1.01 秒察觉，`http.disconnect` watcher 1.00 秒取消。⇒ 非流式路径必须自挂 watcher；流式路径虽被框架取消生成器，**也不能依赖它去关上游**。

另一条方法论经验：查协议语义时，**二手工程博客几乎总能搜到「怎么做」，却很少能搜到「规范怎么说」** —— 本轮前两轮只拿到博客与宣传页，第三轮改用 `web_fetch` 直取规范原文（`.../utilities/cancellation.md`、`docs/gen-ai/gen-ai-spans.md`）才拿到 SHOULD/MAY/MUST 的逐条措辞与「cancelled 不算错误」的规范依据。⇒ 涉及「协议规定了什么」的问题，一律直取一手规范，博客只用于印证工程实践。
