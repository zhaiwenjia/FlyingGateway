# progress/ —— 事件流（按天切分）

> 本目录是本仓的**事件流**：记录「什么时候做了什么、结论是什么、还差什么」。
> 技术结论（为什么这么做、数据是多少）放 `docs/`；实验证据放 `result/`。
> 三者的分工见 `AGENTS.md` 的记录条与文档条。

## 一、文件命名

`YYYY-MM-DD.md` —— **按日归档、不带核心内容**，一个日子一个文件。

⚠️ 这与 `AGENTS.md` 命名条里的「`年月日-核心内容.扩展名`」是**两套命名**：
那套用于文档、脚本、报告；本目录的事件流**按日归档**。

## 二、每条写什么

每条**只写三段**：

1. **做了什么** —— 改了什么、跑出了什么结果；
2. **为什么这么做** —— 当时的判断与取舍（备选方案、以及不选它的理由）；
3. **从过程和结果中学到了什么** —— 经验与教训（可复用、下次能少踩的坑）。

⇒ **别的段一律不写**；段内数字必须**逐字来自真实出处**，不许推断、换算、
「合理推测」（AGENTS.md 的铁律 1）。

## 三、条目怎么写

- **记录完整事件，没有信息损失** —— 一条要能独立讲清「发生了什么、结论是什么、
  还差什么」。关键数字（版本号、百分比、测试通过数、文件行数、耗时、字节数、
  错误码）与关键实体（文件路径、函数名、API 名、字段名）都要保住，
  **拿不准就留着，不设字数上限**。
- **数据 / 结论准确** —— 压缩或改写后出现的每一个数字都必须在原始出处里逐字
  存在过，**禁止推断、换算、「合理推测」**。写错比写少严重得多。
- **在满足前两条的前提下尽量精简** —— 精简是手段不是目的。
  **不许为了压字数而丢信息**：先砍过程叙述，再砍修饰；
  砍到「删了会让人误解这个事件」就该停手。
- **每条自包含** —— 不写「接上条」「同上」「见前文」「与上一条」。
  顺序会变、指代会失效，读单条必须能读懂。

## 四、编号标注（commit / PR）

每条末尾写：

```
对应：commit <短哈希> · PR #<号>
```

或纯文档直推 main 时写：

```
对应：commit <短哈希>（直推 main，无 PR）
```

⚠️ **只认这两种形态**，不许写占位形态（如「PR 未开 —— 等授权后再开」）。

⚠️ **次序是硬约束**：commit 哈希与 PR 号**在提交之前不存在** ⇒
正确次序是「**先提交代码 → 拿到哈希 → 开 PR 拿到 PR # → 再补写记录**」；
记录本身作为**后续提交**。
⇒ **不要为了等编号而把代码和记录塞进同一次提交**（那样记录里的编号只能是空的
或伪造的）。
